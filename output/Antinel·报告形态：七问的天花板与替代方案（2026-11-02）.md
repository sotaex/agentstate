# Antinel·报告形态：七问的天花板与替代方案

**日期**：2026-11-02 深夜
**线**：C 线（主动性线）｜**议题**：DEC-10（报告形态七问）
**性质**：本文是**分析与建议**，不是已拍板决议。全文强度上限 **L0 内部自洽**（铁律 42）。
**一句话结论**：七问是个好框架，但它问的是**报告的参数**，而真问题在**报告的结论从哪来**。
替代方案不是「七问换十二问」，而是把重心从「怎么排版」移到「**结论来源 → 证据分层 → 读者动作**」三层，
并让 C 线的第三只脚落到账本里**已经写好的裁决记录**上。

> **★ 本文的量化基础全部来自可复跑量具**（`output/_p_dispatch_surface.py`、
> `_p_untraceable_split.py`、`_p_alert_surface.py`、`_p_day_denominator.py`、
> `_p_denominator_gap.py`），一次性、不进随包面、不改产品代码。
> 凡本文出现的数字，均可由量具复现；量具末尾自带「不能证明什么」。

## 〇、致读者：先说三件实测到的事

这三件事不是观点，是本轮跑出来的。**它们推翻了「七问是当前最优框架」这个前提。**

### 〇.1 真报告说「需要你看一眼 0 条」，而当天账本里有 29 次真的挡下了

`output/_p_real_report.html`（用真账本跑出的一页纸）首屏写：

> 结论 4 条｜**需要你看一眼 0 条**｜只是记录 2 条｜账本自洽检查 2 条
>
> 「需要你看一眼」为 0，是因为本报告只读账本、不读规则库：「挡下」「提醒」这两档只能由规则命中产生，
> 所以今天结构上产不出来。

而同一份账本 `.psl/audit/2026-11-02.jsonl` 里，11-02 当天：

| 口径 | 数字 | 出处 |
|---|---|---|
| 按 `decision` 值数（block + deny） | **43 条** | `_p_denominator_gap.py`【A】 |
| 其中产品侧判为「非事件」 | 14 条（全在 `pre_tool_use_summary`） | 同上 |
| **按通知面口径（真的可通知）** | **29 条** | 同上 |
| 聚合后（会话 × 规则） | **5 簇** | `_p_day_denominator.py`【3】 |

**这 29 次「动作真的没执行」，在报告里的下场是：一条都不出现。**

根因不在渲染层，在取材层：`output/lineC/evidence.py:621-622` 的 `collect()` 只跑两条腿——
`_run_json("auditor.py")`（账本自检）与 `_run_json("watchman.py")`（变化巡检）。
**两条腿都不读 `decision` 字段，也不读 `hits` / `rules_hit`。**

而 `evidence.py:41-43` 的头注白纸黑字写着：

> ★ 硬约束（代码里 assert，不是文案自律）：`挡下` 只能由**带 rule_id 的规则命中**产生。
> C 线今天读的是账本、不是规则 ⇒ **本模块一条 `挡下` 都不许产出**。

**这句话只对那两条腿成立，不对账本成立。** 它被写成模块级约束，于是整条 C 线自我阉割了：
账本里有 29 条带规则号的真裁决，而 C 线结构上「不许产出」。

### 〇.2 原料早就齐了，只是没被当成结论用

`output/lineC/watchman.py:1031` 有 `classify_verdict(decision, action)` 八档分类器
（含 `REL_SYNONYM`＝「同义两词：deny × block —— 命名未收敛」）；
`watchman.py:996-999` 的注释已经把「`decision` 与 `action` 是两套字段并存」记成了历史。
`hits[].rule_id`、`rules_hit`、`match_kind`、`match_snippet` 全在账本里。

**但这套原料今天只用于「词表收敛审计」**——它回答的是「这批词有没有收敛」，不是「今天挡下了什么」。

### 〇.3 产品侧早就造好了 C 线需要的东西，C 线一个都没用

这是本轮最关键的发现：

| 产品侧已有 | 位置 | C 线今天用了吗 |
|---|---|---|
| **通知面分档**（block/deny→GATE，alert→TOAST，allow→NONE） | `hooks/notify_policy.py:90-102` `_NOTIFY_OF_DECISION` | ❌ |
| **非事件排除表**（`pre_tool_use_summary` 等 5 类） | `hooks/notify_policy.py:118-127` `NON_EVENT_TYPES` | ❌ |
| **提醒预算守恒律** `total == used + dup + merged` | `host_shield.py:1482` `notice_budget_gate` | ❌ |
| **预算记账流水**（`notice_budget_window_closed` / `notice_budget_merged`，共 985 条） | `hooks/pre_tool_use.py:3962` `_notice_budget_trace` | ❌ |
| **六态词表**（R0/L2/L1/Ls/L0/dev） | `inbox_model.py:2218-2219` | 仅借色值 |
| **强规则优先的方向**（失败方向＝「更吵」而非「更静」） | `host_shield.py:1484-1486` 注释 | ❌ |

**C 线自己造了一套替代品**（`onepager.py` 的 `PRIORITY`、`DEFAULT_CAP=5`、`clue_ledger.py` 的 `CAP_HARD=5`），
而且造得更弱：`onepager.py:181-205` 的 `pick()` 砍掉第 6 条起就只印一句「另有 N 条」，
**没有守恒账**——被砍的那些去了哪，一页纸说不清。

> **这才是替代方案的支点。** 不是「C 线要自己再发明一套」，而是
> **「C 线要把账本里已有的、已经过产品侧实战验证的守恒式分档，接进来」。**

## 一、七问的天花板诊断

### 1.1 七问在结构上只问「参数」，不问「来源」

把七问重排，按它实际约束的对象分类：

| 七问 | 原文要点 | 它约束的东西 | 它**没有**问的 |
|---|---|---|---|
| Q1 | 谁读、什么频率 | 读者参数 | 这些结论从哪来 |
| Q2 | 一页纸几条、怎么排序 | 长度参数 | 被砍掉的那些去哪了 |
| Q3 | 骨架 | 布局参数 | — |
| Q4 | 措辞 | 措辞参数 | — |
| Q5 | 反馈怎么回 | 交互参数 | — |
| Q6 | 作废/更正怎么显示 | 状态参数 | — |
| Q7 | 出处格式 | 引用参数 | — |

**七问零命中「结论从哪来」。** 这不是遗漏——这是框架的假设：
七问默认**结论已经存在**，只是还没排版。

而本轮实测证明：结论**不存在**，不是没排版。

### 1.2 真报告的「0 条」是一个被误诊的自我安慰

那句「结构上产不出来」听起来很诚实。但它把**一条腿的限制**说成了**整个系统的能力边界**。
读者读到「需要你看一眼 0 条」，得到的信息是「今天没有需要你处理的事」——
**这是错的**。今天有 29 次动作真的没执行。

这正是铁律 22 的一个变体：**量具（两条腿）的能力上限被当成了被测对象（今天的安全性）的结论。**
量具有限 ⇒ 结论为 0 ⇒ 报 0 ⇒ 读者以为安全。

### 1.3 「一个数承担两个分母」在 C 线已经发生

本轮自己撞上了（记下来，防止再犯）：

- 我第一次统计 11-02 的「挡下」，得 **43 条**（按 `decision` 值数）；
- 按产品侧通知面口径重算，得 **29 条**；
- 差的 14 条全是 `pre_tool_use_summary`——产品侧 `notify_policy.py:108-114` 已明写：
  它与逐条 `pre_tool_use` 覆盖同一批调用，同时进通知面会提醒两次。

**两个数都对，但它们是两个分母。** 任何报告若写「挡下 N 条」而不声明口径，就是 F40。
这正是七问 Q2 里「排序规则」那一行的同类问题，只是七问没有为**分母**留位置。

### 1.4 C 线自己知道「折叠是预算问题」，但没把账做出来

`onepager.py:266-274` 的注释写得极准：

> ★ 修法不是改分母，是让折叠条目**照样带出处**……改分母等于承认「折叠的结论不需要出处」——
> 那是把预算问题说成口径问题。

**C 线已经认出「折叠是预算问题」，并解决了「折叠条目要带出处」这一半；
另一半「预算要有账」一直没做。**
产品侧 `notice_budget_gate` 恰好就是另一半的成品（`total == used + dup + merged`，原始条数一条不丢）。

### 1.5 真正被漏掉的还有两类：宿主盾自检事件，与 alert 侧的 13,581 条

**（a）宿主盾自检事件（1029 条「不可回指的裁决」）**
实测（`_p_untraceable_split.py`）：`decision=deny` 里不带规则号的 1029 条，**全部**是 `host_shield_*` 五类：

| type | 条数 | 占比 |
|---|---|---|
| `host_shield_spawn_failed` | 301 | 29.3% |
| `host_shield_tamper` | 273 | 26.5% |
| `host_shield_zone_locked` | 208 | 20.2% |
| `host_shield_breach` | 172 | 16.7% |
| `host_shield_dev_drift` | 75 | 7.3% |

其中 critical 712 条，reason 明写「**门闸无人值守**」「**须人工介入**」。
**但它们和「规则挡住了」写的是同一个 `decision=deny`。** 只按 `decision` 统计，两者被混成同一个数（铁律 44）。

**（b）alert 侧（21,927 条）**
C 线今天一条不读。其中可回指 13,581 条＝**61.9%**。
主导规则：`DST-02` 10,207 条、`AN-010` 1,438 条、`CTX-01` 741 条、`NET-03` 441 条。
聚合到「规则 × 会话 × 天」后，近 8 天**每天 10–32 簇**（中位 16）。

### 1.6 七问还漏了一个整类读者动作：主动推送的形态

上一轮已发现「七问漏了第八问」，但只当作加一条。这一轮看清了它的分量：
**主动推送是一份与一页纸完全不同的产物**——它有「该不该说」「说几句」「说到什么程度」的决策，
而七问**没有一处在问推送**。

而这恰好是 C 线的**主业**。`clue_ledger.py` 已经做出了一套推送决策
（`CAP_HARD=5`／说满 3 次静默 7 天／kind 语义分组），但**它的形态没有进入任何一份文档的讨论范围**。

## 二、替代方案：从「报告的参数」到「三层管道」

### 2.1 方案本体

**一句话**：把「报告形态」重定义为「**一条结论从账本走到读者眼前，要经过的三层**」。

```
        ┌─────────────────────────────────────────────┐
层 1    │  结论来源：这条结论从哪条账本记录来的？       │  ← 七问完全没问
        │  （可回指率 / 裁决形态 / 分母口径）           │
        └──────────────────┬──────────────────────────┘
                           ↓
        ┌─────────────────────────────────────────────┐
层 2    │  证据分层：这条来源该落到哪一档？             │  ← 七问只问措辞，不问分层
        │  （GATE / TOAST / NONE / 守恒账）            │
        └──────────────────┬──────────────────────────┘
                           ↓
        ┌─────────────────────────────────────────────┐
层 3    │  读者动作：读者看完要做什么，凭什么信？       │  ← 七问只问排版
        │  （后果 / 建议 / 出处 / 反馈）               │
        └─────────────────────────────────────────────┘
```

**七问在这三层里的位置**：Q1（读者）→ 层 3；Q2（长度/排序）→ 层 2；Q3（骨架）→ 层 2+3；
Q4（措辞）→ 层 3；Q5（反馈）→ 层 3；Q6（作废）→ 层 3；Q7（出处）→ 层 1（**七问里唯一碰到来源的一问**）。

**替代方案不是推翻七问，是给七问装上它缺的那一层，并把它从「七个并列问题」改成「三层管道上的七个挂载点」。**

### 2.2 层 1：结论来源 —— 三条判据

**判据 L1-1｜每条结论必须能指到「日文件:行号 + 规则号 + 动作」三元组。**
指不出 ⇒ 不许进结论层，只能进「已记录未判定」。
现成基础：`evidence.py` 的 `Cite(day, lineno)` 已实现；`rule_id` 字段已在 `Evidence` 里。

**判据 L1-2｜每个数字必须带口径说明，且两个分母不许混。**
具体做法：报告里每个数字后面必须能回答「这是哪个分母」——
「挡下 29 条（按通知面口径，不含 `pre_tool_use_summary`）」。
**C 线今天已有两处口径问题（性质不同，须分开说）**：

- `evidence.py:666`：`bundle.denominators["结论"] = "两条腿都跑成且都无异常 —— 这是「查了，没有」，不是「没查」"`
  ——这是**两条腿专用的结论文案**，它本身是对的（它诚实地限定了「两条腿」这个分母）；
  但它一旦被当成**整个报告**的结论分母，读者就会以为「全查过了，没有异常」。
  ⇒ **要修的不是这句话，是它的适用范围**：加第三只脚后，这句话必须随之改写，
  且必须带上「第三条腿查了哪个分母」。
- `onepager.py:505`：`b.denominators["账本"] = "33 个日文件 / 100 条"`
  ——这是**自检夹具里的硬编码**（`render()` 的自检分支），
  它只在自检里用，但**它示范了一种会被复制的写法**。
  ⇒ **报告里的分母必须由量具现算，不许硬编码**（这条对自检夹具同样适用）。

**判据 L1-3｜「查了没有」必须与「没查」在结构上长得不一样。**
这在 C 线已经是硬约束（`evidence.py:666`：「这是『查了，没有』，不是『没查』」），但只对那两条腿成立。
扩到第三只脚后，**每条腿都要单独标出它查没查、查了哪个分母**。

### 2.3 层 2：证据分层 —— 直接接产品侧现成机制

**这是替代方案的核心动作：把 C 线的第三只脚接到 `hooks/notify_policy.py` 与 `host_shield.py` 上。**

**判据 L2-1｜C 线不自己定「哪些该通知人」，改用产品侧 `_NOTIFY_OF_DECISION` + `NON_EVENT_TYPES`。**
理由不是偷懒，是**单一真源**（铁律 R4）：产品侧那张回退表已经过 70 处写入点的实战收敛，
C 线另起一套必然漂。而且**那张表已经在账本里留下 985 条 `notice_budget_*` 流水**，
C 线不接它，等于让 985 条已经记好的账变成孤儿。

**判据 L2-2｜C 线一页纸的每一格数字都必须有守恒账，且守恒式与产品侧同款。**
产品侧现成式子（`host_shield.py:1494-1501`）：
```
total == used + dup + merged
```
C 线侧对应式（**建议，待拍**）：
```
候选簇总数 == 首屏展示 + 折叠(带出处) + 合并(带计数) + 不适用(带原因)
```
**关键差别**：产品侧的 `merged` 是「合并后仍在账上可查」；
C 线现在的 `pick()` 是「砍掉 + 印一句『另有 N 条』」——**没有账**。

**判据 L2-3｜「不可回指」必须拆成两类，不得合并成一个数字。**
实测依据：不可回指的 1029 条裁决**全部**是宿主盾自检事件，
其中 critical 712 条写着「门闸无人值守」「须人工介入」。
⇒ 建议拆成 **「守住了」**（规则命中，有规则号）与 **「守不住」**（守卫自己没上班，五类 `host_shield_*`）。
**这两件事必须分别计数、分别呈现**，不能合称「不可回指」。

**判据 L2-4｜一页纸的分母必须大于 1，且「需要你看一眼」的 0 必须有唯一解释。**
真报告现在这个 0 有两种可能：真的没有，或没取材。这两者在页面上长得一样——
**这违反铁律 22 的精神（零与不可判同貌）**。
⇒ 建议：`需要你看一眼 0 条` 这个格子，只有在「第三只脚已跑成且跑出 0 条」时才许出现，
且必须同时印出「第三只脚查了哪个分母、读了多少条记录」。

### 2.4 层 3：读者动作 —— 补「后果」与「建议」

**判据 L3-1｜每条结论必须能回答「所以呢」。**
实测缺口：`evidence.py:131-154` 的 `Evidence` dataclass 字段＝
`eid / claim / strength / cites / source / read_at / rule_id / blind / items / status`
——**无「后果」字段、无「建议」字段**。
⇒ 建议加 `consequence`（必带）与 `advice`（可选，但为空时须显式写「不需要动作」）。
这与铁律 30「做不到分档（判/处/记/托）」一致：「不需要动作」是合法的一档，
**但它必须被显式说出来，不能靠字段缺失表示。**

**判据 L3-2｜措辞只许有一份，且必须从产品侧派生。**
`evidence.py:82-88` 的 `WORD`（`held/alert/log_only/no_response/checked`）是 C 线的**第二份中文态名表**，
且与产品六态只有两档重合。
⇒ 建议：C 线的中文措辞**改为从 `inbox_model.STATE_LABEL` 派生**，
`WORD` 只保留「内部键 → 态」的映射，**中文一律不自己写**。
（附带解决上一轮发现的 S08 判据漏洞：S08 按键名扫六态键，换一批键名即绕过——
**改成派生后，这个漏洞自动消失**，因为不再有第二批中文词表。）

**判据 L3-3｜反馈必须拆义。**
`ack` 一个词在两处担两义：C 线读成「你确认过了」，产品页面读成「已处理 N」。
⇒ 建议拆成 `claim`（我已看到）／`reply`（我的处置）／`recheck`（处置后复验）。
`clue_ledger.py:395-404` 的 ack 指纹逻辑（`acked_fp != fp` ⇒ REOPENED）已经是这个拆义的雏形，
**但只做到「同值/异值」，没做到「三种语义」**。

### 2.5 层外：第八问（主动推送形态）—— 从附注升为独立一章

上一轮只把「推送形态」当作七问的补充。本轮看清了它该独立成章，理由有二：

1. **它是 C 线的主业**（`INITIATIVE.md`：唯一正当领域＝「系统知道 · 用户不知道自己需要」那一格）；
2. **它有一页纸没有的决策**：「该不该说」——一页纸是被动的，推送是主动的。

建议的推送形态骨架（四问，与七问不是同一类问题）：

| 问 | 内容 | 依据 |
|---|---|---|
| P1 | 这一条**够不够格**说？（阈值由 kind 语义决定，不由条数决定） | `clue_ledger.py:132-136` `FAULT_KINDS`／`EVENT_KINDS` 已实现 |
| P2 | 说到什么程度？（全文 / 一句 / 只说「有 N 条」） | `clue_ledger.py` 的 `kind` 语义分组 |
| P3 | 说过几次了？什么时候可以不再说了？ | `CAP_HARD=5`／说满 3 次静默 7 天 |
| P4 | 说完了，人回了吗？回的东西去哪了？ | `clue_ledger.py` 的 ack 链；**C 线自己的回执没有入口** |

**P4 是本轮的新发现**：`clue_ledger.py` 能记「说过几次」，但**没有一个入口能记「人回了什么」**。
而 `corrections.py` 的更正链只能记「我们改了报告」，记不了「人回应了」。

## 三、可验收判据（含负控）

铁律 9 四件套：**正判据／反向对照／连带对照／可观测**。

| 判据 | 正判据 | 反向对照（负控） | 连带对照 | 可观测 |
|---|---|---|---|---|
| **J1 来源可回指率** | 每条结论有 `日:行 + 规则号 + 动作` | 造一条无规则号的，**必须**掉到「已记录未判定」 | 掉了则 `citecheck` 要报 | 页面 `data-cites` / `data-rule` |
| **J2 分母不混装** | 每个数字带口径说明 | 同一句里塞两个分母，判据**必须**报红 | 报红要指出是哪个数 | 数字旁的口径括号 |
| **J3 守恒账** | `候选 == 展示 + 折叠 + 合并 + 不适用` | 改任一项使不等式破裂，**必须**报红 | 破裂要指名哪一项 | 页面守恒行 |
| **J4 三态不分装** | 「查了没有」≠「没查」≠「不适用」 | 制造「没跑成」，页面**必须**长得不一样 | — | 页面三态标记 |
| **J5 守不住不被混装** | 宿主盾自检事件单独计数 | 把 `host_shield_*` 混进规则命中计数，**必须**报红 | 与 J3 联动 | 页面分栏 |
| **J6 措辞单一真源** | 中文态名从产品侧派生 | 改 `WORD` 的中文值，页面**必须**跟着变 | 改一个词要能改全页 | 全仓唯一声明处 |

**J6 的负控特别重要**：这是把上一轮发现的「S08 判据漏洞」变成自证漏洞的判据——
负控就是「手工改 `WORD` 的中文，看页面是否同步变」。若不同步，说明还有第二份词表。

### 3.1 判据自身必须有负控（本轮教训）

上一轮已犯过一次：**判据「报告里有出处」没有负控**，
结果「用假出处的条目也能通过」——**这是把「夹具污染」当成了「检测器灵敏」**（铁律 22）。
所以本次每条判据都必须配一条「明知该红却绿了」的负控臂。

### 3.2 一处必须纠正的量具错账（本轮自曝）

**我先前口头说的「当天 43 次真实挡下」，口径不完整。**
按 `decision` 值数是 43 条，但其中 14 条是 `pre_tool_use_summary`——
产品侧已把它判为非事件（与逐条 `pre_tool_use` 覆盖同一批调用，同时通知会提醒两次）。
**按通知面口径的真实数字是 29 条。**

⇒ 这条记进 `TOOLPIT.md` 一类的坑位：**同一个「挡下」有两个分母，报告里必须声明用的是哪个。**

## 四、边界：本文不能主张什么

铁律 21：对外强度 ≤ 内部最保守定性。本文全部内容为**内部 L0 级**，不构成对外承诺。

1. **不能主张「C 线应该读裁决记录」是已定的产品判断。** 这是创始人拍板的事（列入 §五）。
   本文只能主张：「数据在账本里，带着规则号、行号、会话号，且当天有 29 条」。
2. **不能主张那 29 条都是真发现。** 它们可能含夹具、可能重复计数；
   `_p_day_denominator.py` 末尾已明写这条限制。
3. **不能主张 alert 侧 13,581 条该给人看。** 可回指率高只说明「可回指」，不等于「值得看」。
4. **不能主张宿主盾自检事件该进一页纸。** 今天它们只是「另一个计数维度」，不是结论。
5. **不能主张本文方案已实现。** 本文是分析，不是产品代码；按阶段纪律，本轮**产品代码零改动**。
6. **Q4（措辞）那条「已定」在现实里是错的**——上一轮已查明：
   `glossary.RETIRED_WORDS` 已把「出事／失守／拦截／注意」四词全部判死，
   而七问 Q4 要定的第一个词「已拦截」正是其中之一。
   **本文不改 Q4 的结论，但必须指出它是已判死的错名**（铁律 21 的反面：不许把已作废的东西当已定）。
