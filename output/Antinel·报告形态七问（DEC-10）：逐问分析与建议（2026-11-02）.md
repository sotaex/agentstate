## 二、七问逐问

### Q1 频次：日／周／月？默认哪个？

**现状**
- **【实测】**七问原文：未定（`...2026-10-29.md:61`）
- **【实测】一页纸今天根本没有周期**：只有 `read_at` 读数时刻（`onepager.py:287,302,306`）⇒ 它是**按需拉取**的，频次问题在它身上**不成立**
- **【实测】**真正有频次的是线索账本那条路，而且**频次已经被拍过了**：
  - 静默按 kind 语义分组：`FAULT_KINDS = {absent, anchor, verdict, baseline}` **天天说、永不静默**；`EVENT_KINDS = {rule_pair, first_seen, repeat, gap}` **说一次就够**（`clue_ledger.py:132,136,142`）
  - `CAP_HARD = 5` 硬上限，且**不因为今天发现 20 条而放宽**（`clue_ledger.py:97,31`；`:473-474` 有断言）
- **【实测】**噪声基线：12 条线索 strict 精确率 **16.7%**（2 true / 2 weak / 8 noise，`output/lineC/noise_baseline.json`）

**关键洞察**
1. **主动性的正确形态不是「定期报告」，是「只在需要你做事时开口」。** 定期报告把「我按时报了」当成交付，可用户收到的 83.3% 是 noise ⇒ **定期报告是噪声制造机，不是主动性**。主动性 v3 已拍板「gap 默认关闭」「静默按 kind 语义分组」，正是这个方向。
2. **频次与读者耦合**：用户自己＝事件驱动；管理者＝周／月；监管＝按需。**同一个频次对三种读者是三种东西。**
3. **【实测】「每天发一份」的形态今天已经自证失败**：12 条金标准里 8 条是 noise，其中 `host:www.microsoft.com`、`path:D:/Application`、`cmd:chmod|Get-Location|probe|printf` 三条都是「每天都会发生的事」。

**【建议】**
- **一页纸：按需 + 事件驱动，不设周期。** 理由：读者是用户自己，而**用户自己触发时才有上下文**（他刚被什么绊住了，才想知道账本怎么样）。
- **线索推送：不设频次，只设「该不该说」。** 已有 kind 语义分组就是判据。**真正要新增的不是频次，是「今天没有该说的」这件事的表达**——即**清白信**（不是空输出，也不是静默）。
- **管理者／监管两路：本轮不定**（B2-2，商业决定）。

**可验收判据**
- ① 一天内推送条数 ≤ `CAP_HARD`（已有硬断言）
- ② **清白信可构造**：无 speakable 线索时，账本产出一份「今天没有需要你回应的线索」，而不是空输出或静默退出
- ③ 连续 30 天推送的 strict 精确率 ≥ 基线 **16.7%**（噪声打分器 `output/_p_score_noise.py` 已具备该能力）

**【待拍】** 清白信发不发？发给谁（只有用户自己，还是也给管理者）？

### Q2 长度：一份报告几条结论？

**现状**
- **【实测】**`DEFAULT_CAP = 5`（`onepager.py:84`）；`pick()` 按 `PRIORITY` 排序（`onepager.py:65-71,181-205`）
- **【实测】**`pick()` 自报裁量：「共 N 条，这里显示 N 条、折叠 M 条。排序规则：按结论强度，同强度按证据 id 字典序」（`onepager.py:199-201`）
- **【实测】**折叠用原生 `<details>`，且**折叠条目照样带出处**（`onepager.py:261-283`）；自检里有一条「折叠样本也要查 `**`」，因为「只在折叠时才渲染的文案从未被检查过」（`onepager.py:685-690`）
- 原则（原文第 62 行）：底层可以厚，界面必须薄，建议 3~5 条

**关键洞察**
1. **今天排的是「强度」，不是「可行动性」。** 而 `K_CHECKED`（已核对）**根本不是结论**——它是分母／账本自洽性检查（`evidence.py:178-186` 的 `strength_note` 自己写着「这是账本自洽性检查，不是拦截结论」）。**它和结论抢同一个 5 条名额，是分母挤掉了结论。**
2. **【实测】C 线今天真正的结论只有 1~2 条，不是 5 条**：
   - 「挡下」「提醒」在 C 线**结构上产不出来**（只读账本、不读规则库）——`onepager.py:345-354` 明写这件事并要求自报
   - ⇒ 实际能出现的只有「已记录未判定」「已发现无法处置」，外加一个**不是结论的**「已核对」
3. ⇒ **长度这个问题今天问错了对象**。不是「一页几条」，是「**首屏几条 ＋ 折叠几条 ＋ 分母几条**」。

**【建议】三层长度，不是一个数**

| 层 | 内容 | 排序轴 | 硬约束 |
|---|---|---|---|
| **首屏** | 需要用户现在能行动的 | **可行动性**（能不能现在做点什么） | 0~3 条 |
| **折叠区** | 其余结论 | 强度 | 全部 |
| **分母区** | 「已核对 N 条」「账本自洽检查」等 | —— | **物理分开，不占结论名额** |

- 硬上限**同源**：`CAP_HARD` 已在线索侧守住（`clue_ledger.py:97`），一页纸侧建议取同一个常量，**不许各处写一个 5**（铁律 44：同值不同义比不同值更难发现）。
- 「折叠的不代表不重要，只代表这一页放不下」这句自报**保留**——它是裁量自报（铁律 30 的可读侧），只是要补一句「**分母区的条目不是结论**」。

**可验收判据**
- ① 首屏任一条目必须能回答「用户现在能做什么」；答不出就不许进首屏
- ② 首屏 ＋ 折叠区的条数 == 结论总数（**分母不算结论**）——今天 `pick()` 已能算，改的是分类不是分母
- ③ **新增判据**：首屏不得出现 `data-strength="checked"` 的条目。**这条今天必然能抓到东西**，因为 checked 条目会跟着 `shown` 一起进首屏

### Q3 骨架：事实＋出处＋后果＋建议，四件都要有？

**现状**
- **【实测】**七问原文：未定（原文第 63 行）
- **【实测】`Evidence` 的字段是**：`eid / claim / strength / cites / source / read_at / rule_id / blind / items / status`（`output/lineC/evidence.py:131-154`）
  ⇒ **没有「后果」字段，也没有「建议」字段。**
- **【实测】「后果」今天藏在强度限定语里**：`strength_note()`（`evidence.py:178-186`）已经在提供第二句——
  - `K_NO_RESPONSE` → 「已发现，但没有可执行的处置手段」
  - `K_LOG_ONLY` → 「已记录，未作判定（不知道是否危险，只知道它变了）」
  ⇒ 这两句**就是后果**，只是被绑在 strength 上
- **【实测】「出处」这一件已经最扎实**：`Cite` 带 `what`（「这一行是什么」，供人眼复核）、带 `day_level`（「整天 · 该日无行号可指」）（`evidence.py:98-124`）；`citecheck` 逐条校验 `data-cites` 可解析（`citecheck.py:46-49`）

**关键洞察**
1. **四件套里有两件是伪需求**：
   - 「建议」不是每条都有。不需要动作的结论硬凑一条建议＝**编造**。而铁律 30 明确「做不到」可以停在任意一档——**「不需要动作」是合法的一档**。
   - 「后果」在多数情况下就是强度限定语的延伸，硬拆成独立字段会让同一句话说两遍。
2. 但**「后果」必须有位置**——因为它决定用户要不要看。「已记录，未作判定」和「已发现，但没有可执行的处置手段」，用户的反应完全不同：前者只是知情，后者是要去找人。⇒ **它值得独立成字段。**
3. ⇒ **「建议」不该是字段，该是「可行动性」的一个属性**（与 Q2 首屏排序用同一个轴）。

**【建议】三件必带 ＋ 一件可选**
- **必带**：① 结论（`claim`）② 出处（`cites` + `what`，人可复核）③ **后果（`consequence`，新增字段，必带非空）**
- **可选且必须显式**：④ **建议（`advice`，新增字段，默认空）**——不存在时写「**不需要动作**」，**不许留白，也不许编**
- 落法：`consequence` 由 `strength_note()` 的现有文案**升级为独立字段**（今天它已经是事实上的第二句）；`advice` 新增。
- **「不需要动作」四字必须由渲染层从「advice 为空」推出，不许由模型自由生成**——自由生成 = 编造。

**可验收判据**
- ① 每条证据必须有非空 `consequence`（构造时校验，不是渲染时提醒）
- ② `advice` 为空时，产物必须出现「不需要动作」；`advice` 非空时，产物**不许**同时出现「不需要动作」（两态同貌 ⇒ 用户不知道自己该听哪个）
- ③ 渲染层不许自己造建议（建议只能来自 `advice` 字段）

### Q4 三种措辞不许互换：「已拦截／已发现无法处置／已记录未判定」

> ★ **本轮最重要的发现：这一问的「已定」定的是一个已经作废的词表。**

**现状**
- **【实测】**七问原文（第 64 行）：「三种措辞不许互换」，且标为**七问里唯一定了的一条**
- **【实测】「已拦截」是产品已经判死的错名**：
  - `glossary.RETIRED_WORDS` = {**出事**, **失守**, **拦截**, **注意**}，四个**全部判死**
  - `inbox_model.py:165` 明载旧标题「已拦截：越界动作被挡下」已弃用，理由是「把『缺口』说成『已拦截』，是**方向反了**的标签」
  - ⇒ **七问唯一「已定」的那条，定的第一个词就是产品已判死的词。**
- **【实测】产品现行真源是两张表**：
  - `STATE_LABEL` = {R0:**没守住**, L2:**挡下**, L1:**提醒**, Ls:**缺粮**, L0:**值守中**, dev:**研发中**}（`inbox_model.py:2218`）
  - `EVENT_LABEL` = 同值（`inbox_model.py:2263`）
  - 取名唯一入口 `state_short()` / `event_short()`（`inbox_model.py:2229`）；产品内部已全线派生（例：`inbox_server.py:3070` 就是 `M.event_short(lv)`）
- **【实测】C 线的 `WORD` 是货真价实的「第二份声明」**（`evidence.py:82-88`）：

  ⇒ 与产品**只有「挡下」「提醒」两档重合**，后三档在产品六态里**没有对应**
- **【实测】S08 判据本该抓它，抓不到**：
  - `_source_files()` 走 `os.walk(ROOT)`，`_skip_dir` 只跳过 `.`开头／`__pycache__`／`_uxtest`／`assets`／`ci`／`build*`／`dist*`／`.away`（`ci/inbox_guards_0372.py:1082-1107`）
    ⇒ **`output/` 在扫描范围内**，`evidence.py` 也不被 `_p_` 规则排除（`:1100`）
    ⇒ **它是被扫到的**
  - 没报红的原因：正则只认六态键 `"R0|L2|L1|Ls|L0|dev"`（`0372.py:918-919`），而 C 线用的是 `held/alert/log_only/...`
    ⇒ **换一批键名，就能绕过「第二份声明」判据**
- **【实测】「看不见」不是六态之一**：它只出现在 `TITLE_OF_KIND` / `TITLE_OF_TOPIC` 的标题前缀里（{挡下, 提醒, 没守住, **看不见**, 缺粮}），**不在 `STATE_LABEL`，也不在 `glossary.TERMS`** ⇒ 产品有一个**只用于标题、不用于灯态**的第五个前缀词

**关键洞察**
1. **Q4 问错了对象**：它问「三种措辞不许互换」，但真正的问题不是措辞，是**报告层不该拥有措辞**。七问把「定词」当成了任务，而正确的动作是**删掉报告层的词**。
2. C 线那三档「已记录未判定／已发现无法处置／已核对」**不是产品态**，它们是 C 线自己的**记账处置档**。两套词表叠加出今天最危险的一种形状：**同一个数字在两个层用两个名字**（C 线说「已记录未判定 3 条」，产品说「提醒 0 条」——读者无法判断这是同一件事还是两件事）。
3. **【实测】今天页面上真正出现的，恰好是 C 线自造的那三档**：因为「挡下／提醒」在 C 线结构上恒空 ⇒ **两套词表重合的两档恰好都是空的**。所以「第二份声明」今天不是洁癖，是**实打实的**。
4. ⇒ **「不可判／不适用／没有」三态必须留在 C 线**，不许硬塞进产品六态（塞进去就是「一词二义」）。产品侧的「看不见」是**标题前缀**，不是灯态档位——**不能拿它当「不可判」的容器**。

**【建议】**
1. **删掉 C 线 `WORD` 的中文表，改为从产品派生。** C 线强度键 → 产品态键写成一张**显式映射表**（held→L2、alert→L1），中文一律走 `M.state_short()` / `M.event_short()`。
   **只有当 C 线那一档在产品六态里也有对应时，才允许出中文词**；没有对应的三档（已记录未判定／已发现无法处置／已核对）**必须保留 C 线自己的词，并显式标注「这是记账处置档，不是灯态」**。
2. **七问第 4 条的答案改为一条纪律**，不是一份词表：
   > **报告层只许有一份措辞（产品的）；C 线自造的那份必须逐档标注「非灯态」。**
3. **补一条守卫判据**（今天可做）：在 `output/lineC/` 新增判据，扫「C 线内是否有第二份**中文**态名表」——**按中文词扫，不按键名扫**。今天 S08 是按键名扫，所以漏了。（详见 §五）
4. **顺带核实一个语义**：C 线的 `K_CHECKED`（已核对）与产品的 `L0`「值守中」**不是一回事**（前者是「查过了」，后者是「在看着」）⇒ 两者**不可合并**，更不可共用一个词。

**可验收判据**
- ① `output/lineC/` 下除显式映射表外，**不得出现** `{"R0": ...}` 形态的中文态名表（今天 0 处，但要有守卫）
- ② 产物页面上每一个中文态词，要么属于产品六态，要么**紧邻**出现「记账处置档」标注
- ③ **反向验证（这条能证明「派生」不是「又抄了一份」）**：把产品 `STATE_LABEL["R0"]` 改一个字，报告页面对应词**必须跟着变**

### Q5 闭环三件套：通知 → 回复（谁改、何时改）→ 复查（改了没）

**现状**
- **【实测】**七问原文（第 65 行）：全空。原文自己写了理由：「★ 第 5 条是整个『监理』类比里最实的一块，我们跳过了」，并引 **GB/T 50319**：监理通知单 → 施工单位回复单 → 监理复查记录；「**没有回复和复查，通知单就只是抱怨**」
- **【实测】产品已有闭环的「回复／处理」半边**：
  - `inbox_server.py:3076` 的「已处理 N」过滤（`f=closed:{d}`）**基于账本 `acked` 计数**
  - `NOTE_REQUIRED_TO_IGNORE = ("R0",)`（`inbox_model.py:315`）⇒ **忽略 R0 必须写理由**（`:1464` 强制）
- **【实测】C 线 v3 已拍板「`--ack` 变了就重开」**：`clue_ledger.py:395-404`——`acked_fingerprint != fp` ⇒ `REOPENED`（说，并标明「你确认过的那件事变了」）；同值 ⇒ `ACKED`（静默）
- **【实测】闭环数据结构仍缺三样**：
  1. **回复单没有结构**（谁改／何时改／改了什么／凭什么说改好了）
  2. **复查没有证据**（`ack` 是用户自述，无外部确认）——这与 `corrections.py:56` 自报的「`by` 是自述，没有身份验证」**是同一个缺口**
  3. **复查结论没有落点**（`REOPENED` 只重开，没归档「复查结果是什么」）

**关键洞察**
1. **GB/T 50319 的三件套不是比喻，是字段设计。** 「通知单 → 回复单 → 复查记录」是**一张表的三行**，不是一个流程图。⇒ 回复单与复查记录必须是**账本记录点**（铁律 38：记录点可无限长），不是报告里的一个章节。
2. **「回复」不是「用户回一句话」——它是责任认定**。用户回「我改了」⇒ 责任转移给用户；系统回「查过了，确实没问题」⇒ 责任还在系统。**两者必须能区分。**
3. **【实测】今天已有的 `--ack` 其实是「复查」的雏形，但方向反了**：
   - `ack` = 「我认为你确认过了」⇒ **被动**（我认领了）
   - 复查 = 「我回访过，状态确实变了」⇒ **主动**（我验证了）
   - ⇒ `REOPENED`（内容变了就重开）已经是主动复查的**触发条件**了，缺的只是「复查结论」这个落点。
4. **★ 今天 `ack` 一个词担了两个义**：
   - C 线：`ack` = 「你确认过了」⇒ 静默线索（`clue_ledger.py`）
   - 产品：`已处理 N` = 账本 `acked` 计数 ⇒ 产品把它**读成了「已处理」**（`inbox_server.py:3076`）
   ⇒ 「我认领了」被读成「我处理完了」。**这是铁律 44「同值不同义比不同值更难发现」的现成实例**，而且它已经出现在对外页面上。
5. **本条决定批 2 能不能开工**（原文第 66 行后：「⇒ 这一条决定批 2 能不能开工，优先级最高」）。但要修正一处：**七问说它「全空」是 10-29 的状态**——今天它有半条腿（ack ＋ 忽略需理由），缺的是**回复单与复查记录的数据结构**。

**【建议】**
- **闭环三件套落成三个记录点，不是三段文案**：

| 件 | 名字 | 字段 |
|---|---|---|
| 通知 | notification | 今天已有（`clue_ledger` 的 speakable 集合） |
| **回复** | reply | `actor`（谁）＋ `at`（何时）＋ `action`（做了什么）＋ `evidence`（凭什么说改好了） |
| **复查** | recheck | `reply_id`（对哪张回复单）＋ `method`（怎么查的）＋ `verdict`（已闭环／未闭环／不适用） |

- **`ack` 拆成三个词**：今天一个 `ack` 承担了「知悉／认领」「处理完了」「已复查」三义。⇒
  - `claim`（知悉／认领）—— 今天 `ack` 的真实语义
  - `reply`（回复：我做了什么）
  - `recheck`（复查：状态确实变了吗）
  - 产品侧「已处理 N」应改为「**已回复 N**」或「**已认领 N**」，**不许继续叫「已处理」**（今天这个词在页面上已经骗了人）
- **铁律 38 的落点**：回复单与复查记录都属于**记录点**，不是**判据**。判据仍然是那 37 条。⇒ **闭环扩充的是记录点，不扩充判据**——这保住了「判据必须克制」。

**可验收判据**
- ① 任一被通知的线索，在账本里都能查到它的回复单**或**明确的「不需要回复」记录（**不许静默消失**）
- ② 任一回复单都能定位到它所回复的通知单（`reply.notification_id` 必须可解析）
- ③ `claim` / `reply` / `recheck` 三个词在产品侧与 C 线侧**各自只许一个含义**（今天 `ack` 一个词两个义，**这条今天必然红**）

**【待拍】** 回复单要不要人工署名？——**这一条决定它是「留痕」还是「追责」**。（今天 `by` 是自述，无身份验证；且署名会引入隐私与存储成本，对应铁律 40 的订阅定价。）

### Q6 更正机制：已发布的报告里有一条错了怎么办？

**现状**
- **【实测】**七问原文（第 66 行）：全空，「且这是记账型产品最危险处——记录错了比没记更危险，因为它看起来像证据」
- **【实测】今天它不是全空**——C 线有 `output/lineC/corrections.py`（568 行）：
  - 三条硬约束（写前 hash 比对、`target_eid` 必须在那份报告里真实存在、一条证据只许被取代一次；`corrections.py:26-33`）
  - 作废横幅在**首屏**（`onepager.py:310-318`）、反向指认（`onepager.py:320-326`）
  - 被更正条目**仍在原位置、不折叠、不隐藏**，加删除线（`onepager.py:145-150` 注释与 `.ev.superseded` 样式）
  - 渲染→`citecheck`→落盘→**逐字节读回比对**，**根本不产生临时文件**（`report.py`）
  - 更正记录**读不出来要停**，不许静默当成「没有更正」（`onepager.py:726-727`）
- **【实测】它自报三条「不能证明什么」**（`corrections.py:49-56`）：不能防故意更正／不能覆盖整份报告被悄悄替换／`by` 是自述

**关键洞察**
1. **七问把 Q6 当成「待设计的机制」，它其实已经是「已实现但没有对外形态」的机制。** 真正缺的不是机制，是**对外怎么说**：「这份报告被更正过」这句话，读者看到的是什么？作废横幅给了内容，但**没有给「更正链」这个概念**——一份报告被更正 3 次，读者看到的是三个横幅里的一个，而不是一条链。
2. **更正机制的第一性问题不是技术，是「不可变 vs 可更正」的哲学定位**。方案书 §5.5 原文：「记录错了比没记更危险，因为它看起来像证据。」⇒ 更正的语义**不是「改掉」，是「标出这一条当时判断错了」**。
   ⇒ **今天 `corrections.py` 的做法（`supersede` ＋ 原条目留在原位加删除线）正是这个语义——做得对。**
3. **【实测】但页面上仍有一处会让人误读**：`onepager.py:138-139` 明写「作废用中性色，不用红 —— 红色会让读者以为发现了安全问题，而实际可能只是口径修正」。**这个判断是对的**，但反过来：**如果读者不知道「作废」是什么**，他会以为这是一次事故报告。⇒ 缺的是**一句话的解释**，不是更多机制。

**【建议】**
- **把「更正」升级为「更正链」**：一份报告有 `report_id`、有 `supersedes` 集合、有一条只追加的更正记录。第三方拿到任一份报告，能看到「本报告取代了谁、被谁取代」。
- **对外强度写成一句话，不许升级**：「更正只追加、不可改写；原结论留在原位并标注作废」——**不许说「不可篡改」**（`corrections.py:49-52` 自己禁止）。
- **必带定语**：更正机制证明的是**「改过会留痕」**，不是「没被改过」。今天的技术边界就在这里，**不许越过**（铁律 21）。
- **补一句页面上的人话解释**：作废横幅必须写清「作废 ＝ 当时判断有误，**不是**发现了安全问题」。

**可验收判据**
- ① 更正记录读不出来时**报告拒绝落盘**（今天已做，`onepager.py:726-727`）
- ② 被更正条目仍在产物里且带删除线（今天已做，`onepager.py:583-589`）
- ③ **新增**：作废横幅必须带一句话解释「作废 ≠ 出了安全问题」。**今天 CSS 注释里有这个意思，页面上没有**——这是本条今天唯一真正缺的

### Q7 用户看不懂怎么办（`DST-02`、`evidence_class` 这种词）

**现状**
- **【实测】**七问原文（第 67 行）：举例 `DST-02`、`evidence_class`
- **【实测】举例本身是假想**：`DST-02`、`evidence_class` 在 `output/lineC/` 的代码与两个 HTML 产物（`design_evidence_ui.html`、`design_evidence_ui_v2.html`）里**各 0 命中**
- **【实测】今天真实会出现在用户眼前的内部标识**是这些：
  - `AUD-2c0abc2c`（稳定哈希 id）——`evidence.py:297-299` 解释过为什么**不能**用 `AUD-{i+1:02d}`（下标会随条数漂移）
  - `WCH-...`（watchman 线索 id，`evidence.py:438`）
  - `rule_id`（如 `AN-002` / `SEC-01`）
  - `data-eid` 属性值
- **【实测】`citecheck` 只管机器能不能核，不管人看不看得懂**：它校验的契约属性是 `data-eid` / `data-strength` / `data-cites` / `data-rule` / `data-status`（`citecheck.py:46-49`）⇒ 这些是**机器契约**，正确地不该出现在正文；但 `claim` 字段里的内部编号**没人管**
- **【实测】产品已经有「人要能核」这个意识，只是没覆盖到「编号」**：`Cite.what` 是为「人眼复核」设计的（`evidence.py:100-107`：「光有行号，读者仍要自己打开文件才知道对不对」）

**关键洞察**
1. **「看不懂」有两类，解法完全不同**：
   - **术语型看不懂**（`evidence_class`）⇒ 解法是**换词／加解释**
   - **结构型看不懂**（`AUD-2c0abc2c`）⇒ 解法是**分层**：编号不是看不懂，是**不该在这一层看**
   ⇒ **「看不懂」多半不是词的问题，是信息层级的问题。**
2. **★ 「标签化」是最大的风险**：把 `AUD-2c0abc2c` 做成「证据 #3」，读者会以为「3 号」是稳定的、可引用的编号——而它的稳定性恰恰来自哈希（**内容变了 id 就变**）。**给人一个看起来像编号、实际会漂的编号，比不给编号更危险。**（铁律 44 的变体：编号的「可引用性」暗示与实际漂移不同义。）
3. ⇒ **正文不该出现任何内部 id**。内部 id 已经在 `data-eid` 里、在 `data-cites` 里、在脚注的出处里——**够了**。

**【建议】**
- **正文零内部编号**：`AUD-` / `WCH-` / `AN-` / `SLOT-` / `REC-` / `DST-` 一律不进正文。折叠区与脚注可以出现 `data-cites` 的定位（`2026-10-31:412`）——因为那是**可复核的位置**，不是**会漂的编号**。
- **术语白名单**：报告层不许自己写术语，一律取自 `glossary.TERMS` 的 `one` 字段（那已经是大白话定义，`glossary.py` 里 R0/L2/L1 都有）。
- **Q7 的第二类＝「不知为何重要」**：这不是术语问题，是**后果没写清**（Q3）。⇒ **Q7 与 Q3 必须一起解**，单治 Q7 无效。

**可验收判据**
- ① **新增判据**：产物正文（不含脚注／折叠区）不含 `AUD-|WCH-|AN-|SLOT-|REC-|DST-` 前缀 token
- ② 产物正文里的每个中文术语都能在 `glossary.TERMS` 里找到（**术语不许自造**）
- ③ 折叠区／脚注里的出处**可复核**（今天 `citecheck` 已守）
