## 3 段一（0–25 min）：线索模型

### 3.1 一条线索长什么样

```python
@dataclass(frozen=True)
class Clue:
    kind: str          # baseline | first_seen | rare_pair
    day: str           # 归属日 YYYY-MM-DD
    subject: str       # 一句话说清「什么变了」
    evidence: tuple    # ((day, lineno), ...) —— 回指，不许空
    note: str = ""     # 附注（分母、口径）
```

**三条不许破的纪律**：

1. **`evidence` 不许为空。** 没有回指的线索是「模型说的」，不是「账本里的」。这是设计稿 §2.1 红线。
2. **一条线索只能有一个 `kind`。** 混装会让「有几条线索」失去意义（F40 口径混装）。
3. **不出现「危险」「可疑」「违规」这些词。** 只说「变了」「首次出现」「从未同时出现过」。

### 3.2 读取层

```python
def iter_records(root=".psl/audit"):
    """只读。返回 (day, lineno, rec)；lineno 从 1 起，与文件行号一致。"""
```

**必须排除** `lock_events.jsonl`（实测 5779 行，字段完全不同，混进来会污染分母）。
**必须跳过不可解析行但计数**——`unparsed` 要打印出来，不许静默吞掉（铁律 45：
扫描器崩溃的表现是「没有那条记录」，不是「空列表」）。

## 4 段二（25–70 min）：三个检测器

### 4.1 D-1 基线偏离（`kind="baseline"`）

| 项 | 内容 |
|---|---|
| 问什么 | 某一天的动作量，相对这台机器过去 N 天的常态，偏了多少 |
| 怎么算 | 每日 `pre_tool_use` 计数 → 取前 14 天的**中位数 M** 与 **MAD** → 当天偏离 > 3×MAD（且 \|M\| ≥ 10）判偏离 |
| 为什么用中位数不用均值 | 均值被离群日拖走；这台机器有闸门日（几千条）与休息日（0 条），均值无意义 |
| 输出 | 「10-30 有 6380 条 pre_tool_use，前 14 天中位数 1200，偏离 5.3 倍」＋ evidence 指向当天第 1 行 |
| 空转长什么样 | 全期无偏离 ⇒ 打印 `0 条（分母：33 天，窗口 14）` |

### 4.2 D-2 首次出现（`kind="first_seen"`）

| 项 | 内容 |
|---|---|
| 问什么 | 某样东西，在全部历史里第一次出现，出现在哪一天 |
| 抽什么 | ① Bash 命令的**首词**（`input.command.split()[0]`）② URL 的**主机名**（正则）③ 写入的**目录前缀**（`input.file_path` 的前两段） |
| 怎么算 | 全期建集合；按时间顺序扫，首次进入集合的那条即「首次出现」 |
| 为什么这条最强 | 基线偏离只能发现「量变了」，首次出现能发现「**性质变了**」——新工具、新域名、新目录 |
| 输出 | 「10-31 首次出现命令 `ollama`」＋ evidence 指向该行 |
| 边界 | 首次出现的**数量**与观察窗口强相关：33 天窗口下，前几天必然大量「首次出现」⇒ **只报最后 3 天**，且必须写明窗口 |

### 4.3 D-3 罕见组合（`kind="rare_pair"`）

| 项 | 内容 |
|---|---|
| 问什么 | 两条规则**从来没同时命中过**，某天同时命中了 |
| 怎么算 | 每条记录的 `rules_hit` 是集合 → 全期统计共现矩阵 → 找「共现次数 == 1」的配对，且这一对的两条各自单独出现过 ≥ 3 次 |
| 为什么要「各自单独出现过 ≥ 3 次」 | 否则两条都只出现过一次，共现一次是必然的，不是异常（**这条不加，D-3 会全是噪声**） |
| 输出 | 「`AN-0xx` 与 `AN-0yy` 首次同时命中，10-31」＋ evidence 指向该行 |
| 空转长什么样 | 无 ⇒ 打印 `0 条（分母：N 个规则，M 个配对）` |

### 9.2 首轮撞出来的两个真问题（比「能跑」重要）

**问题一：D-3 在这份账本上结构上不成立。**

实测：1,390 条非空 `rules_hit` 记录，**每一条的长度恒为 1**（`{1: 1390}`）。
⇒ 账本里从来没有「一条记录同时命中两条规则」的情况 ⇒ 共现矩阵为空，
「罕见组合」这个检测器**不是报 0 条，是不可判定**。

**这一条改变了报告语义**：如果把「不可判定」报成「0 条」，用户会读成「没有异常」——
而真相是「这个问法在这份数据上没有答案」。代码里已按不可判定处理（`status` 字段）。
这同时是**铁律 45 的镜像**：扫描器崩溃的表现是「没有那条记录」；
反过来，**数据里没有的东西，也不能报成 0**。

**问题二：账本的规则号没有归一化，`legacy_id` 只在规则库里有，账本里没有。**

实测：`rules_hit` 里出现过 **38 个不同的 id**，而规则库是 **37 条**。
其中 **28 个是旧号**（`CTX-01`、`DST-01`、`SEC-01`、`NET-03`、`GOV-01`、`SLOP-01`…），
不在当前 `AN-NNN` 规则库里。

⇒ **按 id 做的任何统计（巡检、报告层、覆盖率）都会把同一条规则拆成两条。**
这是**分母问题，不是检测结果**，所以代码里把它做成报告头部的「口径警告」，
不做成一条线索（线索是「变了」，这个是「尺子不对」）。

**与 A 线的关系**：A 线本批修的是 `custom.json` 里**旧号覆盖失效**（写入侧）；
C 线撞到的是**账本里旧号未归一**（读取侧）。**同一个根因的两个面**，
A 线的修法（`by_legacy` 索引）不解决 C 线这一面——账本已经写下的历史记录不会因为改代码而变号。

**这一条留给合入轮**：要么在读取层做 `legacy_id → id` 归一（加一张映射表），
要么在报告里永远带「id 为混合口径」的定语。**不能装作没看见。**

### 9.4 对账 Agent 撞出来的三个设计决定（都不是写代码前能想到的）

**决定一：hash 必须带 prev 才能重算。**

首版只拿 `canon(rec)` 去算 sha256，**2000 条里只有 1 条对得上**。
真实算法是 `sha256(prev_full + canon(rec))`，其中 `prev_full` 是**完整 64 位**上一条 hash，
不是记录里存的那个后 16 位（`audit_chain.py:450 chain_with`）。
⇒ 任何外部复算工具都必须先拿到这一条，否则永远验不对。

**决定二：对账必须单次快照，不能每个维度各读一遍。**

首版五个维度各读一遍文件，结果 **A1 报了 162,120 条、A2 报了 162,116 条**——
差 4 条。因为账本**正在被写**，两次读到的是不同时刻的账本。
⇒ 改成 `load_ledger()` 一次读入、全部维度共用（`Snapshot`）。**否则每个数都不可比。**

**决定三：不是所有「不符」都是「不自洽」，四档不是两档。**

| 档 | 含义 | 实例 |
|---|---|---|
| PASS | 通过 | A1／A2 |
| **WARN** | 性质偏离，不是篡改 | **A4 时间单调 936 处**——ts 创建时打、追加时排队 ⇒ 事件时间与链上顺序本来不同序。**★ 原写「全是 `host_shield_heartbeat`」已证伪**：实际 `pre_tool_use` 300／`dst02_bash_path_suspect` 82／`post_tool_use` 48／heartbeat 仅 10（见 §9.7） |
| FAIL | 篡改证据 | A1／A2／A3／A5 |
| SKIP | 不适用（**没有的东西不能报成失败**） | 外部账本没有 `day_manifest.json` |

**如果把 A4 判成 FAIL，工具第一次跑就报红，用户就不看了——狼来了比不报更糟。**
同理，A3 必须跳过当日文件（正在写，size 必然对不上），那是量具错不是账本错。

**对外口径（不能省）**：结论只能写「内部自洽」，后面必须紧跟一句
「**不说明它没有被整链重写**——整链重写后重算全部 hash 与清单，本工具仍会报内部自洽」。
这就是铁律 42 的 L0／L2 之分，少一句就是过度承诺。

**撞出来的缺陷：`first_seen` 只把前 6 个名字写进 subject，其余压成「等 N 个」——而那个 N 里就藏着新东西。**

注入的 `zzz_probe_nc` 排在最后，首轮直接判 NG。这不是检测器错，是**渲染错**：
用户看到「等 9 个」，却没有任何途径看到第 7 个是什么——**「等 N 个」是死路**。
修法：`Clue` 加 `items` 字段（全量名字），subject 仍截断（注意力预算），
但截断掉的必须能取回；`--json` 输出 `items`，文本改成「其余 N 个见明细」。
⇒ **负控的价值不在于证明「它能响」，而在于证明「它响的时候说的是那件事」。**

**另一条纪律：交叉污染要报，不能藏。** 一处篡改往往同时惊动多个检测器
（删记录既挖洞也降量）。首版把「干净臂本来就有的 kind」也写成「被惊动的」，
等于虚报响应面。改成**只报相对干净臂计数变化的 kind**——本次四条篡改臂全部无交叉污染。

**还剩一条没做的负控**：`rare_pair`（罕见组合）在这份账本上**不可判定**——
1390 条非空 `rules_hit` 长度恒为 1，凑不出「两条规则同时命中」。
按铁律 31，这种情况必须写「**已记录，未判定**」，不许写成「已通过」。

### 9.6 深挖「主动性」撞出的两处改动（同日深夜，负控 8/8）

**改动一：基线改「同期口径」（这是 bug，也是设计）。**

把当日账本截到 09:00 模拟「早上九点送达」，旧检测器报
「今天 640 条，前 8 天中位数 1940.5，偏离 0.3 倍」——**纯误报**：不是今天少了，是今天没过完。
根因是拿「今天到此刻」比「前 8 天全天」，两个分母（F40 同族）。

修法：前 8 天也截到同一钟点（`cutoff` = 今天最后一条记录的钟点）再算中位数与 MAD。
修后同一场景 0 条；真实账本 0 条；负控「当日 10 倍量」仍报 49.7×MAD。
⇒ **修的是假红，没把真红一起压掉。**

> **送达时机决定基线口径，这两件事是一件事。** 报告越早送越必须同期比；
> 午夜送达才可以用全天口径。这条约束以前没人写过，是因为以前没想过「什么时候送」。

**改动二：新增 `detect_absent`（预期缺席）。**

问题不是「今天比平常少」，是「**这个东西昨天还在，今天一条都没有**」。
按 `type` 分组，过去 7 天里 ≥5 天出现且中位数 ≥3 的键，今天为 0 ⇒ 一条线索。

**为什么它排在 `first_seen` 前面**：新东西出现多半是用户在正常干活（信息），
**旧东西消失多半是产品自己坏了（警报）**。巡检工具最尴尬的失败不是「报了没用的」，
是「**它自己坏了，却什么都没说**」。

**缺席的回指怎么给**：没有记录就没有行号。指向**文件末尾**（`(day, 当日总行数)`）——
「我读到了这里，零条」。假装能指到某一行是造假。

**排序随之改写**：`absent 0 / baseline 1 / first_seen 2 / gap 3 / rare_pair 4`。
`gap` 从第 3 降到第 4，因为断层分不清「你去吃饭了」和「钩子断了」——
**同一现象已经有更准的问句（absent）**，更钝的问句不该排在前面。

**负控扩到 8 臂**（`nc4` 两条臂新增）：

| 臂 | 改动 | 断言 | 结果 |
|---|---|---|---|
| `nc4_clean` | 不动 | `absent` 必须 0 条 | [OK] 0 |
| `nc4_tampered` | 删当日全部 `post_tool_use` 共 2,279 行 | 必须报 `post_tool_use` 缺席 | [OK] 前 7 天 7/7 天出现，中位数 1,600 条 |

### 9.7 A4 定性复查：**数错了一倍，归因也写错了类型**（2026-10-31 深夜）

**错误一：936 里有 455 处是字符串比较造出来的假倒序。**

`check_monotonic` 用 `ts < last` 做**字符串**比较，而账本混装两种 ts 格式：
**162,182 条带 `+08:00`、916 条不带**。逐对拆解后：

| 口径 | 倒序处数 |
|---|---|
| 字符串比较（现行代码） | **936** |
| datetime 解析后比较 | **481** |
| 字符串误报中「至少一侧无时区」 | **455** |
| 字符串误报中「两侧同格式」 | **0** |

⇒ 差额 455 全部来自格式混装，同格式对的误报为 0。**根因确定，不是估计。**

**错误二：原写「934 处全是 `host_shield_heartbeat` 并发写」——已证伪。**

实际按 `type` 分布：`pre_tool_use` **300**／`dst02_bash_path_suspect` **82**／
`post_tool_use` **48**／`pre_tool_use_summary` 13／`usage_delta` 12／
`host_shield_heartbeat` **仅 10**。heartbeat 占不到 2%。

**但结论（并发排队，不是篡改）成立，而且这次有证据了。**

`lock_events.jsonl`（5,779 行，一直被 `iter_records` 排除、从未被读过）里：

| 证据 | 数值 |
|---|---|
| `acq_timeout` 事件 | **5,461** 次 |
| 等待时长 | 中位 **1,601 ms**，最大 **9,068 ms** |
| 同一文件同一秒内 ≥2 个 pid 抢锁 | **361** 次 |
| ts 倒序幅度 | 中位 **1.0 s**，90 分位 **2.0 s**，最大 18 s |

**锁等待中位 1.6 s ≈ 倒序幅度中位 1.0 s，同量级** ⇒ 「ts 在创建时打、追加时排队」
这个机制被独立证据支持。**这是把推断变成证据，不是把证据再推断一遍。**

**⇒ 排除出分母 ≠ 从此不读它。** `lock_events.jsonl` 字段与日文件完全不同，
排除出统计是对的；但它是 A4 定性的**唯一证据源**，排除之后从没人回头读过，
于是这个 WARN 的归因一直是推断。

**修法（待做）**：`check_monotonic` 改成 datetime 归一后比较；WARN 文案改成
「按 type 分布 top3 + 锁等待证据」，不再写含糊的「属并发写的性质」。

按「机制层」而不是「把功能加上」来做。每条都过四件套：**正判据／反向对照／连带对照／自报活跃**。

| # | 事 | 机制落点 | 反向对照 |
|---|---|---|---|
| 1 | A4 改 datetime 比较 | `tsnorm.py` 唯一实现，`auditor` 与 `watchman` 都 import | 同格式真倒序仍红（120→121）；非倒序改动不触发（120→120） |
| 2 | 规则 id 归一 | `_rules_of` 是唯一读取点，映射表从 `rules/default.json` 的 `legacy_id` 生成 | 注入未出现过的旧号：原样 id 35→36、涉及规则仍 24；注入未知号：浮现为非规则号且不进分母 |
| 3 | `repeat`（第二次才算数） | 与 `first_seen` 共用 `_item_stats` 一处统计 | 1 次不报 repeat（仍归 first_seen）；3 次报 repeat 且**从 first_seen 剔除** |
| 4 | `rare_pair` 换形态 | 旧实现整段删除；`rule_pair_index` 供检测器与负控共用 | A→B 1 分钟内报；A→A 不报；A→B 隔 30 分钟不报 |
| 5 | 盲区自述 | `COVERAGE_KEYS` ＋ `_coverage_selfcheck`，漏一个就抛 | 故意漏 `gap` ⇒ 必须抛（实测抛出） |

**九维对应**（挑真正咬到的说，不逐条凑）：

- **入口唯一性**：ts 解析、规则 id 读取、item 统计、配对索引，各自只有一处实现。
  负控也复用同一实现（`rule_pair_index`）——负控自己再写一遍配对，检测器改窗口时它会静默失配，于是「通过」变成没有意义的绿灯。
- **反向对照**：19 臂里 8 臂是纯反向（干净副本必须不响、旧词不许报、A→A 不报、超窗不报、非倒序不触发）。
- **保护自报活跃**：盲区自述不是手写文案，是 `coverage` 字典；漏报即抛。
- **数据版本迁移**：0.63.0 的规则改名在**读取层**归一；ts 的两种格式在 `tsnorm` 归一，规则写死并公开（无时区按 UTC+8）。
- **文档与代码同锚**：本文所有数字由 `--json` 输出直接摘录，不手算。

**三处「差一点就写错」的实测教训**：

1. **把「不适用」算成「坏」**。`format_census` 首版把 33 条 `session_dna`（本来就没有 `ts` 字段）记进 `(坏)`，
   于是「混装 917 条」变成「混装 950 条」。改成三档：`(无ts字段)`／`(坏)`／`(无)`。
   **没有的东西不能报成失败**，这一条在统计层同样成立。
2. **门槛选错，检测器就变成噪声源**。`rare_pair` 换形态后只设下界（各自 ≥3 次），
   10-30 一天报 **30 条**——因为 `AN-014` 单独命中 406 次，它跟谁在 5 分钟内凑一起都不稀奇。
   加上界（当天 >3 次算**新常态**，归 `baseline`）后降到 24 条（3 天窗口）。
3. **负控样本选错会造出假 NG**。`nc6` 首版固定注入 `SEC-01`，而它本就在那 9 个日文件里，
   「原样 id 数」当然不变 ⇒ 断言必然失败。改成运行时挑「副本里还没出现过、且目标规则已命中」的旧号。
   **负控自己也会错，所以它必须打印它到底改了什么。**

**口径提醒**：负控副本只取最近 **9 个日文件**（8 天前置 + 目标日），
所以 `nc5_clean` 的 A4 基线是 **120 处**，不是全账本的 482 处。两个数不同源，不许混用。
