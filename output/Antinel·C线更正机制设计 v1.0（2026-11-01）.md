# C 线更正机制设计 v1.0（2026-11-01）

> 出处：方案书 §5.5「闭环三件套与更正机制（**全空，批 2 的硬阻塞**）」。
> 原文一句话：**「记录错了比没记更危险，因为它看起来像证据。」**
> 本文只设计「更正」，不设计「闭环三件套」（通知单→回复单→复查记录）——
> 后者缺的是**交互面**（产品今天没有「回复」这个动作），不是设计。

---

## 0 一句话结论

**报告一旦发出就不许改。更正只能追加，不能覆盖；被更正的条目必须自己说出「我被取代了」。**

这与账本的链式追加是**同一条原则**，不是两套规矩。理由见 §2。

---

## 1 要解决的是什么（三个真实场景）

| # | 场景 | 今天的后果 |
|---|---|---|
| 1 | 报告说「10-05 历史缺锚」，后来查明那天机制还不存在（B 线 `acd9d6e` 实测） | 结论错了一格（说成「漏了」）。**旧报告还在流通，没人知道它被推翻过** |
| 2 | 某条证据的 `(day, lineno)` 因账本滚动删除而失效 | 回指断了，但报告看着仍然完整 |
| 3 | 整份报告基于错误的读数（如把字节数当记录数，B 线 `BD-5`） | 整份作废，但没有「作废」这个动作 |

三个场景的共同点：**错的不是「没记录」，是「记了，且看起来是对的」。**

---

## 2 为什么不能「改掉它」——三条理由

**① 改了就失去「曾经这么说过」这个事实。**
监理的价值有一半在「当时我判断的是什么」。事后抹掉，等于把一个判断从历史里删掉——
那和从没做过判断，在证据上无法区分。

**② 改旧报告 = 让第三方无法复核。**
如果 A 昨天拿到一份报告，今天同一份文件内容变了，他手里的副本和源不一致，
**而两边都自称是真的**。这比错更糟：错还能被指出，改过的错会让人怀疑全部记录。

**③ 与账本同构。**
账本是 append-only（`prev`/`hash` 链），我们对账本不许「改一条记录」。
报告是我们自己的账，**凭什么可以改**。

> 一句话：**我们监别人的账不许改，自己的账就更不许改。**

## 3 数据结构

### 3.1 报告标识 `report_id`

一份报告要有稳定标识，才能被引用。建议：

```
report_id = "R-" + sha256(读数时刻 + 账本末条 hash + 证据 id 集合)[:12]
```

三个成分各有用：
- **读数时刻**：区分同一天的两份报告
- **账本末条 hash**：区分「账本没变但重跑」与「账本变了」
- **证据 id 集合**：区分「同一账本、不同检测器版本」

★ **不取文件内容的 hash**：内容里含渲染时间戳，会导致「同一份报告每次算出的 id 都不同」。

### 3.2 更正记录 `corrections.jsonl`

append-only，与账本同目录，**一行一条**：

```json
{"at":"2026-11-01T03:10:00+08:00","by":"C-3","kind":"supersede",
 "target_report":"R-a1b2c3d4e5f6","target_eid":"AUD-9f3c1a77",
 "reason":"该日机制当时不存在（B线 acd9d6e），不是漏了",
 "new_report":"R-112233445566","new_eid":"AUD-7c2b8e01"}
```

| 字段 | 含义 | 缺了会怎样 |
|---|---|---|
| `kind` | `supersede`（一条被取代）／`void`（整份作废）／`note`（补充说明不改结论） | 无法区分「更正」与「补充」 |
| `target_report` | 被更正的那份 | 找不到该改哪份 |
| `target_eid` | 被更正的那条（`void` 时为空） | 只能整份作废，无法精确到条 |
| `reason` | **人话理由** | 更正没有理由 = 又一次不可核的断言 |
| `new_report` / `new_eid` | 取代它的新条目（`void` 时为新报告） | 读者不知道该去看哪份 |
| `at` / `by` | 何时、谁 | 责任无法认定 |

### 3.3 三条硬约束（代码里 assert）

1. **`corrections.jsonl` 只许追加**：任何一次写入前先算文件 hash，与上次记录比对；不一致 ⇒ 拒绝写并报「更正记录被动过」。
2. **`target_eid` 必须在那份报告里真实存在**：拿不到 ⇒ 拒绝（不许更正一个不存在的条目——那会造出一条幽灵更正）。
3. **一条证据只许被取代一次**：第二次 `supersede` 指向同一个 `target_eid` ⇒ 拒绝，要求先撤销前一条（用 `note` 记录撤销理由）。

## 4 渲染规则（这是设计的重点，不是数据结构）

### 4.1 被更正的条目**仍然显示**，但换一种长相

| 状态 | 视觉 | 文字 |
|---|---|---|
| 正常 | 原样 | — |
| 已被取代 | 整条加**删除线**＋左侧灰边 | 前置一行：`此条已被 2026-11-01 的报告取代：<理由>（点开看新结论）` |
| 整份作废 | 页首一条**通栏横幅**，中性色（不是红色） | `本报告已于 2026-11-01 作废，原因：<理由>。请以 <新报告> 为准` |

**为什么作废用中性色不用红色**：作废不等于「出事了」，它是「这一版不再有效」。
红色会让读者以为发现了安全问题，而实际可能只是口径修正。
**颜色的含义必须稳定**，否则同一个红在两种意思之间摇摆，读者就都不信了。

### 4.2 三条渲染红线

1. **被更正的条目不许隐藏、不许折叠、不许移出原位置。**
   藏起来等于「事后没人知道这里错过」——那正是 §5.5 说的「看起来像证据」。
2. **作废横幅必须在首屏可见**，不许放在页脚。
   第三方拿到一份作废报告而没看到横幅，等于被误导。
3. **新报告必须反向指认旧报告**（`supersedes: [R-a1b2...]`）。
   只单向（旧→新）会让读者在旧报告里找不到新报告（若旧报告已归档），双向才闭合。

## 5 与「闭环三件套」的边界

方案书 §5.5 要的是三件套：**监理通知单 → 施工单位回复单 → 监理复查记录**。

| 件 | 本设计管不管 | 理由 |
|---|:-:|---|
| 通知单 | ✅ 就是报告本身 | 已有 |
| **回复单** | ❌ **不管** | 产品今天没有「对方回复」这个交互面。造一个没人回的通知单，比不做更糟 |
| 复查记录 | ⚠️ **部分** | `corrections.jsonl` 的 `note` 可以记复查结论，但没有「到期未复查」的提醒机制 |

**明确说清：本设计只补了「更正」，没补「闭环」。** 这两件事经常被混为一谈，
混起来的后果是：以为补了更正就等于闭环了，而实际上「通知了但没人理」这个状态仍然无处记录。

## 6 验收口径（没有验收口径的包不许开工）

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | 被更正的条目**仍然出现在渲染产物里** | 构造一份含 `supersede` 的报告 ⇒ 产物里必须有该 `eid` |
| 2 | 作废横幅**在首屏**（正文第一屏内，不在页脚之后） | 断言横幅在 HTML 中出现在 `<footer>` 之前 |
| 3 | `corrections.jsonl` 被外部改动 ⇒ **拒绝写入并报错** | 改一个字节后尝试追加 ⇒ 必须抛 |
| 4 | `target_eid` 不存在 ⇒ **拒绝** | 指向 `AUD-zzzz` ⇒ 必须抛 |
| 5 | 同一条被取代两次 ⇒ **拒绝** | 连写两条 `supersede` ⇒ 第二条必须抛 |
| 6 | 新报告能反向指认旧报告 | 断言新报告的 `supersedes` 含旧 `report_id` |

**六条全部要有负控**（每条一个「该红」的样本）。没有负控的验收口径等于没有。

---

## 7 本设计**不能**证明什么

1. **不能防「故意更正」**：有人可以把真结论「更正」成假的。锚只在账本层，
   报告层没有外部锚。⇒ 措辞里不许说「不可篡改」，只能说「改过会留痕」。
2. **不能覆盖「整份报告被悄悄替换」**：与账本同一个盲区——替换文件并同步改
   `corrections.jsonl`，本机制看不出来。
3. **不解决「谁有权更正」**：`by` 字段是自述，没有身份验证。
   ⇒ 单机场景下它只是「写下来」，不是「证明了」。

---

## 8 一句话

**更正的诚实程度，决定报告能不能被当作证据：**
**能改的账不是账，是笔记；改过不说改了，是伪证。**
