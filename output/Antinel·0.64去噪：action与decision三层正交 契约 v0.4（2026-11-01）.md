# 0.64 去噪：`action` / `decision` / `notify` 三层正交（契约 v0.4 · S1–S4 收束）

> 2026-11-01 03:30。v0.3 定稿的是「怎么做」；v0.4 记录的是**做完之后实测推翻了什么**。
> 一句话：**v0.3 §3 末段对那 944 条的解释大部分是错的**——实测 959 条里 920 条是
> 通知预算的账务流水（不该吵），只有 39 条真事件（该吵）。因此 S4 的「写点收敛」
> 不该做——做了会改错语义。本稿把这个更正、已完成项与剩余项钉死。

---

## 1 一页更正

| 项 | v0.3 的说法 | 实测（2026-11-01 03:27:49，172,129 条 / 35 个日文件） |
|---|---|---|
| `allow`+`alert` 并存 | 944 条，"说明它们**本该吵**"，收敛后自动归位 toast | 959 条，其中 **920 条是通知预算的账务流水**（920/959 = 95.9%），结构上**不该吵**；只有 39 条是真事件（39/959 = 4.1%） |
| 修法 | 收敛 `decision` 为 `action` 的纯函数 ⇒ 这 959 条自动归位 | **不收敛**：read 侧 `decision_of()` 已经把它们逐条判对（见 §3） |
| 非裁决白名单 | 只 `usage_delta` / `session_dna` | 实测加了 3 类（`pre_tool_use_summary` / `notice_budget_window_closed` / `notice_budget_merged`），理由见 §2 |

## 2 959 条到底是什么（逐类）

| type | 条数 | 它是什么 | 该吵吗 |
|---|---|---|---|
| `notice_budget_window_closed` | 768 | 通知预算的**窗口结算**：reason 写着"本窗口 5 条提醒，出声 0 条" | **不该**——让它出声＝"说自己没出声的同时自己出声" |
| `notice_budget_merged` | 152 | 同上，合并记账 | **不该** |
| `hook_slow` | 38 | 钩子跑超预算（最坏 42,923 ms）。超时被宿主当 ALLOW ⇒ 裁决可能根本没送达 | **该**——这是"牌没打出去且无人知晓" |
| `hook_error` | 1 | 钩子中途崩 | **该** |

⇒ 账务 768+152 = **920**（959 里的 95.9%）；真事件 38+1 = **39**（959 里的 4.1%）。
v0.3 把这两类混成一句"它们本该吵"，是把**记账流水**与**需要人处理的事**当成了同一种东西。

**因此白名单必须是 5 类而不是 v0.3 写的 2 类**：多出的三类（`pre_tool_use_summary`
1,163 条按调用聚合、两个 `notice_budget_*`）各有独立理由，逐条写在
`hooks/notify_policy.py` 的 `NON_EVENT_TYPES` 注释里。**未列入 ≠ 放行**：其余 29 类
一律走回退表，未知 type 默认 toast（偏吵）。

## 3 为什么 S4 的「写点收敛」不做（这是本稿最要紧的一条）

v0.3 §5.2 把"把 70 处写入点的 `decision` 收敛成 `decision_of()`"当作 0.64 主体。
实测后这个动作**收益为零、风险为实**：

1. **收益为零**：收敛的目的是让矛盾对归位。而 read 侧 `notify_of()` 内部调的正是
   `decision_of(action, severity, current)`——**账本里的矛盾对在读的时候已经被判对了**
   （`alert`+`allow` ⇒ 取严 ⇒ alert ⇒ toast）。写侧再收敛一遍，读出来的结果一模一样。
   **一个不改变任何读数的改动，没有任何可验收的口径。**
2. **风险是实**：`_SEVERITY_ESCALATE` 会把 `critical/warning` + `allow` 升级成 alert
   （账本 333 条）。若写侧一律收敛，这些记录在新账本里会变成 `decision=alert` 而
   `action=allow` —— 把今天"两字段独立赋值"的可见矛盾，换成"看起来自洽、实际被升级过"
   的**不可见改动**。**证据不可篡改**这条不变式要求的恰恰是"矛盾留在原地，读法逐条解释"。
3. **§7.2 早写了不改历史**：历史不能重写，那么唯一能改的就是"未来的写法"。而未来
   写法改不改，读者都读不出差别 ⇒ 这笔改动只能靠 code review 断言"更干净"，
   这在本项目是**不被接受的验收方式**（判据不许用"我觉得"）。

**结论**：`decision` 保持为写入字段，`decision_of()` 作为**读侧唯一派生实现**并在
`notify_of()` 里被逐条调用；账本不动。**S4 的验收口径改为读侧**：

| 验收项 | 读数 | 出处 |
|---|---|---|
| 959 条 `alert`+`allow` 逐条落档 | gate 0 / toast 39 / none 920（全账本） | `output/lineA/s1_notify_distribution.py --audit-dir .psl/audit` 的「矛盾组合归位核对」 |
| 三档之和 == 记录数 | 45,288 = 45,288（7 天窗口） | `python -m scripts.report --days 7` 那一行 |
| 拿不到唯一实现时不与"全 0"同貌 | `stats["notify"] = null` ＋ 报告印 `not computable` | `output/lineA/test_report_notify.py` 负控腿 |
