## 1 为什么这件事不能靠"加个字段"解决

方案书原话：**「没有回复和复查，通知单就只是抱怨。」**
以及：**「记录错了比没记更危险，因为它看起来像证据。」**

这两句合起来给出两条硬要求，而不是一条：

| 要求 | 含义 | 不满足时的后果 |
|---|---|---|
| **闭环** | 通知单必须有对手方回执与己方复查，否则状态不成立 | 报告里写"已发现 N 项"，N 项永远悬空 ⇒ 与"已拦截"混为一谈 |
| **可更正** | 记录不可原地改，只能用**新记录取代**旧记录，且取代关系本身留痕 | 改一下字段就"没有了" ⇒ 证据链断在没人看得见的地方 |

## 2 三件文书：字段表

三件共用一套外壳，差异只在"谁填、填什么"。**所有 `*_refs` 一律指向审计记录 id，不许填自由文本。**

### 2.1 外壳（三件共有）

| 字段 | 类型 | 谁填 | 何时填 | 约束 |
|---|---|---|---|---|
| `doc_id` | str | 系统 | 生成时 | 全局唯一；不得复用已取代的 id |
| `kind` | enum | 系统 | 生成时 | `notice` / `reply` / `review` |
| `case_id` | str | 系统 | 生成时 | 一次"发现"= 一个 case，三件文书同 case 串联 |
| `supersedes` | str \| null | 系统 | 更正时 | 指向被取代的 `doc_id`；**非更正一律 null** |
| `state` | enum | 状态机 | 每次转移 | 见 §3；**与 `Item.state` 分离**（理由见 §4） |
| `evidence_refs` | list[str] | 填表人 | 填表时 | 必须每条都能在账本里取到；**取不到即拒收** |
| `at` | iso8601 | 系统 | 生成时 | 用 UTC，展示时本地化 |

### 2.2 `notice`（监理通知单）

| 字段 | 说明 | 来源约束 |
|---|---|---|
| `finding` | 看见了什么 | 必须能回指 `evidence_refs` 里的一条，**不许写"疑似""可能存在"** |
| `severity` | 后果等级 | 复用 `none` / `some` / `unknown`（与现有四轴同值，不新造第二套） |
| `demand` | 要求对方做什么 | 一句一动作，可判定是否完成 |
| `due_at` | 回复期限 | 必填；无期限即视为未发出 |
| `consulted_at` | 何时向谁听取意见（§5.6 第四项） | **现在 96 个字段里没有位置**，此处必须预留，否则补它要动 schema |

### 2.3 `reply`（回复单）

| 字段 | 说明 | 约束 |
|---|---|---|
| `for_notice` | 回的是哪张通知单 | 必须是 `state=issued` 的 `notice` |
| `claim` | 声称做了什么 | 允许"不整改＋理由"，但**必须给理由** |
| `evidence_refs` | 支持该声明的证据 | 空列表合法（＝"我只是声明"），但要在报告里如实标"未提供证据" |

### 2.4 `review`（复查记录）

| 字段 | 说明 | 约束 |
|---|---|---|
| `for_reply` | 复查的是哪张回复单 | 必须存在对应 `reply` |
| `verdict` | `confirmed`（问题消失）／`not_confirmed`（仍在） | **`not_confirmed` 必须重新开一张 `notice`**，不许把 case 直接关掉 |
| `observed_refs` | 复查当时看到的证据 | 与 `reply.evidence_refs` 分开存 —— 两者的差异本身就是结论 |

## 3 状态机

```
                        ┌──────────── 超期且无 reply ────────────┐
                        ↓                                       │
 draft ──issue──> issued ──reply──> replied ──review──> reviewed ─┴─> closed
                        │                    │            │
                        │                    │            └─ not_confirmed ─> reopened ─┐
                        └── withdraw ─> withdrawn            （必须新开 notice）        │
                                                                  ↑__________________│
```

| 转移 | 触发 | 守卫（不满足则拒绝） | 写哪条审计记录 |
|---|---|---|---|
| draft→issued | 发出 | `evidence_refs` 非空且全部可取；`due_at` 非空 | `notice_issued` |
| issued→replied | 收到回复 | `for_notice` 对得上且未被取代 | `reply_received` |
| replied→reviewed | 己方复查 | `observed_refs` 非空 | `review_recorded` |
| reviewed→closed | 结案 | `verdict=confirmed` | `case_closed` |
| reviewed→reopened | 未消失 | 同时生成新 `notice`，`supersedes` 指向原单 | `case_reopened` |
| issued→overdue | 超 `due_at` | 仅标记，**不改变 case 统计** | `notice_overdue` |
| *→withdrawn | 撤回 | **必须写理由**，且理由进报告 | `notice_withdrawn` |

**超期是标记，不是结案。** 这一条是整张表的重点：把"没人回"当成"已处置"，
正是方案书 §5.3 禁的那句互换（"已记录未判定"写成"已拦截"）。

## 4 一个必须现在就说清的复用陷阱

仓里已有 `Item.state`，而它**兼职两件事**：知情状态 ＋ 生命周期。
记忆里的实测结论：**用户点一次「忽略」会把未修复的缺口从统计里删掉**。

⇒ 文书状态**绝对不许复用 `Item.state`**。理由：

| 若复用 | 会发生什么 |
|---|---|
| 通知单用 `Item.state` 表示"已发出" | 用户点「忽略」→ 通知单从统计消失 → 报告里"已发现 N 项"变成 N−k，而 k 项其实还在 |
| 复查用 `Item.state` 表示"已关闭" | "关闭"与"被忽略"在同一个枚举里 ⇒ 无法区分"修好了"与"不想看了" |

⇒ **`case` 状态自成一个枚举**（§3 那 8 个），与 `Item.state` 只在**投影**处相遇：
报告显示时用 `case.state`，用户视图的"忽略"只影响 `Item.state`，两者不互相写。

## 5 更正机制（比闭环更容易做错的一半）

**唯一实现一句话：记录只增不改，更正是"新记录 ＋ `supersedes` 指针"，旧记录永不删除、永不编辑。**

| 场景 | 正确动作 | 禁止动作 |
|---|---|---|
| 通知单里 severity 填错了 | 新开一张 `notice`，`supersedes` 指旧单；旧单标 `state=superseded` | 原地改 severity |
| 复查结论被推翻（后来发现确实修好了） | 新 `review` + `supersedes`，并在报告里**同时**呈现两次结论及差异 | 删掉前一条 review |
| 发现某条 `evidence_refs` 指向的记录本身是误报 | 对那条**审计记录**走它自己的更正通道（追加更正记录），文书侧只改指针 | 改文书让它指向别的记录而不留痕 |

三条自检（写完必须能回答）：

1. 任意一条 `doc` 能否顺着 `supersedes` 链找到**最初那一版**？（能 ⇒ 链没断）
2. 报告里每个"已发现／已拦截／已记录"能否回指到一条具体审计记录？（不能 ⇒ 不许写，§5.7）
3. 一条被更正的记录，在**证据包**（第二种读者）里是"消失了"还是"两次都看得见"？（必须是后者）

## 7 与批 2 的关系（为什么它是硬阻塞）

批 2 要交付的是**给第二种读者（客户的管理者）的证据包**。证据包的每一段都由这三件文书拼成；
三件不存在 ⇒ 证据包只能是"一份更长的报告"，而报告不能自证。
