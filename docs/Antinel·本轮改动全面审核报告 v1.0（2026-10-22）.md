## 1. P0 —— 必须先修

### A1 「点开即已读」把已处置/已忽略的记录改回「未修」

**位置**：`inbox_server.py:639-664`（`_READ_JS`）、`inbox_server.py:4216`（`set_state(iid, op)` 无门禁）、
`inbox_store.set_state()` 的 `else: ent["gap_state"] = M.GAP_OPEN` 分支、`inbox_server.py:1832`（`_item_html`）。

**实测**（`output/_p_gap_ui.py`）：

```
A 忽略后        : ('ignored', 'acked', True)      ← closed_at 是"你说先不管的时刻"
A 点开即已读后  : ('read',    'open',  False)     ← ack 撤销、复核计时清零
B 处置后        : ('done',    'closed', True)
B 点开即已读后  : ('read',    'open',  False)     ← 已修好的缺口变回"未修"
```

**为什么它在真实使用中会发生**（[读码] 逐条核实）：

1. `_item_html` 给**每一条**记录（含已处置、已忽略）都发 `data-id`／`data-token`；
2. 整个仓库**没有任何地方输出 `data-readed`**（`grep -rn "readed"` 只有 JS 自己写），
   所以 JS 的早退守卫 `if (d.dataset.readed === '1') return;` 在**每次打开页面时都不成立**；
3. 于是「展开任意一条 `.item`」⇒ 发 `op=read` ⇒ `set_state(..., "read")`；
4. 服务端只校验「迁移合法」（`ignored→read`、`done→read` 都合法，注释写着"重开"），
   **不区分这是自动已读还是用户主动重开**。

**后果**：`unrepaired_count()` 的 `n` 会把"其实已经修好、只是被展开看过"的条数算进去；
反过来，"你说过先不管"的决定被一次浏览抹掉，且 `closed_at` 被 `pop` ⇒ **复核期永远重新计时**。
这正是 40 格「人·判」这一格要消灭的病，只是换了个入口回来。

**判据为什么没抓到**：`P28`／`P29` 都直接调 `M.gap_state_of` / `S.set_state` 的**模型参数**，
不打 UI 路径 —— 假绿族④「判据走注入参数、生产走默认参数」的原样复现。

**修法（建议 a＋b 同时做，改动 ≤ 10 行）**：
- **a**：`_item_html` 对 `it.state != "unread"` 输出 `data-readed="1"`
  （这样"点开即已读"只对未读生效，与它本来的语义一致）；
- **b**：`/action` 的 `op=="read"` 分支加门禁——只有「当前 `unread`」或「显式带 `X-Antinel-Reopen: 1`」才允许走
  （显式重开由页面「重开」按钮发出），自动已读其余一律忽略。
- 另：`set_state` 的 `else` 分支建议区分 `read`（来自 auto）与 `reopen`（显式）——若不做 b，至少不许 pop `closed_at`。

**要补的判据**：P34「点开即已读不得改变缺口态」——正控：模拟 `_READ_JS` 的请求打到 `ignored` 项，
断言 `gap_state` 仍 `acked`、`closed_at` 未清；负控：显式重开时**必须**变 `open`。

### A2 heredoc 正文「管道给解释器」时仍被剥掉 ⇒ 危险内容漏扫

**位置**：`hooks/pre_tool_use.py` `strip_heredoc_bodies()`：
`if exec_re.search(line[:m.start()]):` —— **只看 `<<` 之前**。

**实测**（`output/_p_hook_bypass.py`）：

| 形状 | 正文是否仍在扫描面 | 实际是否被执行 |
|---|---|---|
| `cat <<'EOF' …` | 否（正确，正文是数据） | 否 |
| `bash <<'EOF' …` | 是（正确） | 是 |
| `cat <<'EOF' \| bash` | **否（错）** | **是** |
| `cat <<'EOF' \| sh` | **否（错）** | **是** |
| `tee /tmp/a <<'EOF' \| bash` | **否（错）** | **是** |
| `sudo bash <<'EOF' …` | 是（正确） | 是 |

**后果**：这是**漏放**方向——被剥掉的正文照样被管道右侧的解释器执行，但扫描面里已经没有它。
比"误挡"严重一档（误挡会被用户投诉，漏放不会有人知道）。

**修法（一处改动）**：`exec_re.search(line[:m.start()])` → `exec_re.search(line)`。
代价是少数"数据里恰好出现 `sh` 这个词"的 heredoc 不再被剥（多扫，属安全方向）。

**要补的判据**：P30 扩一条「管道给解释器不许剥」——三个形状各一例正控 ＋
「纯 `cat` 必须剥」的对照（证明不是整段不剥）。

### A3 丢失计数被静默抹掉（真值 4 报 1）

**位置**：`egress._note_lost()`。

```python
_LOST["n"] += 1                      # 先记内存
cur = _read_json("lost.json", {})    # 只读盘上那份
...
if _write_json("lost.json", {"n": n + 1, ...}):   # ← 写的只有 "盘上+1"
    _LOST["n"], _LOST["first"], _LOST["last"] = 0, None, None   # ← 内存那份直接扔了
```

**实测**（`output/_p_lost_merge.py`）：

```
磁盘满期间 · 内存 _LOST = {'n': 3, ...}      lost_pending = (3, 1000.0, ...)
恢复后再失败一条       · lost_pending = (1, 2000.0, ...)   ← 真值应为 4
盘上 lost.json = {'n': 1, 'first': 2000.0, ...}            ← 起点也从"最早"退成"最晚"
```

**根因**：读的时候用 `lost_pending()`（盘＋内存取和），写的时候却只用"盘上那份"，
写完还把内存清零 ⇒ **内存里那 3 条既没进盘也没留内存**。
这直接违反函数上方自己写的口径「**宁可多记，不许少记** —— 少记等于替一次丢失撒谎」。

**修法**：

```python
n, first, last = lost_pending()          # 盘＋内存，唯一口径
if _write_json("lost.json", {"n": n + 1, "first": first or now, "last": now}):
    _LOST["n"], _LOST["first"], _LOST["last"] = 0, None, None
```

**要补的判据**：P25 加一条「跨形态合并」——内存在涨、盘上也可写时，
`lost_pending()` 必须等于两者之和，不许变小（负控：把上面这行改回旧写法，判据必红）。

## 2. P1 —— 逻辑与盲区

### A4 `KEEP_DAYS` 边界抖动：今天那份不存在时留 15 天

**位置**：`egress.enforce_retention()`：`n_days = len(ds["days"])`（含今天的文件，如果它已存在）。

**实测**（`output/_p_keepdays.py`）：

```
今天那份存在=True  ⇒ 删后剩 14 天
今天那份存在=False ⇒ 删后剩 15 天   ← 随后 _append 会创建今天那份 ⇒ 稳态 15 天
```

**为什么这不是边角**：`run()` 的顺序是 `sample() → housekeep() → _append()`，
`tick()` 是 `housekeep() → sample() → _append()`。两者都在**当天第一次写之前**跑保留策略 ⇒
**每天早晨都会落到"今天那份不存在"这个分支**。所以"保留 14 天"实际常常是 15 天。

**修法**：按"含今天共 `KEEP_DAYS` 天"算，与今天在不在无关：

```python
while len(days) > KEEP_DAYS - 1 and days:   # days 已排除今天
```

**判据为什么没抓到**：`P24` 的夹具**恒造今天那份**并显式传 `today=`（`ci/inbox_guards_0353.py:5104-5106`）
⇒ 假绿族②「夹具合成形状」——夹具形状与真实调用形状不同。

**要补的判据**：P24 加第二形状（无今天那份），断言"删完 + 新建今天 = `KEEP_DAYS` 天"。

### A5 `lock_pressure.checked` 契约自毁，页面又把「查不到」吞成「没竞争」

**位置**：`audit_chain.lock_pressure()` 末尾 `if os.path.isdir(...): out["checked"] = True`；
`inbox_server._lock_line()` 的 `if not (pr.get("timeouts") or pr.get("steals")): return ""`。

**两处都错**：
1. docstring 明写「`checked=False` 是读不到/不存在，**后者不是"没问题"**」，
   但函数末尾只要**目录在**就 `checked=True` ⇒ 事件文件不存在（最常见情形）也被报成"查过了，0 次"。
2. 页面在 `timeouts=steals=0` 时直接不显示 —— 包括 `checked=False` 的时候 ⇒
   「没量到」和「量了没竞争」在上屏层面合流，正是本仓第 ④ 条判据
   （「没查 ≠ 没发现」）禁止的那件事，出现在**本轮新写的代码**里。

**修法**：删掉末尾那个 `isdir ⇒ checked=True`；页面在 `checked=False` 时显示
「记录连写的读数读不到（这一项不是「没问题」，是「没量到」）」——与 `capacity()` 的 `cap is None` 分支同款措辞。

**要补的判据**：`P32` 加一形状：事件文件不存在但目录在 ⇒ `checked` 必须是 `False`（负控：旧实现必红）。

### A6 `capacity.readable` 算了没人读

**位置**：`egress.render()` 只判 `if cap:` / `elif cap is None:`；`cap["readable"]` 无消费点。

**后果**：账本目录读不到时 `dir_stats()` 返回 `bytes=0, files=0, readable=False`，
于是页面显示「账本 0 个文件 0.0 MB（上限 48 MB，保留 14 天）」——
**把"没量到"说成"一个文件都没有"**。这与 `dir_stats` docstring 里
「可读性是独立字段：0 字节和"读不到"是两件事」自相矛盾。

**修法**：`render()` 加一支 `if cap and not cap.get("readable"):` 走"读不到"文案。

**要补的判据**：`P26` 加形状：`readable=False` ⇒ 渲染里**不许**出现 `0 个文件`，必须出现"读不到"。

## 3. P2 —— 口径与文案

### A7 一句话里两个不同基准的「天前」

`inbox_server._unrepaired_line()` 输出：
「你说过先不管、其实还没修好的：N 条（最早 **D 天前**）。其中 M 条已过 14 天复核期。」

- `oldest_days` 来自 `it.ts`（**这条告警发生**的时间）
- `due`／复核期来自 `closed_at`（**你点"先不管"**的时间）

两个数同句并列，读者会当成同一个基准。极端形状：一条 30 天前的告警今天才被忽略 ⇒
页面写「最早 30 天前」，但复核期才第 0 天 —— 读者会以为系统算错了。

**修法**：把基准写进句子，例如「最早一条发生在 D 天前；其中 M 条距你设为先不管已满 14 天」。

### A8 「有 N 条没能写进账本」是上界，页面按精确值说

`analyze()` ④ 把 `lost` 事件的 `n` 相加；而机制层明确允许**重复补记**
（`_flush_lost` 清零那步失败就会再补一遍，口径"宁可多记"）。
⇒ 这个 N 是**上界**，页面却说成确定条数。

**修法**：文案改为「至少 N 条」；或在 `lost` 事件里带 `dup_ok=1` 标记，读数处据此措辞。

### A9 「账本 N 个文件」把非事件文件也数进去

`dir_stats()` 的 `files` 统计目录下**所有**文件（`current.json`、`lost.json`、`disk_warn.json`、`resolve.json` 等），
而文案写「账本 N 个文件」。事件文件数与总文件数不是一回事。

**修法**：`dir_stats` 增 `event_files`；文案用事件文件数，或改成「目录 N 个文件」。

## 4. P3 —— 脆弱（暂不致命，但会在某些机器上咬人）

| 编号 | 位置 | 现象 | 建议 |
|---|---|---|---|
| A10 | `egress._read_json`、`load_events` | `json.load(open(p))` / `for line in open(p)` 不显式关闭。CPython 靠引用计数即刻回收，PyPy 或未来换解释器会积句柄；Windows 上未关句柄会让 `os.replace` 失败 | 一律 `with open(...)` |
| A10b | `egress._write_json` | 临时名固定 `p + ".tmp"`：两个进程同时写 `lost.json` 会互踩，`os.replace` 可能搬走半个文件 | 临时名带 pid：`p + ".%d.tmp" % os.getpid()` |
| A11 | `egress._disk_pressure_once` | 用 `_write_line` 直写账本，绕过 `_flush_lost`／`_note_lost` ⇒ 这条写失败既没补偿也没进 lost 计数 | 改走 `_append`（它已带三段式），或显式补记 |
| A12 | `egress.run()` vs `tick()` | `run()`：sample → housekeep；`tick()`：housekeep → sample。顺序不同使"容量观测"看到的时点不同 | 统一为 housekeep 先（与 A4 的修法配合） |
| A13 | `egress._append` | 每次写事件都 `_flush_lost` → `lost_pending()` → 读一次 `lost.json`。`tick()` 每条 new/gone 都走一次，连接多时是纯浪费 | 进程内用 `_LOST` 判空跳过读盘；或每 N 次才查盘 |

## 9. 需要你拍板的两件事

### 9.1 A1 的修法

- **方案甲（推荐）**：服务端对非未读项发 `data-readed="1"` ＋ `/action` 的 `read` 加门禁（只允许 `unread`，或显式 `X-Antinel-Reopen`）。
  改动 ≤ 10 行，不动「重开」按钮语义，**不改变任何既有交互**。
- **方案乙**：只在 `set_state` 里保护 —— `read` 不再 pop `closed_at`、不再改 `gap_state`（除显式重开）。
  改动更小，但"点开即已读"仍会改 `state`，`done`→`read` 的视觉状态还是会变。

### 9.2 版本号

本轮引入了**会删用户数据**的行为（保留策略）＋ 会改状态语义的字段（`gap_state`）＋ 命令扫描面变更。
按本仓"版本号升降严格反映变更幅度"的纪律，这应当是 **0.53.2 → 0.54.0**。
但现在 `--no-verify` 的理由正是"D-23：dist 缺 0.53.2 发布件"——
**不升版就把"删数据的行为变更"挂在旧版号下**，与 PCM 账本那行 `0.53.5` 属同一类"登记与事实分家"。
两条路都通：① 升 0.54.0 ＋ 九处承载件同步 ＋ 出包让 D-23 变绿；② 明确写"0.53.2 为开发号，不对外"。

### 9.3 是否立刻修 A1–A3

P0 三条都在我手上，修法与负控都已写清。我的建议顺序：**A3（10 行，纯口径错）→ A2（1 行，漏放）→ A1（10 行，需你选方案）**，
每修一条先补判据让它红。
