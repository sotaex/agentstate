- 现有的 27 套闸门、315 条断言、发布验收，回答的都是「**这个包对不对**」；**没有任何一条回答「用户装完能不能用、好不好用」**。
- 已有覆盖的边界要说清，避免重复劳动：
  - `scripts/verify_release.py` 的 [D] 步：`pip install --target` ＋ 导入探针 ⇒ 回答「装得上、导得进」；
  - `ci/j1_install_test.py`：干净 `venv` ＋ **从本地路径**安装 ＋ 裸调用 ＋ 早晨命令 ⇒ 回答「本仓形态可用」。
- **两者都不是「从索引下载」**，且都不覆盖：首次运行、宿主接入、升级、卸载、离线、中文路径、非 `Windows` 平台 —— 这些全是**用户旅程**。
- 上传是不可逆动作（同版本号不可覆盖，只能 `yank` 或发新版）⇒ 上传前的用户旅程闸门，是性价比最高的一道。

## 3. 模拟的边界与两条轨道

- **只测用户旅程**，不重测产品内部逻辑（后者归 27 套闸门与 315 条断言，重复做等于浪费且会互相污染结论）。
- **轨道 A（上传前，今天就能跑）**：把 `dist/` 两件当「下载物」，三种等价形态：
  1. 直接装 `wheel` 文件；
  2. `pip install --no-index --find-links dist antinel`（最接近索引语义：走元数据解析与依赖解析）；
  3. 本地 `--index-url file://` 目录当索引。
  **轨道 A 能回答绝大多数问题**，且不需要先上传。
- **轨道 B（上传后 D+0）**：真 `pip install antinel`（线上 0.48.1），同一套脚本复跑，作为最终确认。
- 一条纪律：**两轨共用同一份脚本**，避免「测的东西和发的东西不是一套」。
