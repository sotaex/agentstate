## 二、补偿第一件：`DST-08` 属设计 —— 已写进 README

判据原文（`rules/default.json` → `DST-08`，`critical` ⇒ block）：

```
chmod 000 / chmod … -R … / chown … -R …
icacls … /deny … / icacls … /t … /reset / icacls … /reset … /t / takeown … /r …
```

★ 为什么不是「按模式收窄」：正控 `ci/inbox_guards_0514.py` 里就有一条 `chmod -R 755 /var/www` 期望被拦。按模式收窄会把这条正控一起废掉 —— 那是把判据改绿，不是把问题修好。

## 三、补偿第二件：0.63.0 设计债（按「欠谁的」排序）

| # | 债 | 现在的事实 | 0.63.0 的修法 |
|---|---|---|---|
| 1 | `DST-08` 只看形态、不看位置 | 连 `chmod 000 ~/notes.txt` 这种单文件也硬拦 | 改**按位置收窄**：只拦系统目录与工作区之外的递归改权限；工作区内保留但降为 alert |
| 2 | `uninstall` / `archive` 在宿主拒绝删除时**判红** | 宿主安全垫片挡住批量删除时，卸载判据红；判据外手工复跑同场景 rc=0 | 拒绝删除属**环境事实**不是产品失败：返回 0 并写一条警告记录（与 `D-40` 四态串同范式） |
| 3 | 「未读数 / 超时」混在失败里 | 9 条失败中至少 1 条是判据内 60 秒超时，读起来与「断言为假」一样 | 失败分类新增两档：`unreadable`（读数缺失）、`timeout`；两者都不许冒充 `product` |
| 4 | 回退演练无脚本 | 七条闸门里 #5 回退演练此前估计需 1 小时手工 | 落成 30 分钟可重跑脚本（装 N-1 → 验 N → 卸 → 装 N-1 → 比审计链） |
| 5 | 每版一次的「清单 ⊆ 载荷」与「研发树专属文件必登记」互相顶牛 | 见下节；本轮靠**版本落差**同时满足，属巧合式解 | 把研发树专属文件从**随包清单**里结构性分开（例如清单加 `dev_only: true` 分区），让两条判据不再靠版本落差共存 |

### 我没有定论的一件事（写下来，不粉饰）

同一台机器，2026-10-29 16:40 记录的 `0.61.0` 那一行是 **0 失败**；2026-10-30 12:30 的 `0.62.0` 行是 **9 失败**。两种解释都还活着：

1. `0.62.0` 真的改变了卸载／归档路径 —— 安装末尾新增 `canary plant`，卸载要多清一族文件，删除通道被打得更狠；
2. 宿主当天变了 —— bulk-guard 的锁文件在 10-30 才第一次挡住删除（今天确实遇到 `state lock timeout`，把锁文件改名让开后删除探针恢复）。

判据外同一场景手工跑三遍 `rc=0`、判据内 `rc=1`，支持解释 ②；但它**证明不了「0.61.0 今天也会绿」** —— 在禁删宿主上重放 0.61.0 的完整场景我没做成。所以我只写「我没有定论」，不写「与 0.62.0 无关」。

### 我为什么不给自己签豁免单

`.psl/gate/pcm_waiver.json` 的设计里写着「**只能由人写**，闸门自己永远不写它 —— 否则『违规者给自己开路』只需要改一行判据代码」。这 9 条算不算「环境使然、不是产品缺陷」，该由创始人签字；执行者签自己的豁免单，正是那条注释要防的事。所以本条留红，直到有人签字或者 0.63.0 把它们修掉。
