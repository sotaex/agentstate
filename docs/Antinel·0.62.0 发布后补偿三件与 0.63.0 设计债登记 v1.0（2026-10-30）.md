## 三、补偿第二件：0.63.0 设计债（按「欠谁的」排序）

| # | 债 | 现在的事实 | 0.63.0 的修法 |

| 4 | 回退演练无脚本 | 七条闸门里 #5 回退演练此前估计需 1 小时手工 | 落成 30 分钟可重跑脚本（装 N-1 → 验 N → 卸 → 装 N-1 → 比审计链） |
| 5 | 每版一次的「清单 ⊆ 载荷」与「研发树专属文件必登记」互相顶牛 | 见下节；本轮靠**版本落差**同时满足，属巧合式解 | 把研发树专属文件从**随包清单**里结构性分开（例如清单加 `dev_only: true` 分区），让两条判据不再靠版本落差共存 |

### 那件「我没有定论」的事 —— 当日 14:00 结清了

上面这张表是 12:30 那次全量的原样留账，**不改写**。它的三条红里，`PCM` 与那 9 条失败的定性在当天下午有了实测结论：

| 时点 | 动作 | 结果 |
|---|---|---|
| 13:26–13:37 | 让开宿主锁文件后，第一次独立重跑判定 | `verdict=PASS assertions=325/325`，失败集为空 |
| 13:37–13:44 | 第二次独立重跑（与上一次部分重叠，故只作旁证） | 同上，`PASS 325/325`，四类计数全 0 |
| 14:00 | `--only PCM` | **闸门通过**：同版本内 9 条全部关闭、新增 0 |

**根因**：宿主批量删除看守留下 0 字节锁文件，每次删除都报 `state lock timeout`。锁让开后，**同一份代码**两次独立重跑全绿。所以原表里「解释 ②：宿主当天变了」成立，「解释 ①：0.62.0 改了删除路径导致退化」被排除。

**三个连带动作**（都是收紧，不是放松）：

1. **豁免单没签**，也不需要签了 —— `PCM-03` 靠 9 条在同版本内关闭自然转绿。执行者没有给自己开路，那张 `pcm_waiver.json` 至今不存在。
2. **9 条 `environment` 登记已从 `run_harness.py` 撤掉**。留着等于给这 9 条预开一张长期绿灯：将来真出退化也会被静默归到 `environment`。删掉它，等于把这 9 条重新暴露在「会红」之下。理由与保留知识（先查锁文件与磁盘余量）写在撤除处的注释里。
3. **仓内自证卡转 `true`**：`psl-verified-at: 2026-10-30T13:44:30+08:00`，`evidence` 里写明「两次独立重跑同结果 + 9 条为锁文件所致 + 27,162 条重放零增减 + **已发布的 0.62.0 wheel 内仍是 false，本卡描述源码树而非发布件**」。

⚠️ **由此产生的唯一不一致，写在这里而不是藏起来**：`pip install antinel==0.62.0` 装到的包里，自证卡写 `false`；仓库 `main` 写 `true`。前者是装配那一刻的如实记录，后者是四小时后的实测记录，**两个都不是假话**；想让二者一致，只能出 `0.62.1`，而那属于冻结期外的决定，不在本轮。

### 关于「为什么不自己签豁免单」

`.psl/gate/pcm_waiver.json` 的设计里写着「**只能由人写**，闸门自己永远不写它 —— 否则『违规者给自己开路』只需要改一行判据代码」。这条设计本轮被证明有用：正因为没签，才会去把「昨天绿今天红」查到底，而不是拿一张单子把它盖住；查下去才发现根因在宿主锁文件、不在产品。**留红的代价是几小时，签单的代价是把一个未知的退化永久封存。**

## 七、同日补丁 0.62.1：自证卡 `false` → `true`（零规则变更）

### 起因是一次误读，而误读本身是证据

创始人读到「`pip install` 装到的包里自证卡写 false」，第一反应是**「是不是装不上」**。实测不是（见下），但这个反应本身就是结论：**如果做这个产品的人都这么读，测试用户会读得更糟。**

### 先证伪「装不上」

★ 第一版探针把 cwd 留在仓库里 ⇒ `import antinel` 命中的是仓库代码、`-m` 跑的是仓库工具（还报 144 条＝仓库那份清单）。**把子进程 cwd 挪到空目录重测，才是安装态。** 这条错误与「读数归属」同源，写在这里当反面样例。

### 改了什么（逐条点名，没有第四条）

1. 九处版本承载件 → `0.62.1`；
2. 自证卡由构建器重写：`psl-verified: true`、`at` 取判定运行时刻 `2026-10-30T14:53:48+0800`、`evidence` 写 `digest check 21/21 digests match this build (assertions 325/325)`；
3. 判定重跑为 `0.62.1`：**PASS 325/325**，失败 0，四类计数 0。

规则条数、拦截集合、判定口径、登记表，一概未动 ⇒ 符合冻结期「拦截不增」＋补丁名额 1/3。

### 判定为什么跑了两遍

第一遍 **FAIL 323/325**，两条都是 `process-stale`：`antinel.py` 与 `rules/default.json` 换了字节，旧指纹不再覆盖新代码。第一遍跑完指纹刷新，第二遍 325/325。这不是缺陷，是「改过覆盖文件 ⇒ 第一遍必红」那条纪律在起作用；把它写成缺陷就会去改判据。
