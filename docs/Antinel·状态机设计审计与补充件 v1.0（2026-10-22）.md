### 3.1 N5（BL-14 补完）：mode 的输入契约——「装了没跑」不许落进「未启用」

**现状取证**：新模型已把两件事 Structural 分离——`unarmed`（没装，默认全关，
最优设计 §4.1）与 `armed ∧ duty=off`（装了没跑 ⇒ paused/absent，§4.2）。但
**「凭什么判 mode」没有落成字段**：施工件 §1.5 自认缺件 A（事实字段表），
而 mode 恰好在三轴之外，两份设计件都没写它的输入。

**设计**：mode 的权威源是**链**，不是状态文件。

| mode | 判定（唯一实现 `facts.mode()`） | 用户要不要做事 |
|---|---|---|
| `unarmed` | 全链无 `host_shield_changed{field:"enabled", change 含 → true}` 记录 | **不用**——默认全关是产品第一原则，不是故障（灰环＋「还没开启」） |
| `armed` | 链上最近一条 `armed` 字段为 `true`（AUDIT_SCHEMA §4：`armed` 布尔＝「翻转后的权威值——哨兵对 enabled 的执法以链上本字段为准」，B4b「无声开关」的闭合） | 看 duty/trust/harm |
| `drill` | 不是用户旋钮，是**构建属性**：与 dev 徽标同源（`is_dev_build`／`host_shield_dev_drift` 判定，AUDIT_SCHEMA §4 门闸类） | 不用（结论不代表生产担保） |

- **为什么权威源必须是链**：状态文件 `enabled` 可被静默改（B4b 系），
  而链上 `armed` 是「执法依据」。用文件判 mode ＝ 把「无声开关」放回 mode 层。
- **`autostart_missing` 不是 mode 是并存成因**：armed ∧ 在岗 ∧ 自启不在
  ⇒ 主成因照算，自启缺失以徽标/条目呈现（深化件 §8 并存成因）。
- 与 D-02 字段表的接口：`facts.mode_armed ∈ {True, False, None}`；
  `None` ＝ 从未启用（**绝不填 False**——「没记过」与「记了关」是两件事）。

**判据**：① 夹具「全链无 armed 记录」⇒ 必须 `unarmed`，且首屏不得出现任何
绿色元素（与施工件 §7-8 同向，两条都立）；② 夹具「`armed=true` ∧ 进程不在」
⇒ 必须落 armed 家族（黄/红），**不许落灰**；③ 负控：把 mode 判定改成
「进程不在 ⇒ unarmed」⇒ 必须红（那正是 BL-14 的现行形状）。

**落点**：阶段 1（`facts.py`）＋阶段 4（首屏）。

### 3.2 N6（BL-15）：at-risk 来路开放注册表——「将来」从此有家

**现状取证**：`duty=at-risk` 在全仓只有两个实例：缺粮（`granary.state="low"`，
阈值 168＝7 天标准档，`granary.py:68`）与「心跳将断」（无实现——判陈旧只用
`_STALE_AFTER=1800s` 判**已断**，没有**将断**）。BL-15 点的证书到期、磁盘将满、
规则过期、授权到期**没有任何文档接单**（本轮 grep 全 docs 证实）。

**设计**：`at-risk` 不是新灯（黄），是 duty 轴的一个值；它的来路必须**开放注册**，
不许散在分支里。注册表四格缺一不许进：

| 来路 | 触发条件（可复算） | 预告期 | 一句话（将来时） | 动作 |
|---|---|---|---|---|
| `granary_low` | `balance < 168` | `days_left` 天 | 粮还够 N 天，用完监理会停 | 补粮 |
| `heartbeat_will_stall` | 最近心跳年龄 > `0.5 × _STALE_AFTER`（**同源派生，不写死 900**） | 剩余分钟 | 监理 N 分钟没动静，再断就要拉 | （自动重拉，不用动手） |
| `disk_write_full` | 审计卷剩余空间 < 7 天写入量（按实测 84 MB/月折算，`output/_p_silent.txt`）；**真源已存在**：`egress.capacity()`（`egress.py:303`，矩阵 v1.1 N2 已修）＋保留闸三道（14 天／48 MB／剩余 64 MB，`ba374dc`）⇒ 从「候选」升「可注册」 | 约 N 天 | 账本快写不下了，写不下就不能记账 | 清磁盘／改审计目录 || `cert_expiry`／`rules_expiry`／`license_expiry` | **有待核**：先确认产品里有这个事实源再注册 | — | — | — |

- **纪律一（防自造概念）**：后三行是 BL-15 原文点的候选，但**没有真源不许注册**——
  「说得通」正是它比写错数字更危险的地方（F56 第三形态：检索命中的词还要问地位）。
  注册动作本身＝「在源码里找到可复算的读取点」，找不到就停在候选。
- **纪律二**：表外来路点亮 at-risk ⇒ 判据红（注册表是唯一真源，G8 同源）。
- **纪律三**：at-risk 与 paused/absent 的边界——at-risk 是「在岗但即将失去」，
  一旦真断就走 duty=off，不许停在 at-risk 装太平。

**判据**：① 夹具 `balance=100` ⇒ 必须黄且句含「还够 N 天」；② 夹具心跳年龄
1000s（>900 且 <1800）⇒ 必须 at-risk 而非 off；负控：把 `heartbeat_will_stall`
的阈值写死成 900（切断与 `_STALE_AFTER` 的派生）⇒ 必须红。

**落点**：阶段 1（`facts.duty()` 的 at-risk 分支）＋阶段 5（定义句入术语表）。

### 3.3 N7（BL-13）：部分读语义——「读了一半」必须说，facts 要有这一格

**现状取证**：钩子侧已有纪律且实现了：`hooks/pre_tool_use.py:1359 scan_truncated()`，
注释明写「没查到的部分要说出来，不能假装查过」（`:78`）。**体检侧（host-scan）与
事实层没有对应物**：v1.20 §27.10 六态空态里，E5＝「0 个地方被检查（全没查成）」、
E3＝「有 N 个地方没查到（已知盲区）」，**「查了 N 处、还剩 M 处没查（截断）」这一态
没有原文、没有字段**。截断不说＝假绿的一种（BL-13 原文）。

**设计**：扫描结果从「一个数」改三成分，facts 增加 `partial_read` 一格：

```
scan_result = {scanned: N, total: M, truncated: bool, reason: str|None}
facts.partial_read = None | {seen: N, total: M, why: "预算内未完成"}   # 缺失=None，绝不填 0
```

- **预算显式声明**：host-scan 必须声明自己的上限（目录数／字节／秒，三者取先到），
  上限本身进审计（这次扫描用什么预算跑的）——不声明上限，就没法判「该不该截断」。
- **上屏原文**（并入 E3 家族，新态 E3b，写死不许现编）：
  `这次只看了 N 处，还有 M 处没看——没看的部分当空白读，不要当成「没问题」。`
- **与 E5/E3 的分工**：E5＝一次都没查成（结果不算数）；E3＝已知盲区（结构性没查）；
  E3b＝预算内截断（这次没查完）。三者**不许合并**——「没查成」「没查」「没查完」
  是三件不同的事，合并就回到 BL-08 的「读不到当没有」。

**判据**：① 夹具喂 `truncated=True` ⇒ 页面必须出现 E3b 原文且**不许**出现
「没发现问题」类句子；② `facts.partial_read` 缺失时渲染层必须显示「不知道」，
不许渲染 0；负控：把截断分支改成静默跳过 ⇒ 必须红。

**落点**：阶段 1（facts）＋阶段 5（E3b 原文入空态表）。

### 3.4 N8（BL-18）：粮尽三态与「我现在看得少了」必须上屏

**现状取证**（全部本轮源码实测）：
`granary.py:266-271` `tier()` 注释「按余额给档位（**粮尽降档续守用**）。余额低于
一天口粮 ⇒ 守备档」；档位表 `granary.py:126-127`：守备档 12 粮/天「1 台机、
**基础目录**」，标准档 24 粮/天「1 台机、全目录 ＋ 钩子」。**但 `tier()` 全仓没有
第二个调用方**（`granary.py:319` 自用；`inbox_daemon.py` grep `granary` 0 命中）；
`spend()`（`granary.py:252`，注释「哨兵站岗按天走这里」）**无任何生产调用方**
（`antinel.py:1076` 只是 `cmd_granary` 展示 CLI）。⇒ **降档机制只有读数，
没有任何东西在降，用户更不可能知道「看得少了」——因为「看得少」还不存在。**

**设计**：粮不是灯，是 duty 的燃料。三态＋两条披露：

| 态 | 判定 | duty | 用户看见什么 |
|---|---|---|---|
| 标准档 | `balance ≥ 24` | on | 无（常态） |
| 守备档 | `0 ≤ balance < 24` | **at-risk** | 徽标「缺粮」＋一句「现在只看基础目录，钩子停了」 |
| 停摆 | `balance < 0`（真归零） | **off** | 收件箱一条＋期间行标注「这段时间没在守」 |

- **停摆不是 paused**：paused 的前提是「这段时间没有要管的东西」；粮尽停摆期间
  落点照常有对象经过 ⇒ 期间有未拦记录 ⇒ `absent`（有损失）红，无记录也至少黄＋
  「口粮用完了，这段时间没在守」。**把停摆画成 paused 是把「没付电费」画成「无事发生」。**
- **降档披露义务**：守备档生效的那一刻，必须说出**少了什么**（基础目录 vs 全目录＋
  钩子）——不说，用户以为防护强度没变，那是比缺粮本身更贵的假象。
- **与 N6 的关系**：`granary_low` 是 at-risk 注册表的第一个实例；停摆是它的终态。

**判据**：① 夹具 `balance=10` ⇒ 必须 at-risk 且披露含「基础目录」；② 夹具
`balance=-5 ∧ 期间有对象` ⇒ 必须 `absent` 红，**不许 paused 黄**；负控：把停摆
分支接到 paused ⇒ 必须红。

**落点**：阶段 1（duty 的 granary 分支）＋阶段 5（披露句）。**前置**：`spend()`
先有生产调用方（否则整条链无数据可判）——这一步本身零产品行为变化（只加记账）。

### 3.5 N9（D-12 补）：同屏互斥入网——「没事」与「有损失」不许同时出现

**现状取证**：规则早有原文——顶部红块诊断 §5.3：「若同一屏已有『没有要你处理的
事』，红块**不许**再出现 —— 两者互斥（一条说『有损失』，一条说『没事』，必须只能
留一条）」。但**没有任何机器守它**：施工件 §5.2 信息网管的是「同页不许两套计数」，
管不了「两句结论相反」；§5.3 状态词网三条规矩（一词一义／词必有定义／词须对档）
也没有互斥这一条。

**设计**：状态词网补第四条＋一条豁免清单：

- **规矩**：同一渲染产物内，「无账/都替你处理完了」句与「有未修复缺口」句
  **互斥**，同屏只许留一句。
- **新模型下它在结构上自然成立**（主行由 `cause()` 单源派生，§1.2 规矩三），
  但判据仍要立——防的是将来有人把期间行、徽标语、通知句拼进同一屏。
- **豁免（显式列出，不然后患）**：① 期间行（`since-last-look`）是复盘提示，
  自带「这段时间」限定，不算互斥对象；② 徽标语（研发中/缺粮）是身份不是处境，
  不算；③ 收件箱列表与顶部条是两个渲染产物，不算同屏。

**判据**：夹具「`gap_state=open` ∧ info 桶有账」⇒ 主行必须是缺口句，
**不许出现「都替你处理完了」**；负控：把 info 桶句拼进主行 ⇒ 必须红。

**落点**：阶段 3（投影）＋阶段 4（渲染点各一条）。

### 3.6 N10（N4 补＋BL-11 接单）：写链对账锚与「天」的口径

**现状取证**（AUDIT_SCHEMA v1.21 全文复核）：
① §2 链字段只有 `prev`/`hash`/`chain`——**无序号、无计数**；
② §1 `day_manifest.json`＝「每日文件的字节大小＋末行 hash（**链外副本，用于检出
尾部删除**）」；③ `tools/verify_chain.py` 逐条链校验＋日锚对照。
⇒ 三件事说清：**篡改与中段删除检得出（prev 链断）；「从未发生的写」检不出**
——没有任何东西指向一条不存在的记录，而日锚只保尾。这正是深化件 N4 终裁二
（`chain_write_lost>0 ⇒ trust=unbounded` 红）的证据基底，但**对账锚一直没定义**。

**设计**：对账锚＝心跳自己的节律。`host_shield_heartbeat` 是**链上记录**
（AUDIT_SCHEMA §4 会话与心跳类；`host_shield.py:4619 record(audit_dir,
"host_shield_heartbeat", …)`），每 `HEARTBEAT_SECONDS=600` 秒一条
（`host_shield.py:54`）⇒ **每日期望条数可以由墙钟独立算出**：

```
期望条数 = 当日跨度秒数 ÷ 600        # 不写死 144（见下）
实际条数 = 链上当日 type=host_shield_heartbeat 计数
差 > 1   ⇒ 记 chain_write_lost 嫌疑（trust=unbounded，红）
```

- **BL-11 接单部分——DST 口径**：143/144/145 取决于那天是 23/24/25 小时。
  「天」一律**本地时区**的日历日；分母按当日**实际跨度**算（DST 变更日 138 或 150），
  写死 144 会在一年两天上假红/假绿。百分比一律写「分子/分母」（`141/144`），
  不写 97.9%（F40 纪律）。
- **两条腿分开断言（纠缠声明）**：心跳缺失同时是 **duty 信号**（空档⇒不在岗）
  与 **trust 信号**（写丢失⇒证据基底可疑）。一条判据不许同时守两件事——
  否则改一条另一条假绿。duty 腿＝N5/D-05 的活；trust 腿＝本条。
- **不回溯原则保持**：对账发现的写丢失只影响**此刻的 trust 判定**与当日报数，
  不重算历史灯（链不可改，0.39.0 铁律不倒）。
- **2026-10-22 签收后补三条**（《八项开放事项分析与建议》§1.8 命题①，已签收）：
  ① **期望条数扣睡眠时段**——若实测哨兵进程内 monotonic 在睡眠恢复后不前进
  （预判 S3 如此），每次睡眠后心跳排班相对墙钟漂移，链上条数被睡眠系统性吃掉；
  对账期望＝(跨度 − 睡眠时长) ÷ 600，睡眠证据用 D-05 的 `asleep` 标注，拿不到不猜；
  ② **对账视野＝保留窗**——保留策略已落地（14 天／48 MB，`ba374dc`；矩阵 v1.1 §6.5
  明立边界「产品自己会删证据」）⇒ 窗外不可对账，**对外不许说「所有记录都在」**，
  只能说「保留 14 天，删了什么有账」；
  ③ **与矩阵 v1.1 N8 的接法**——N8 说「丢失补偿有尽头：再也不写＝永远不知道」
  （`lost.json` 只在下次写成功时补得出去）；本对账的期望值**按时钟累加、不依赖
  下一次写成功**，恰好覆盖那个「永远看不见」的窗口（期望持续增长而实际条数不动
  ⇒ 差越拉越大 ⇒ 必报）。两条互补，不是重复。

**判据**：① 夹具造一天缺 3 条心跳 ⇒ 对账必须报差且 trust=unbounded；
② DST 夹具（23h 日）⇒ 分母必须是 138；负控：把分母写死 144 ⇒ 在 23h 夹具下
必须红。

**落点**：阶段 1（`facts.chain_health()` 的 L3 腿；L1/L2 已由代码线
`36b7a99` 的 `write_health()` 与深化件 N4 的补偿文件覆盖）。

### 3.7 N11（M2 补）：时态四象 × 8 成因显式映射——四象自己漏了一格

**现状取证**：M2/《最优设计》§2 都把四象用在**灯位**上（不适用/不用/稍后/现在），
但 8 个成因各自在四象里是什么，**没有任何文档声明过**。G3 要求「每个事实声明它在
四象里的表现；缺一即红」——本轮第一次对 8 成因真的声明一遍：

| 成因 | 从未 | 正在 | 曾经 | 将来 |
|---|---|---|---|---|
| `unarmed` 未启用 | ✔ 从未启用 | | | |
| `drill` 演练中 | ✔ 此构建从未发布 | | | |
| `ok` 值守中 | | ✔ | | |
| `paused` 暂停中 | | | ✔ 刚停过 | |
| `draining` 快没粮了 | | | | ✔ |
| `breach` 有缺口 | | ✔ **缺口此刻还在** | ✔ 事件是过去 | |
| `absent` 失守 | | ✔ | | |
| `blind` 看不清 | | | | |

**两个发现（这是把生成器用在生成器自己身上的产出）**：

1. **四象缺第五格「不可知」**。`blind` 归不入任何时态——它不是「从未/正在/
   曾经/将来」，它是「**我说不出**」。⇒ M2 从四象改**五格**（加「不可知」），
   G3 从此对每个事实查五格；`blind` 的「不可知」格必须**显式登记**，不许留空
   （留空＝把它悄悄塞进「正在」，正是 I5 要防的折叠）。
2. **`breach` 横跨两格，正是 F1 的根因**。缺口的事件是「曾经」、状态是「正在」；
   现行实现用**时间窗**判过去（`within_hours`），打的是「事件曾经」那格，
   于是三天前至今没修的缺口被判绿。P4 把判据改成「是否已恢复」，打的就是
   **「状态正在」那格**——这条现在有了时态层面的解释，不再只是一条工程修正。

**判据**：G3 对 8 成因各跑一遍，五格每格要么✔要么显式登记「不适用＋理由」；
`blind` 必须登记在「不可知」格；负控：把 `blind` 的登记删掉 ⇒ 必须红。

**落点**：阶段 3（成因表加 `tense` 列）＋阶段 6（文档同锚：M2 改五格）。

### 3.8 N12（BL-05）：通知送达的兜底链——「最后一米」也要有证据

**现状取证**：`inbox_notify.py` 三种 toast 实现，**无回执**；Windows 免打扰／
通知中心关闭／专注助手 ⇒ 报了，用户没看到，产品不知道（BL-05 原文）。
全 docs grep `delivery_unknown`／「送达」0 命中 ⇒ 无任何文档接单。
已有的相邻资产：`inbox_bubble.bubble_health()`（B-18 闭合，0514 三条判据守着）
给了气泡通道的**健康可见面**；ack 机制在（「知道了」按钮）。**缺的是 seen 与
unknown 两态，以及降级链。**

**设计**（最小闭环，三态记账＋一条降级链）：

| 态 | 怎么记 | 谁记 |
|---|---|---|
| `notice_sent` | 气泡/toast 发出即记（进程内＋文件，不进链——发了什么不是审计事实） | `inbox_bubble` |
| `notice_seen` | **只靠用户动作**（点开／ack），不许猜——猜＝假绿 | 同一处 |
| `delivery_unknown` | sent 且超 30 分钟未见，且降级也失败 ⇒ **进链**（L1，不弹泡——它自己就是「报不达」的证据，再弹一次会递归） | daemon tick |

- **降级链**：sent ∧ 未 seen ∧ >30min ⇒ 降级为托盘角标＋首屏横幅（BL-05 原文
  给的兜底）；降级成功 ⇒ 流程闭合，不记 unknown。
- **无头场景除外**：服务器/无 toast 环境直接走文件通道，**不算 unknown**
  （没有通道不是通道坏了）。
- **度量**：sent/seen/unknown 三个数进日报，**先报数不设阈**（D-13 同款纪律）。

**判据**：① 夹具模拟「发了没人看」⇒ 必须出现托盘/横幅降级；② 降级也失败的
夹具 ⇒ 必须出现 `delivery_unknown` 链记录；负控：把降级链删掉 ⇒ 必须红。

**落点**：阶段 4（渲染/通知点）＋阶段 5（unknown 的呈现句）。
