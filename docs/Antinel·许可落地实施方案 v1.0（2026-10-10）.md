### 1.5 MIT 五件的「可分离性」实测（策略未验，本件补）

策略把五件列为 MIT，但**没验证它们能否真的从 Apache 主体里拆出去**。这一条决定分层是真是假：

| 件 | 是否被 Apache 侧反向依赖 | 结论 |
|---|---|---|
| `challenge/verify.py` | 否（独立复算件，只读链） | **可分离** |
| `antinel_mcp.py` | **待验**（MCP 服务要读审计链） | 需查 |
| `transcript_reader.py` | 否（只解析宿主转录格式） | **可分离** |
| `tools/probe_host.py` | 否 | **可分离** |
| `strings.py` / `glossary.py` | **待验**（宿主侧可能 import） | 需查 |

> **这三条待验项是本件 §5 的核心风险**：若 MIT 件反向 import Apache 件，则 MIT 件的实际使用需要 Apache 代码 ⇒ 「目录级 LICENSE + 目录级依赖」这个模型不成立，必须改为**文件级 SPDX 声明 + 依赖说明**，而不是目录级 LICENSE。

### 3.1 第一层：构建器模板（真源）

| # | 改哪里 | 改什么 | 判据 |

### 3.2 第二层：目录级与文件级 SPDX

**先解 §1.5 的三条待验项。** 验证命令（只读）：

```
查 antinel_mcp.py / strings.py / glossary.py 是否 import 了 Apache 侧模块
```

- 若**不依赖**：走目录级 LICENSE（`challenge/LICENSE`、`tools/LICENSE`）。
- 若**依赖**：**必须改成文件级 SPDX + 依赖说明**，且在 MIT 目录的 LICENSE 里写一句「本目录代码以 Apache-2.0 组件为依赖，依赖部分不受本 LICENSE 约束」。

> **这不是措辞问题，是可执行性问题**：若 MIT 件 import Apache 件，下游拿到 MIT 目录却跑不起来，等于分层是假的。

每个源文件头部：

```
# SPDX-License-Identifier: Apache-2.0     ← 默认
# SPDX-License-Identifier: MIT             ← 五件 MIT 里的
# Copyright (c) 2026 Zhilv Technology (Antinel / PSL)
```

**JSON 与 MD 件**：JSON 用 `//`-free 方式（`rules/*.json` 加一个 `_license` 字段，或在文件头加 `<!-- SPDX-License-Identifier: CC-BY-4.0 -->`；MD 用 HTML 注释）。⚠️ **JSON 加字段会改结构**——须确认 `rules/default.json` 的解析方是否容忍未知键（**待验证项**）。

### 3.3 第三层：SPDX lint（进闸门，不是脚本）

**判据（六条，每条配负控）**

| # | 正判据 | 反向对照 |
|---|---|---|
| L1 | 每个 `.py` 文件首 5 行内有 SPDX 标识 | 摘掉任一文件的头 ⇒ 红 |
| L2 | SPDX 取值只在白名单内（`Apache-2.0` / `MIT` / `CC-BY-4.0` / `CC-BY-SA-4.0`） | 塞一个 `GPL-3.0` 进去 ⇒ 红 |
| L3 | 五件 MIT 目录内的文件必须标 `MIT`，其余必须标 `Apache-2.0` | 把 `challenge/verify.py` 改成 Apache ⇒ 红（防 MIT 层被悄悄收窄） |
| L4 | 护栏清单里的模块（`audit_chain.py` 等）必须标 `Apache-2.0` | 把 `audit_chain.py` 标成 MIT ⇒ **红**（这是护栏本身的守卫） |
| L5 | 根 LICENSE 必须是标准 Apache-2.0 全文，**相似度达标且无附加声明** | 在根 LICENSE 末尾追加一句中文声明 ⇒ 红 |
| L6 | NOTICE 存在且首行是 MIT 豁免声明 | 删掉首行 ⇒ 红 |

⚠️ **L5 的相似度判据要写死阈值并记核验日**——否则「达标」两个字就是空话，与策略 §十二「MIT 回收触发」一个毛病。

## 4. 排期：两个方案，请选一个

**我推荐方案甲。** 理由：许可分层是**发布元数据**，不是运行时行为；混进 0.47.0 会让那一次的版本语义不纯（0.47.0 是告警预算的运行时变更），而版本号纪律要求「运行时行为变化 ⇒ 次版本」。方案乙单独用 0.46.1 是 patch 位，**语义上更诚实**。

| 步 | 方案甲（推荐）：随 0.47.0 一起发 | 方案乙：单独 0.46.1 先发 |
|---|---|---|
| 1 | 先落构建器模板 ＋ SPDX 头 ＋ NOTICE ＋ lint（不发版） | 同左 |
| 2 | 先跑 harness ＋ lint ＋ 闸门，确认全绿 | 同左 |
| 3 | 随后做 Step 5 告警预算（0.47.0） | 直接发 0.46.1 |
| 4 | 0.47.0 一次带齐许可分层 ＋ 告警预算 | 后续 0.47.0 只做告警预算 |
| 风险 | 一版两件事，出问题分不清是谁（**这正是交接件 §8 明令禁止的**） | 发版次数多一次 |

> ⚠️ **注意这个矛盾**：交接件 §8 写过「第 1 步与第 2、3 步不要合并：一处动规则、一处动安全组件的状态语义，合在一版出问题时分不清是谁」。方案甲恰好违反同一条纪律——**一处动发布元数据、一处动告警呈现**。这不算同类（都不是判定语义），但仍不合「一版一事」的通则。**因此我推荐方案乙**，把许可单独作为一次元数据发布；它的改动面小、可回滚性高，风险低于混版。

**修正后的推荐：方案乙**——许可分层单独走 0.46.1。

⚠️ **第 5 步是不可省的一步**：它不产出任何用户可见功能，**只产出「坏了会有人知道」**。按本仓惯例（`selfcert-timing` 把自证卡刷新移到 harness 之后的那一类机制），这一类改动最容易被当成「可有可无」而省掉。**省掉它，本件 §3 的六条 lint 判据就只剩人工执行，而人工执行等于没有。**

## 5. 三处必须防复发的地方（沿用交接件的机制纪律）

### 5.1 最主要的一条：协议事实必须进闸门，不能只进文档

策略 §5 已经点出「分层不是 README 上的一句话」，但**没说怎么保证**。本仓的机制是「真源在构建器」——所以：

- 协议**文本**真源＝构建器模板（改产物会被静默回退，这是本仓实测过的坑）；
- 协议**归属**真源＝文件头 SPDX；
- 协议**一致性**必须由闸门判定，且**每条判据配负控**。

**只做前两层不做第三层 = 分层会随下一次重构悄悄烂掉。** 这是本项目复发过七次的那个形状（换判据来源，不是加检查）。

### 5.2 第二条：`rules/*.json` 加字段会改结构

策略 §十 第 7 条要 `rules/*.json` 头部加 `CC-BY-4.0` 标识。**JSON 没有注释语法**，所以只能：

- 加一个 `_license` 键（**改结构，可能与解析方冲突**），或
- 用 `spdx-tools` 之类的 sidecar 文件（不污染 JSON，但分散）。

⚠️ **必须先验证解析方是否容忍未知键**——本仓规则加载是自研解析器，**未知键被当成规则字段会导致规则集加载失败**。这条是本件列出的第二个高风险点。

### 5.3 第三条：`build_package.py` 改完必须跑回归

构建器有 2597 行、七处许可声明、多个复制分支。改模板后**必须**跑完整构建 ＋ `verify_release` ＋ harness 三件套——构建器自己静默失败过一次（0.42.1 那次假红就是发布验收脚本从未真跑过）。

## 7.5 让协议分层【不可被迭代掉】：三道机制，挂在已有链上

> **这一节是本件的重心。** 前面 §3 讲「怎么落地」，这一节讲**「怎么保证半年后它还在，而且坏了会有人知道」**。
>
> 参照系是交接件 §5 的判据：**复发不是运气不好，是机制缺位的结果。** 协议分层尤其危险，因为它有三条别的机制没有的复发通道：
>
> | 复发通道 | 为什么危险 |
> |---|---|
> | **重构顺手删头** | SPDX 头是一行注释。任何「清理文件头」「统一格式」「批量重写」的重构都会顺手抹掉它，**且不报错** |
> | **发布不复核** | 每次发版都会重跑构建器；**没有任何一处要求发版前检查协议一致性**，所以烂了也能发出去 |
> | **downstream 装到旧层** | 用户装到的是「某一版分层」。发新版不改变旧版已装的事实，于是**协议漂移对用户不可见**，只在下次有人读源码时才发现 |

**核心判断：不能新建机制，必须挂在已经跑了几十个版本的链上。** 本仓已经有三样现成的东西——

| 已有机制 | 现状 | 挂什么 |
|---|---|---|
| **构建器真源** | `LICENSE_MD` ＋ 七处声明同一真源（§1.2） | 协议文本的**唯一真源**；改产物必被回滚（这正是我们要的保护方向） |
| **`psl/manifest.json`** | 逐文件 sha256，实测 **122 条**，**已含 `LICENSE` 与 `challenge/*` 全部 7 个文件** | 协议文件的**内容级指纹**；已有一条诚实声明说它「证明树等于清单、不证明清单等于发布时清单」 |
| **`tools/antinel_verify.py` 的 `superseded` 判定** | 已实现「任一受覆盖文件不同 ⇒ 判 superseded」，实测在用 | 把 SPDX 头**纳入受覆盖集合**，则「头被删」自动变成「判定已失效」 |

### 7.5.1 机制一：SPDX 头纳入 manifest 覆盖（核心）

**做法**：构建器写 `manifest.json` 时，把每个 `.py` 文件的**文件头 SPDX 行**作为独立条目记入（如 `challenge/verify.py#spdx`）。这样一来：

| 事件 | 现状 | 挂上之后 |
|---|---|---|
| 有人删了某文件的 SPDX 头 | **无任何反应** | `antinel verify --manifest` 判 **`superseded`**，与「文件被篡改」同级 |
| 下游装了被删头的包 | 不知情 | 一条命令自查即知 |

**为什么这条是核心而不是锦上添花**：manifest ＋ verify 这套**已经跑了很多个版本、已经被用户信任、已被写进 A6 声明**。往里加一个字段的成本，远低于新建一套「SPDX 检查器」——而后者的致命弱点是：**没人会主动跑它**。

⚠️ **实现要点（防复发）**：
1. **不许只加 SPDX 行的哈希，要加「该文件是否声明了 SPDX」这个事实本身**。零覆盖必须判红——这是本仓已用 `instrument-selfaudit` 固化的纪律。
2. **归一化口径**：版本号行在 `antinel.py` 里是有意变动的（每版都改），而 SPDX 行**永不变动**。所以 SPDX 的哈希是稳定量，可以进 `judgment.digests`；反之若把它与版本号一起归一化，就又变成了「永远不失效」的假保证。
3. 负控：**删掉任一 SPDX 头，`verify --manifest` 必须红**。这条负控必须实测见过红。

### 7.5.2 机制二：发版前的协议一致性闸门（挂在既有闸门链）

**做法**：新闸门件 `ci/inbox_guards_0461.py`，六条判据即 §3.3 的 L1 至 L6。

**挂在哪儿很关键**——按本仓既有纪律，分三档，**逐档收紧**：

| 档 | 时机 | 挂法 | 失败后果 |
|---|---|---|---|
| 轻 | 提交前 | 现有 pre-commit 钩子链（实测已在拦回归闸门） | 提交被拒 |
| **中** | 发版前 | `scripts/verify_release.py` 加一步（它已有 A 至 D 四步，第五步查协议） | **发版中止** |
| 重 | 事后 | `antinel verify`（manifest 机制，见 7.5.1） | 用户自查即知 |

> **为什么不能只做轻档**：SPDX 头被误删的路径大多发生在「重构提交」里，pre-commit 能拦住。但**构建器模板被改错**（比如有人为了好看把 Apache 全文里加了一句话）只有在产物里才看得出来——所以中档必须挂在 `verify_release` 上，那里的四步验收已经是本仓的收口位置。

### 7.5.3 机制三：把「谁属于哪层」写成数据，而不是读代码推断

**做法**：新增一个**协议清单文件**（建议 `psl/license-map.json`），形如：

```
{ "challenge/verify.py": "MIT", "audit_chain.py": "Apache-2.0", ... }
```

**为什么必须做成数据而不是让闸门去猜**：

- 若靠正则扫 import 来推断归属，**有人改了 import 结构就静默改判**；
- 若靠人工维护一份注释，又回到「注释会过期」的老路（本项目复发过的那类）；
- **做成数据之后，它可以被 manifest 覆盖**（进 7.5.1 那条链）⇒ 连它自己被改都能查出来。

⚠️ **一份数据必须有一个唯一的真源和一条它自己的守卫**：
- 真源＝构建器模板（与协议文本同一处，与 §3.1 一致）；
- 守卫＝一条闸门判据：**清单里出现的文件必须真实存在**（防删文件后清单留残渣）；**仓内 .py 文件必须都在清单里**（防新增文件漏登记）。

### 7.5.4 三道机制与「复发形态」的对应

| 复发形态 | 挂哪道 | 挂了之后会怎样 |
|---|---|---|
| 重构删掉 SPDX 头 | 机制一 | verify 判 superseded |
| 构建器模板被改坏 | 机制二（中档） | 发版中止 |
| 协议归属被悄悄改动 | 机制三 ＋ L3/L4 判据 | 闸门红 |
| MIT 层被扩大（护栏失效） | L4 判据（`audit_chain.py` 标 MIT 即红） | 闸门红 |
| 下游装到旧分层 | 机制一（manifest 指纹） | 下游自查可发现 |
| **人不在场、无人主动跑** | — | **无解**。这一条必须诚实标注：任何机制都需要有人跑。现有闸门是**快到没有理由跳过**才活下来的（实测约 8 秒）；协议检查若要进 pre-commit，**必须同样在 1 秒内**，否则会被跳过 |

> **最后一行是本节最该记住的一句**：本仓历史上被明说过的教训是——**闸门太慢等于没有闸门**。所以机制二的三档不是「越严越好」，是**每加一档就要确认它还能天天跑**。
