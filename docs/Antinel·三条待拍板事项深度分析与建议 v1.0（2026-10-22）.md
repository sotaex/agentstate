## 2. 第一问：接受 L2 退出主灯 —— **建议接受**

### 2.1 问题是什么

创始人的观察是「状态一直是拦截」。要判它是不是毛病，先分清「拦截」在产品里是什么：
按规格 v1.2 §1②，**R0/Ls/L0/dev 是状态（有时态、只由此刻）；L2 是事件（天然过去时、只由账）**。
一个「事件」被放进了「状态」的灯里，这就是病根的总纲。

### 2.2 事实基（全部落到行号）

| 事实 | 证据 |
| --- | --- |
| L2 只有一个 kind：`tool_call_blocked` | `inbox_model.py` `LEVEL_OF_KIND`（其余 L2 位无来路） |
| 它恒进 info 桶（Antinel 自己处理掉） | `needs_owner()`＝`item.kind not in AUTO_HANDLED_KINDS`（`inbox_model.py:380`），`tool_call_blocked` ∈ `AUTO_HANDLED_KINDS`（:318）⇒ `bucket_of()` 落 info |
| 生产里**没有 action 桶的 L2 来路** | 活体实测（2026-10-22 02:40）：链上 97 条 L2 的桶集合只有 `{info, archive}`，**无 action** |
| 保持期 30 分钟、按最近一条滑动 | `inbox_model.py:2199` `LAMP_HOLD_MINUTES = 30`；`_event_lamp_level`（:2683-2709）与规格 §3.1 一字不差 |
| 高频下无限续期 ⇒ 常亮 | 24h **21 条**跨 **10 个不同小时**（设计稿 §47.11.7.10.1 ③）⇒ 灯亮约 **6.5 小时/24 小时** |
| 落实到位，不是没落实 | 代码与规格 §3.1 逐字一致 ⇒ **是规格自己有缺口**（§47.11.7.10.2 已结论） |

**规格内部两条理由打架**：语义理由（§1②：事件不该抬状态的灯）被工程理由（§3.5：只有 action 桶抬灯会让 L2 不可达）压住。而工程理由本可以另一条路解（给 action 桶造一个 L2 级来路），规格当时没走。

### 2.3 三个候选与代价

| 候选 | 做法 | 代价 | 判定 |
| --- | --- | --- | --- |
| **A 接受退出** | info 桶一律不抬主灯（现行 `INFO_LAMP_LIFT=False`），L2 降为仅机制可达 | 值守台上看不到「刚被挡下」；但气泡＋计数仍在（§2.4） | **推荐** |
| B 短暂亮一下 | `INFO_LAMP_LIFT=True`＋H 调小 | 见 §3.3 三项代价；治标 | 不推荐（除非创始人坚持） |
| C 给 action 桶造 L2 来路 | 造一种「只有用户能解决的拦截」让 L2 可达 | **今天没有这种真实来路**；造一个就是拿夹具冒充生产可达，正是设计稿 §47.11.7.10 纪律点名禁止的 | 拒绝 |

### 2.4 ★ 必须更正的申报：**气泡没有少**（设计稿 §47.11.7.10.4 那句不准确）

设计稿 §47.11.7.10.4 现写「被挡下的命令从此：**不收气泡、不点灯**」。这是**少报**——实测证明气泡通道对 L2 仍然开着：

- L2 ∈ `inbox_bubble.URGENT_LEVELS = ("R0", "L2")`（`inbox_bubble.py:40`）；
- 守护进程 tick ② 明写路由：`if it.level in BB.URGENT_LEVELS: self._pop_bubble(it)`，否则才走 toast（`inbox_daemon.py` `tick()`，注释「同一个事件只走一条通道」）；
- **活体铁证**（2026-10-22 02:45 读 `~/.antinel/console/notify_state.json`）：
  `bubble:tool_call_blocked = 10-21 03:46:45`、`bubble-ack:tool_call_blocked = 10-21 03:47:11`
  ⇒ 紧急窗真弹过、真被点过「知道了」。

准确形状（四道闸，缺一不弹）：

| 闸 | 位置 | 本机实测 |
| --- | --- | --- |
| 级别闸：只 R0/L2 | `inbox_bubble.py:341` | L2 通过 |
| 配置闸：`bubble=false` 则一声不响 | `cfg_bubble_on()`，**默认开** | 开着（无 cfg.json ⇒ 默认 True） |
| 可见性闸：面板正开着 ⇒ 不打扰 | `pop()` ① | 近 24h 14 条 L2 **零次实弹**，最后实弹在 22.9h 前——最可能是这条 |
| 节流闸：同类 1800s／确认后 1800s | `_throttled()`（`MIN_INTERVAL=1800`、`ACK_QUIET_SEC=1800`） | 03:47 确认 ⇒ 静默到约 04:17 |

⇒ **申报应改为**：被挡下的命令从此不点值守台的灯；主动告知改由气泡承担，但气泡只在
「面板没开着 ∧ 同类 30 分钟内没弹过 ∧ 30 分钟内没被确认过」时敲门。
**新发现盲区**：为什么没弹（面板开着／节流／服务起不来）只存在于那一次 tick 的返回里，**不落盘** ⇒ 事后查不出。这列入 §3.4 的真缺口。

### 2.5 建议与落地清单

1. **接受候选 A**（信息架构口径回到规格自己的语义：事件归气泡与计数，状态的灯只答“此刻”）；
2. 设计稿 §47.11.7.10.4 那句「不收气泡」按 §2.4 改写（**这是文档修订，不是产品改动**）；
3. 规格 v1.2 §3.5 的工程理由改写为：可达性由**机制臂**（S15 第二集合）声明，不由 info 桶抬灯承担；
4. 无需新判据：S15 已拆生产可达／仅机制可达，check 名里就写着“生产今日无 action 桶 L2 记录”，每次闸门跑都把这事实念一遍。

## 3. 第二问：若想「短暂亮一下」—— **建议维持 `INFO_LAMP_LIFT=False`**

### 3.1 机制与两个旋钮

`INFO_LAMP_LIFT`（`inbox_model.py:2461`，现值 **False**）是产品**写明的回退开关**；
`LAMP_HOLD_MINUTES`（:2199，现值 30）是保持期。规格 lineage 清楚：v1.1 §B 上策＝不抬灯（现行），
v1.2 §3.1 回退档＝未读 ∧ H 内抬灯。**被实测推翻的是 30 分钟这个值，不是机制本身。**

### 3.2 打开后会亮多久（推算，口径写明）

算式：`亮灯时长 ≈ 条数 × H × 重叠折损系数`；折损系数取实测同口径
`6.5h ÷ (21 条 × 30 分钟 = 10.5h) = 0.619`。

| H | 推算亮灯时长 | 说明 |
| --- | --- | --- |
| 30（现值，若开开关） | 约 6.5 小时/24h | **实测值**（设计稿 §47.11.7.10.1 ③），非推算 |
| 5 | 约 **65 分钟/天** | 推算：21×5×0.619 |
| 2 | 约 **26 分钟/天** | 推算：21×2×0.619 |

前提「未读」在实测中成立（近 24h 14 条 L2 **全部未读**）。簇发时仍会连亮——滑动续期没变，
只是窗口短了 ⇒ **常亮只是变轻，没有消失**。

### 3.3 三项代价

1. **告警泛洪**：灯与气泡双响。daemon 的设计原话是「同一个事件只走一条通道」——两条都响正是它要避免的；
2. **两套负控失去分辨力＋一套正判据当场红**（逐套核实过，不是一句带过）：
   - `ci/inbox_guards_0380.py:796-801`：负控变异体正是 `M.INFO_LAMP_LIFT = True` ⇒ 翻 flag 后**变异体与现行档重合**，负控失去分辨力，必须重签；
   - `ci/inbox_guards_0470.py:423-432`：同型（`M0.INFO_LAMP_LIFT = True`）；
   - `ci/inbox_guards_0490.py` `_w03_assert()`（:1329）②③④ 现场＋:1339 注释：**正判据**里「拦截」是禁用词，翻 flag 会让它当场红——这是正判据红，不是负控件；其 `N-W03`（:1417）变异体是“旧合并读”，与开关无关。
   ⇒ 翻一个 flag 的账是：两套负控重签＋一套正判据重写。这是新出错面，不是零成本；
3. **语义**：仍是“新闻占着状态的灯”——状态灯只该答“此刻什么情况”。

**若创始人坚持要开**：取 **H=5 不要 2**（2 分钟窗用户来不及抬头看值守台），且必须同时重签那三套负控。

### 3.4 真正的缺口：气泡通道健康**没有可见面、也没有判据守**

§2.4 查出：气泡能否到达，取决于三件用户看不见的事——守护进程在跑、配置开着、面板没开着。
活体实测（`inbox_cli.py daemon status`，2026-10-22 02:47）：

- 仓里 0.53.2（`inbox_server.py` mtime 2026-10-22 02:10:26）；
- **守护进程 pid 23396 在跑，但没有版本戳**（0.53.0 及更早从不写戳）⇒ 看不出跑的是哪版代码；
- 监理服务版本一致（0.53.2）。

⇒ 建议补的是**可见面**而不是灯：让用户能一眼看到「主动提醒：开／守护进程没在跑／刚被挡下 N 次」，
配一条判据钉住“通道不健康时必须如实说，不许静默”。判据层现状：气泡**机制**有 0514 B-02…B-06b 守着
（界面同源、不一闪而过、声音、节流与确认静默、可见性闸），但**运行时健康度**无判据——
`daemon_alive` 在 0372／0490 里只作为猴子补丁的夹具出现，不校验本机真实进程。

### 3.5 建议与落地清单

1. **不翻开关**（维持 False）；
2. 立项「气泡通道健康可见面」：产品面（需签发）＋判据各一；
3. 若要做，判据建议落在 0514 族（紧急提醒的既有家），编号 **B-18**（已查：0514 现到 B-17，全仓不撞号）；
   负控：把可见面摘掉 ⇒ 必须红。

## 4. 第三问：研发态根治 —— **建议产品零改动：补判据＋固入口**

### 4.1 ★ 先更正：**根治机制已经在产品里**

上一轮我曾倾向“改 `is_dev_build` 的触发器”。查证后**自我否决**，因为复位机制早已内置：

| 环节 | 位置 | 做什么 |
| --- | --- | --- |
| 发布最后一步调用复位 | `scripts/release.py:275` | `if _finalize_dev_tree(version) != 0: return 1`——修不成就**大声说并非零退出**，绝不让“包发出去了、研发树在报假失守”悄悄留着 |
| 复位本体 | `scripts/release.py:291` `_finalize_dev_tree()` | ① `_tools_034/_resign_manifest.py --adopt-dev` 补登研发态专属件；② manifest version 回落为 `_DEV_MANIFEST_VERSION = "0.50.5"`（:288，**刻意低于代码版**）；③ 用产品自己的 `host_shield.self_check()` 收口 |
| 判据守着落差 | `ci/inbox_guards_0431.py:563` S70／:581 N-S70 | 「研发树上版本落差必须存在」——落差为 0 即红并给出路 |

**当前树就在复位态**（2026-10-22 02:50 实测）：`self_check() = (True, [])` 0 条问题；
`is_dev_build() = True`（登记版 0.50.5 ＜ 代码版 0.53.2）；`ci/freeze_zones.json` 已登记进 manifest；
活体屏幕「值守中｜研发中」，无红块。

### 4.2 19:22 假失守的真因是**过程缺口**，不是产品缺口

时间线（当日日志 §22）：19:20:30–34 的出包是**直跑构建器、绕行 release.py** ⇒
构建器按设计把树 manifest 刷平（version=0.53.2＝代码版、摘掉 dev 条目、去尾换行）⇒
版本落差归零 ⇒ `is_dev_build()` 的触发器不成立（**第二道闸都没进**）⇒ fail-closed 判 tamper R0，
还建议「请重新安装当前版本」。

关键推论：**刷平态若当时跑闸门，S70 当场红并给出路**——是“用户先于闸门看到红”。
⇒ 缺的不是产品判定力，是**入口纪律**与**守住入口的判据**。

### 4.3 为什么不再改 `is_dev_build`

- 按 problem 形状补触发器，会把**未复位态**修饰成“研发中”绿灯 ⇒ **掩盖 S70 要暴露的结构性红**。
  用户级假红换成闸门级假绿，是**转移**不是根治；
- 研发态只认「登记版 ＜ 代码版」一个**可复算**信号，是早有留械的判定（B1 撤回留档）；
- `_dev_exempt_problems()` 已能把“代码迭代产物”类漂移归入可豁免类（`_fine`），
  把 `host_shield_tamper` 等永不豁免类留在 `_never`——**分级已经存在**，不需要第二套判定。

### 4.4 三个候选与代价

| 候选 | 做法 | 代价 | 判定 |
| --- | --- | --- | --- |
| **A 补判据＋固入口** | 新增 `S54-release`：release.py 必须调 `_finalize_dev_tree` 且在 verify_release 之后，负控摘掉必须红；重申“研发树出包只走 release.py” | 一套判据＋一次负控自证；无产品字节变动 | **推荐** |
| B 改 `is_dev_build` 触发器 | 按 problem 形状补一条研发态判定 | 闸门级假绿（§4.3） | 拒绝 |
| C 构建器收尾自带告警 | build_package 在“final==仓根”语境收尾时若自检不绿／落差为 0，大声警告 | 动到构建器（产品侧），且**不如 A 根本**——它仍然允许绕行 | 可选，暂不做 |

**为什么 A 不是可有可无**：`ci/guard_release_entry.py:109` 的 S40 只查三个 token
（`build_package.py`／`"-m", "build"`／`verify_release.py`）及其顺序——
**`_finalize_dev_tree` 不在其列**。也就是说：今天把 release.py 里那行复位调用删掉，S40 照样绿。
这正是该套件 0.42.0 立身时对付过的“建了没人调用”癌的**同型复发**：复位步现在是零判据覆盖的形态。

### 4.5 残余风险（如实申报）

1. **git 层无机制可防**：另一写者的 `git reset`／`checkout -- <文件>` 可在复位后再次把树打回非复位态
   （本轮已被扫走两次改动，见当日日志 §24.3）。只能靠“每绿一个套件立即提交＋提交前三处比对”缩短窗口；
2. **守护进程无版本戳**：pid 23396 这类旧进程看不出跑的是哪版（§3.4）——与研发态判定无关，但同属“运行态不可确认”家族；
3. **`--adopt-dev` 是止痛不是根治**这句话只对“绕行出包”成立；走正规入口时复位是自动的。
