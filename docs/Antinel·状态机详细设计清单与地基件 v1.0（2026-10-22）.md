## 4. D-03 四轴推导真值表（地基二）

### 4.1 mode

| 值 | 成立条件 | 现行对应 |
|---|---|---|
| `unarmed` | `armed == False`（链权威） | 分支① `POSTURE_OFF` |
| `drill` | `armed == True ∧ is_dev == True` | 分支③ dev（注意：今天 dev 分支还吞 trust，见 N1） |
| `armed` | `armed == True ∧ is_dev == False` | 其余分支 |
| （读不到 armed） | `armed is None` | 分支⑧ exception ⇒ **不许**落 unarmed |

### 4.2 duty

| 值 | 成立条件 | 现行对应 |
|---|---|---|
| `on` | `sentinel_alive ∧ fresh`；`fresh`＝`_elapsed_ok(age) ∧ age ≤ 1800`，或 `age is None ∧ _elapsed_ok(uptime) ∧ uptime ≤ 1800`（`host_shield.py:3625-3626`） | 分支②③⑤ |
| `at-risk` | `duty=on ∧ (granary_level 低 ∨ credits_low_open)` | 今天无对应灯档（Ls 已移徽标）⇒ **新增黄** |
| `off` | `¬alive ∨ (alive ∧ ¬fresh)`；含 age None ∧ uptime>1800、进程死、心跳陈旧 | 分支④⑥⑦ |

**待拍板 Q1（时钟回拨）**：`clock_skewed=True` 时 duty 取哪值？

- 方案 (a)（建议）：`trust=bounded ∧ duty=on`——进程活着、心跳在写是**可观测事实**，
  不可信的只是「时长」读数；动作＝校准时钟（partial），与现行 BL-02 的 `fix_hint`
  「先校准机器时间……让监理进程保持原样」一致。
- 方案 (b)：`duty=off`——证明不了在岗；但动作会变成「拉起」，正是 BL-02 明确拒绝的假按钮。
- 两方案灯同（黄），差在词与动作。**建议 (a)。**

**未来项**：「心跳将断」（at-risk 的第二来路）无现行实现，需 presence 趋势数据
（D-07 衍生指标），本期只落粮将尽。

### 4.3 trust

| 值 | 成立条件 | 现行对应 |
|---|---|---|
| `unbounded` | `self_check_ok == False ∧ 问题非 dev 豁免`（`_never` 类）∨ `chain_integrity_ok == False` ∨ `chain_write_lost > 0`（N4，**待拍板**：建议算——证据链不完整即证明不了在场） | 分支④ warn（R0）＋分支③的 dev 豁免判定 |
| `bounded` | 探针抛错（`probe_error`）∨ 心跳链读不到（分支⑥）∨ 时钟回拨（BL-02）∨ 非核心探针失败（宿主探测、granary 读数失败，D-14）∨ `armed is None` | 分支⑤⑥⑧（L1 盲区） |
| `sound` | 其余：自检通过∨问题全在 `_fine` 豁免类，链完整，无写链丢失 | 分支② |

**注**：`chain_integrity_ok` 的入口当前不明确——`self_check()` 是否已含链完整性校验，
需代码线在阶段 1 明确（设计件的 trust 输入列了「链完整性」，产品侧入口待指认）。

### 4.4 harm

| 值 | 成立条件 | 现行对应 |
|---|---|---|
| `some` | ∃ 记录 `gap_state == open` | 今天无对应灯输入（R0 绝不由账给）⇒ F1 假绿的根因 |
| `none` | 能统计 ∧ 无 `open` | — |
| `unknown` | **仅随 `trust=unbounded` 出现**（裁定 R2） | 无 |

**裁定 R2**（把探针里的隐含规则升为明文）：`unbounded ⇒ harm 置 unknown`
（证明不了自己在守 ⇒ 后果也不可信）；反之 `sound`/`bounded` 必须能统计出 `none`/`some`。
矛盾输入（`sound ∧ unknown`）代码仍须兜住，归 `blind`（探针现有行为：连后果都报不出来，
本来也说不清自己在守什么）。

**待拍板 Q3**：`_outage_consequences()`（缺岗后果，现行由 state 现算）与账本

### 6.1 D-04 `gap_state` 修复判定（挡阶段 2）

`open → fixed` 的三个判定源，按优先级：

| 源 | 判定 | 落地 |
|---|---|---|
| 自愈 | 链上出现 `recovered=True` 或 `state_drift` 已自动恢复 | 读路径派生（`normalize()`），不落盘 |
| 重装后自检通过 | `host_shield_tamper` 类缺口，`self_check()` 恢复通过 ⇒ 该族 open 记录转 fixed | 读路径派生；需定义「哪族缺口对应哪项自检」的映射表 |
| 用户显式 | 「我修好了」按钮 | **产品改动，需签发**；写成一条新链记录（决定发生在那一刻，是事实） |

**默认保守**：无证据 ⇒ `open`（深化件 §6.3 方向）。`waived` 只由用户显式「忽略」产生，
留在期间行（减法留账）。

> **2026-10-22 对齐（实现已落地，`3a6bf7f`）**：代码线按同向实现了拆分，词汇为
> `gap_state ∈ {open, acked, closed}`，与本设计的 `open/fixed/waived` 映射关系：
> `fixed ↔ closed`、`waived ↔ acked`。**采纳实现侧词汇**，且它比本设计多一条好性质：
> `acked` 有 **14 天复核期**（`ACK_REVIEW_DAYS`），过期且仍在时间窗内、有后果、
> 需本人处理的**重新进「要看」**——本设计原让 `waived` 终态退出 harm，实现侧堵上了
> 「先不管＝永远不管」的洞。本表「用户显式」源（「我修好了」按钮）对应 `closed`＋
> 一条新链记录；`unrepaired_count()` 把 n（总数）与 due（过期）分开给，不合成一个数
> （F40 纪律）。旧数据派生规则与 §6.3 同向保守：`ignored → acked`、`done → closed`。

### 6.4 D-07 presence 算法规格（挡阶段 1／4）

```
presence(facts, days=1) →
  片数        144            # 24h ÷ 600s（HEARTBEAT_SECONDS=600，host_shield.py:49 一带）
  有证据片数  141            # 有心跳记录落在 [t, t+600) 的片
  空档        [(起, 止, 分钟数, asleep?), …]   # 连续缺片；分钟数 = 缺片数 × 10
  最老证据    3 天前（4 分钟）
```

规则（在深化件 §7.4 四条上补操作定义）：

1. **空档必须显式列出**，不许折叠成「大概都在」；每条带 `asleep` 标注（D-05）。
2. **空档 ≥ 1800s（3 片）⇒ 该段判缺席**，参与 `since-last-look` scope 的 duty 判定；
   < 3 片的空档只列不判。
3. **在场率写 141/144，不写百分比**（F40 纪律）。
4. **与账本对账**：presence 汇总里「期间挡下 N 次」必须与 `day_counts()` 的
   `blocked` 同源，不另造计数。
5. **首屏露出阈值**：只有 ≥ 30 分钟的空档进首屏块③，其余进折叠（施工件 §14.1 防噪音）。
