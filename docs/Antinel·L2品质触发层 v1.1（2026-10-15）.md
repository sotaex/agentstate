## 0. 这一层是什么、为什么不是判据套件

机制论文档 §5 的分层：正确性走 L0 机械闸门＋L1 判据套件；**品质走 L2 触发-采样-人判**。理由是古德哈特防线：品质判据一旦做成「不过就红」，AI 的优化对象就从品质变成判据，同时 R3「说不出的不对」永远不在判据里——机制越严，盲区越深。

⇒ 本层的全部机制化努力只做一件事：**让该发生的人判在固定时机发生，并且留痕**。判定本身归人（创始人/用户/外部视角）。

⇒ 因此本层的执行程序 `ci/l2_wenhe_selfask.py` **不是判据套件**：不进 `delivery_gate.SUITES`、不写 `@check`、不占 A2 的 29 常驻预算、不产机器绿红。它是触发器＋记录器。（若把 L2 做成套件，等于用机器裁决替代人判，正是机制论文档 §5 明令禁止的形态。）

## 1. 三件流程（按交付时序）

### 1.1 每次交付：违和自问（R3 触发）

**时机**：任何对外交付前（报告、文档、页面、包、提交说明）。
**动作**：`python ci/l2_wenhe_selfask.py`（可加 `--note "观察到的违和"`）。
**程序做的事**：打印本节 checklist ⇒ 人逐条过 ⇒ 有违和则 `--note` 留痕 ⇒ 记录写入 `ci/l2_feedback.jsonl`（含时间戳，供 48 小时沉淀流程消费）。

**违和自问清单（R3：用户潜意识期待 —— 「说不出哪里不对」的那一类）**：

1. 一个**不认识这个项目的人**第一眼看到它，会觉得「这是什么」还是「这又是另一个工具」？
2. 界面/文案/结构有没有「每处都对、放一起不对」的组合违和（术语跨模块不一致、符号混用、同一动作两种叫法）？
3. 数字有没有「说不出的不对」——分母换了、口径混了、时点没标？（回 F40 家族：本句是 R3 与正确性的交界，判据归 L0/L1，违和归本层）
4. 交互有没有让用户等一个**没有反馈**的瞬间？（静默降级，BT-33）
5. 这次交付把什么变复杂了？新人要重读多少才能接手？（E3 演进弹性／BT-62）
6. **本月有没有出现上面五条都没覆盖的违和？**（v1.1 新增 —— 本条不是枚举更多违和类型，
   枚举追不上 R3；它是**清单自身的活性探针**：答案为「有」⇒ 该类型必须进 48h 流程第②类
   （checklist）或第①类（机械化），不许只留在脑子里。G4 的 per-delivery 补偿只有这一条）

**创始人 UX 洁癖清单（每问必过，来自历轮截图吐槽的沉淀）**：

- [ ] 去星号：正文不裸用 `**` `＊` 等强调符（判据侧另有 0430 命令行去星号，本层管人眼可见面）
- [ ] 去杂符号：不裸用 `→` `⇒` `·` `◆` 等装饰符堆叠；不用 emoji 充当状态词
- [ ] 去英文变量名：面向用户的文字不出现 `run_id` `fail-open` `byte-budget` 等裸术语；必须出现时首次给一句平实解释
- [ ] 去过度 jargon：每个技术词能回答「它指向哪个字段/哪类现象」，答不出就回源字段直述（F47/F56 纪律的人眼版）
- [ ] 平实语言：短句、主动语态、说人话；不用「赋能/抓手/闭环」式空转词

**时机**：每月最后一个工作日（或版本发布周，取其近）。
**动作**：`python ci/l2_wenhe_selfask.py --monthly`，按模板逐项过，记录写入同一 jsonl（kind=monthly）。

### 1.3 48 小时沉淀流程（人判 → 判据）

**触发**：任何人判事件（创始人吐槽/试用反馈/PM 意见/违和自问记录）进入 `ci/l2_feedback.jsonl`。
**时限**：48 小时内完成分类（品质论文档 §7.1）。
**四岔分类**（每条必选其一，不许悬空）：

| 类 | 去向 | 沉淀物必须带 |
|---|---|---|
| ① 可机械化 | 升 L1 指标或 L0 判据（走 A1 前置门） | 判据文本、反例样本、首次沉淀日期、负控必红记录 |
| ② 可 checklist 化 | 进本层月度评审模板或交付自问清单 |  checklist 条目、首次沉淀日期 |
| ③ 可外部化 | 进 R1（域内最佳实践）/R2（竞品）参照系 | 参照条目、来源、版本/时点 |
| ④ 不可沉淀 | 保留为 R3 触发点 | 记录**为什么不可沉淀**（不许沉默丢弃） |

**闭环标记**：jsonl 条目 `settled` 字段从 null 改为分类结果＋日期；48 小时未分类 ⇒ 月度评审第 2 项见红。

## 2. 与品质论 M1–M3 阈值的对应

| 阈值 | 本层实现 |
|---|---|
| M1-a **分类率**：每月人判事件 100% 有分类记录（判④也计达标） | jsonl 全量留痕＋48h 时限＋月度评审第 2 项对账 |
| M1-b **沉淀率**：①②③ 三类才计达标；判④只计记录不计沉淀 | 月度评审第 2/6 项对账；`--guard` 输出四岔分布 |
| M2 同反馈重复人判两次＝沉淀失败，红 | 自问清单即防重复人判的第一层（写下来的判据不会忘）；月度评审复核 |
| M3 看板每轮重填、当期值脚本取数、休眠维度有唤醒条件 | A5 看板（脚本取数）＋月度模板第 1 项休眠声明 |

> **v1.1 为什么把 M1 拆成两个分母**（G3）：v1.0 的 M1 写成「100% 有分类记录」，
> 而条目**全判④「不可沉淀」时分类率照样 100%** —— 指标一片翠绿，沉淀实际为零。
> 这是古德哈特防线在**元指标层**的漏网（防线只守住了产品指标，没守住机制的仪表自身），
> 且这次被优化的不是 AI 是**填表的人**（人找最省力满意解的速度比 AI 快）。
> 拆开后 M1-a 仍可用④满足（它就是只要求「不许悬空」），但 M1-b 会让「全判④」立刻现形。
> **反向探针**（v1.1 起每季度一次）：造一条明显可沉淀的人判事件（例如「术语表缺一条已三处出现的同义叫法」），
> 若被归④ ⇒ 记一次沉淀失败，红的是**流程**不是品质。

## 3. 边界（如实）

1. **本层不承诺品质可被机器判定**——A 类负收益四项（R3 终审、复合失效组合识别、元问题终审、「违和」终审）按机制论文档 §4.1 保持人判，本层只保证它们**被触发且留痕**。
2. **自问清单会过期**（BT-57 时效腐坏）：清单条目参照系变迁时按 48h 流程第③类升版，不静默沿用。
3. **执行率本身是纪律指标不是品质指标**：自问做了不等于品质好了——M2 防的是「做了自问就以为解决了」。
4. 本文件是机制论文档 §9-4 自撞条款的实例（第五份文稿）：下一轮机制问题到来时，若本层三流程未被任何机制设计引用，本文件自动列入退役候选，不续版。
5. **v1.1 新增·本层判据（执行率、四岔分布）只能报警不能验收**（B2）：它们变难看时的正确动作是查流程，不是改产品。
6. **v1.1 新增·元守护探针 rc 恒 0 ⇒ 永不影响闸门结论**（D-37 同型）。若有人为让它出声而放宽口径，那是新的盲区，按 §4 申报。

## 4. 元守护（v1.1 新增）：本层自己的活性探针

### 4.1 为什么需要它（G5 的诚实申报）

v1.0 落地时，本层**零守护且未申报盲区**：`ci/l2_feedback.jsonl` 的唯一消费者是本程序自身，
`delivery_gate.SUITES` 无本层条目，任何判据都不看它。后果可实测：**连续三个月没人跑自问程序，
闸门全绿、看板无事**——只有 jsonl 的空洞能证明，而没有任何东西看这个空洞。
这违反本仓 M-C 铁律（守护必须分层声明，每层至少一条或申报盲区）。v1.1 补上，并保留申报记录。

### 4.2 探针形态：只出声、不裁决

```
python ci/l2_wenhe_selfask.py --guard
```

查四件事，**全部只打印，rc 恒 0**：

| # | 查什么 | 为什么是它 |
|---|---|---|
| ① | jsonl 是否存在、近 30 天有无记录 | 「没人跑」是唯一真事故，其余都是品质问题 |
| ② | 48h 队列积压条数与最老条目年龄 | M1-a 的实时形态（不必等月末） |
| ③ | 本期自问执行次数 vs 交付次数（分母按 §5 机械定义） | 让执行率**可核算**（v1.0 的分母靠人工估） |
| ④ | 四岔分布：①②③ 各几条、④ 占比多少 | M1-b 的实时形态；④ 占比持续走高 ⇒ 沉淀漏斗上游漏 |

### 4.3 为什么不进 SUITES（与 §0 同一条理由，但方向相反）

§0 说品质判据不能做成「不过就红」；本节说**连「这层还活着吗」也不做成红**——
做成红，就会有人为了让灯绿而批量生成自问记录，把活性探针变成表演（§3-6）。
它回答「这层还活着吗」，不回答「品质好不好」；后者归人，且只在月度评审发生。

## 5. 「一次对外交付」的机械定义（v1.1 新增）：让分母可算

v1.0 的月度模板第 5 项「交付违和自问执行率」要求填「应交付次数」，但**没有机械定义** ⇒
该项不可核算，只能人工估 ⇒ 估出来的数不能进看板（F40：百分比一律带分母）。

**定义**：统计期内 `git log` 中**改动产品路径或文档路径**的提交数，一次提交记一次交付。

**口径声明（三条，缺一即混口径）**：

1. **计入**：`antinel*.py`、`inbox_*.py`、`host_shield.py`、`hooks/`、`rules/`、`assets/`、`scripts/`、`ci/`、`docs/`、`*.md`、`*.json`（psl/ 除外见 2）；
2. **不计入**：`.workbuddy-ai/`（记忆）、`_p_*`（探针）、`out/`、`_uxtest2/`（构建产物）、纯 stash/revert 提交；
3. **一次提交 = 一次交付，不论大小**（不做「非平凡变更」分级——分级阈值本身需要人判，会 reintroduce 人工分母；分级若将来要建，走机制论 A1 前置门）。

> 与仓内既有实践同源：S70 判据（`ci/inbox_guards_0431.py`）同样以 git 为可靠读数。
> 该定义只服务于**分母核算**，不构成「必须自问才许提交」的钩子强制（那是咽喉点机制，
> 属正确性域，需单独过 P1–P5，本版不做）。

## 附：执行程序

```
python ci/l2_wenhe_selfask.py                  # 交付前违和自问（打印清单+留痕）
python ci/l2_wenhe_selfask.py --note "..."     # 自问中发现违和：留痕进 48h 沉淀队列
python ci/l2_wenhe_selfask.py --monthly        # 月度品质评审（打印模板+留痕）
python ci/l2_wenhe_selfask.py --pending        # 看 48h 沉淀队列：哪些条目超时未分类
python ci/l2_wenhe_selfask.py --guard          # 元守护探针：四件事只打印，rc 恒 0（v1.1 新增）
```

记录文件：`ci/l2_feedback.jsonl`（每行一条：ts/kind/text/settled）。
**`settled` 字段 v1.1 起改为四岔枚举值**（`mech` / `checklist` / `external` / `unsettleable`）＋日期，
不再接受自由文本——否则 M1-b 的沉淀率算不出来（自由文本无法机械分组）。
存量自由文本条目按「无法判定 ⇒ 不计入 M1-b 分母」处理，并在 `--guard` 第 ④ 项单列一行报告。
