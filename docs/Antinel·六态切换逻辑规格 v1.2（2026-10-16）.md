## 0. 本轮输入与总结论

**创始人四问（2026-10-16 上午，原话摘录）**：

1. 「可能同时存在多态，例如缺粮跟其他几态可能同时存在，这种情况下怎么办，
   要拿出方案。」
2. 「关于拦截，因为是一个瞬时的事情，是否需要约定一个时长，在拦截刚发生之后
   的一定时间段内显示呢。」
3. 「关于注意，如果触发了，那么，什么时候结束呢。」
4. 「研发中这个态其实也是跟其他几个态会并存的，只要研发机版本号高于 pypi 上边
   的版本号，就是研发态，应该一直显示，不过其他态也要显示，因此是同时的，
   而且始终同时。」
5. （附带决定）「口粮可以后续迭代升级再接入……不过要先把切换逻辑准备好。」

**总结论——现行「单值优先级梯」在结构上无法表达并存**：

`current_state()`（`inbox_model.py:1169-1223`）返回**一个** `lv`，
`PRIORITY`（`:78`，`{R0:5, Ls:4, L2:3, L1:2, L0:1}`，dev 不在梯上）把六态
压成一条**互斥**的梯。创始人的两个例子——缺粮＋拦截、研发中＋其他态——
都是**两个同时为真的事实**；单值灯必须二选一，**选哪个都在掩盖另一个**。
今早事故（11 条 22 小时前的自动拦截把灯钉在「拦截」）是同一病根的第三例：
**事件的新鲜度维度在灯里根本没有表达手段**，只有「在不在 24h 窗口」一个
粗粒度开关。

⇒ 修法不是给梯子加级，是**分通道**：

| 通道 | 答什么问题 | 取值 | 互斥性 |
|---|---|---|---|
| **主灯** | 此刻什么情况 | R0 / L2 / L1 / L0 | **互斥**（同一维度按严重度取最高） |
| **徽标** | 还有哪些并存态 | 研发中 / 缺粮 | **不互斥**，可同时多枚，常驻 |
| **计数** | 多少事没办 / 没看 | 要处理 N / 待阅 N | 不互斥 |

六态词表**不动**（03372 S09：`GL.TERMS[k]["w"]` 六态键不可撤）：dev 与 Ls
从「灯态」变为「**徽标态**」——词条还在、键不撤，变的是**组成方式**与判据锚点。

## 1. 诊断：为什么必须是分通道（三条证据）

**① 单值梯的结构缺陷（代码事实）**：`current_state` 四步（Step 0 基础档 →
Step 1 事件抬灯 → Step 2 篡改分通道 → Step 3 粮）全部在争**同一个返回值**。
任何两个同时为真的态进入这个函数，只有一个能出来。v1.1 探针实测的两处
「被迫二选一」：

- **B3**（`output/_p_state_bounds.log`）：guarding ＋ 历史 dev_drift 账 ⇒
  灯 **dev「研发中」**——姿态说「监理在岗」、灯说「研发中」，同屏两个事实
  只有一个能显示；
- **B5**：guarding ＋ zone 上锁失败（R0 级、action 桶）⇒ 灯 **L0「值守中」**——
  「真正只有你能解决的事」躺在收件箱里，灯说没事（v1.1 已记：现行原因句在
  这种情形下**会说错**）。

**② 来源分工表自己就暗示了分类**（`current_state` docstring `:1175-1184`，
0.39.0）：R0/Ls/L0/dev 是「**状态**（有时态，只由此刻）」，L2 是「**事件**
（天然过去时，只由账）」，L1「兼有」。事件还要再分「**刚发生**」（值得上灯）
与「**已历史**」（只配计数）——这个「新鲜度」子维度在现行灯里不存在。

**③ 今早事故是第三例**：`tool_call_blocked` 是 `AUTO_HANDLED_KINDS` 成员
（`:189-199`，Antinel 已自己拦下）却在 22 小时里把灯钉在 L2。创始人裁定
0.35.3「尽可能少让人处理……你知情即可」与 0.39.0「反应当前的准确状态」
各只落了一半（桶改了、灯没改；R0 改了、L2 没改）——**单值灯是那个漏配的落点**。

## 2. 三通道显示模型（本轮核心方案）

### 2.1 主灯（互斥维）——「此刻什么情况」

- **基础档**（姿态七值，现行 `base_state` 大部分保留）：
  `down`/`warn` ⇒ R0；`interrupted`/`unknown` ⇒ L1；`guarding`/`off` ⇒ L0；
  **`dev` ⇒ L0**（哨兵在岗放哨是事实，研发身份移徽标——0.36.4「研发中不掩盖
  真实状况」的彻底化：不是把研发身份说成在岗，是**两个通道各说各的**）。
- **事件抬灯**：窗口内未关闭的记录，按桶分流——
  - **action 桶**（`needs_owner`，只有你能解决）⇒ 抬至该条 level 的灯档
    （L2/L1），**在 24h 窗口内持续到处理/关闭**（它是待办，不是新闻）；
  - **info 桶**（自动处理/无后果）⇒ 仅当 **unread ∧ 在保持期 H 内** 才抬灯
    （§3）；
  - **R0 绝不由账给**（0.39.0 铁律，S16 不动）——未处理的 R0 级 action 事项
    由「要处理」计数与原因句出面，灯不染红。
- **dev 姿态不再产 dev 灯**；`light()` 与 `base_state` **不动**
  （0364 钉的正是它们——`light("dev")`⇒STATE_DEV、base_state dev 分支源码
  结构；`light()` 是诊断/归因面的合并读，不是灯）。

### 2.2 徽标（并存维）——「还有哪些并存态」（常驻，可多枚同时）

- **研发中**：判据＝**本机代码版本 > PyPI 已发布版本**
  （`antinel.py::VERSION` vs `psl/workspace_facts.json` 的
  `release.pypi.published_version`——该位只由实查改写，是本仓既有纪律）。
  本机现状：代码 **0.50.6** vs 已发布 **0.35.1**（2026-10-06 实查）
  ⇒ 徽标**现在就该亮**（而现行灯态今天任何 dev 都不显示——见 §4.2）。
  - 取不到版本对照（facts 缺失/解析失败）⇒ **不显示徽标**（降级不假阳，
    同 `granary_now` 的容错哲学 `:995-1000`）；
  - **收敛靠事实追平**：PyPI 上传成功 ⇒ 实查回写 `published_version` ⇒
    徽标自动消失（同 `is_dev_build()` 的 0.36.4 纪律「靠事实追平，不靠时间
    自己好」）。**发布流程增补项**（§7 拍板 10）。
- **缺粮**：`granary=low ∧ 在岗`（`_GRANARY_ON_DUTY=("guarding","dev")`，
  `:992`；**数据源待接入**，§4）**∨** 存在未关闭的 `credits_low` 记录
  （已活：level=Ls、进要处理、标题「缺粮：积分余额偏低」`:126`——v1.1 T3
  实测：不点灯但进 action 桶，正是「第二个桶灯分裂」，徽标化后它有了正位）。
- **与主灯的关系**：不争位、不互斥、**始终同时**。dev 徽标 + R0 主灯
  ＝「研发中的机器此刻失守」——两个事实都显示，谁也不掩盖谁。

### 2.3 计数（待办/待阅维）——「多少事没办、没看」

- **要处理 N**：action 桶**件事**数（现成；24h 窗口是 0.35.3 既定——
  `bucket_of` docstring `:310-312` 有实测理由：不带窗口时 100 条「要处理」
  绝大多数是 7 天前已过期的拦截，窗口外的进归档不丢）；
- **待阅 N**：info 桶窗口内未处理条数（**保持期外的未读＋已读进这里**——
  今早那 11 条的归宿）；
- **原因句三元组**（立规）：主灯原因 ＋ 徽标原因 ＋ 待办提示；
  **action>0 时禁止说「此刻是好的」**（v1.1 B5 记的缺陷正式立规；
  文案仍守 W06/W09：不露英文变量、不露技术名）。

### 2.4 渲染面（S-14 六消费面的落法）

| 面 | 现行 | v1.2 |
|---|---|---|
| 窗口标题（`inbox_window.py:770` 派生） | 「拦截 · Antinel 监理#run_id」 | **不变**（主灯态；徽标不进标题，避免长标题） |
| 页面标题/顶部条（`inbox_server.py:615/:2043/:2265`） | 主灯 | 主灯＋**徽标芯片行**（与术语芯片同构：`glossary.chip()` 的 `name="term"` 互斥手风琴先例） |
| 托盘（`inbox_tray.py:302`） | 主灯 | tooltip 带徽标文字 |
| 归因面板（`remediation.py:503`） | `light()` 合并读 | 合并读＋三通道全量解释 |

（窗口标题是否带徽标：待拍板 6，建议不带。）

## 3. 保持期：拦截与注意的「时长」（创始人第 2、3 问）

### 3.1 规则

- **info 桶事件**（自动处理的拦截/注意）只在 `unread ∧ now - ts ≤ H` 内
  抬灯；**已读＝已知情，提前结束**（0.35.3「你知情即可」的机制化）；
  超期 ⇒ 只进「待阅 N」计数与收件箱，**灯回基础档**。
- **action 桶事件**（要你处理的）在 24h 窗口内未关闭即**持续抬灯**——
  它不适用保持期：**待办不是新闻**。（窗口上限是 0.35.3 既定，不改。）
- 保持期从**最近一条**合格记录起算（滑动：期间再来新的，顺延）。

### 3.2 H 取值（待拍板 2）

`LAMP_HOLD_MINUTES`，参数化（改值不改结构）。**建议 30 分钟**，理由三条：
① 创始人 2026-10-06 已判「窗口太长了，默认不要这么长」——H 是同一方向的
进一步收敛（24h ⇒ 30min，1/48）；② 30 分钟覆盖一次短暂离席（咖啡/一个电话），
又与「紧急提醒」气泡形成分工——**气泡管「刚发生」、灯管「还新鲜」、计数管
「还没看」**；③ L2/L1 **同一 H**：保持期的目的是「给看一眼的机会」，
不是按严重度分级霸屏，同一值更易解释也更易判据化。候选 10/30/60。

### 3.3 与气泡的关系（不替代）

紧急提醒气泡是**即时打断**（发生了什么，现在看）；保持期灯是**环境状态**
（刚才的事还新）。两者并存，不互相收编。

### 3.4 「注意什么时候结束」——完整答案（三个来源各自结束）

| L1 来源 | 结束条件 |
|---|---|
| 姿态类（interrupted/unknown，此刻探不到/缺岗无损失） | 姿态恢复（探到了/哨兵回岗） |
| 事件类 info（revived/changed/dev_drift 等自动处理） | **H 后衰减**，或**已读提前结束** |
| 事件类 action（未关闭的要注意事项） | 处理/关闭（24h 窗口内） |

⇒ L1 **从不单独挂 24 小时**——现行「24h 窗口内未处理即抬灯」正是创始人
此问指向的缺陷。

### 3.5 保住 L2 可达性（对 v1.1 的重要修正）

v1.1 的中策（口径 B：只有 action 桶抬灯）有隐藏代价——**今天没有任何
action 桶的 L2 kind**（`tool_call_blocked` 在 `AUTO_HANDLED_KINDS`），
口径 B 会让 L2 成为**不可达态**（S15 必红且六态少一态）。保持期方案下
fresh 的 info L2 仍亮「拦截」⇒ **S15 的 L2 行不用重签**（§7.3 实测：
可达表夹具全 fresh）。⇒ **保持期是比口径 B 更省的修法**：同样fixes今早
事故，不动六态可达集。

## 6. 显示规则汇总（实现轮的判定清单）

1. 主灯 = 基础档(姿态) ↑ 事件抬灯(action 未关闭 ∨ info unread∧fresh)，
   R0 绝不由账给，dev 姿态 ⇒ L0；
2. 徽标研发中 = 代码版本 > published_version（取不到 ⇒ 不显示）；
3. 徽标缺粮 = granary 低∧在岗 ∨ credits_low 未关闭；
4. 计数：要处理 N（action 件事）／待阅 N（info 未处理，含 aged）；
5. 原因句三元组；action>0 禁说「此刻是好的」；
6. `light()` / `base_state` / `_window_open` / `bucket_of` **不动**
   （0353/0364/S16/S10 前半的锚都靠它们——边界即安全）。
