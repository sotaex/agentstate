## 0. 结论先行

**问「能不能完备」，要先问「完备」指哪一种。它有三种含义，只有第一种做不到。**

| # | 含义 | 判据 | 能否做到 | 理由 |
|---|---|---|---|---|
| ① | **世界完备**：把现实世界所有可能的失效列完 | 清单穷尽 | **不可能** | 失效空间是开放的：新硬件、新系统版本、新用法每天在产生新的失效型 |
| ② | **合同完备**：对已声明的输入域，每一点都有定义输出 | 全函数 | **可能且必须** | 域是有限且我们定义的 |
| ③ | **闭合完备**：域外输入不得被静默映射成域内值，必须具名拒绝 | 无默认放行 | **可能，且比②更重要** | 这是纯代码属性，可机械检查 |

**所以「100% 包含」这个说法，只能对 ②③ 成立，对 ① 不成立。任何声称做到 ① 的方案都是自欺。**

但这不等于「只能列清单、必然有洞」。本轮的核心发现是：

> **功能是开放的，载体是封闭的。**
> 按「功能」枚举必然漏（功能无限）；按「载体」枚举可以封闭——一个进程能失效的方式，受限于它能消耗和依赖的**有限几类资源**。

八类载体（§2）是封闭集。**5 个控制动作 × 8 类载体 = 40 格**，这是有限的、可逐格签字画押的完备域。**"无死角"只能在这个 40 格上定义，不能在"所有可能的故障"上定义。**

## 1. 为什么"列清单"必然有洞：本仓的三条实证

不要讲抽象道理，用本仓自己的证据。

### 1.1 洞一：清单由人写，而人只列自己想得到的

上一轮我列了 14 个「未被提出的维度」。本轮用载体法重跑，40 格里**明确无检测的至少 11 格**（§6.2），其中 3 格是上一轮 14 条里完全没有的（磁盘自噬、通知无回执、误挡）。**同一作者、同一系统、隔一天，就漏了三条。** 这就是清单法的天花板：它的产出上限是作者的想象力上限，而不是系统的失效上限。

### 1.2 洞二：清单会过期，而系统在长

`0372 S08` 守的是「全仓只许有一份词表声明」，所以它守得住 6 张表之间的漂移。**但托盘那三处是元组，不是表**（`inbox_tray.py:161/199/201`），于是天然全绿。清单上"词表已收口"这一行，在代码长出内联副本的那一刻就失效了，而清单不会自己变红。

### 1.3 洞三：清单只管"有没有想到"，不管"判据是不是活的"

本仓已记录**假绿五族**（死判据、夹具合成形状、输入边界≠规则边界、判据走注入参数而生产走默认参数、锚被别处天然满足）。**这五族的共同点是：清单上那一行是打勾的。** 清单无法区分"守住了"和"以为守住了"。

⇒ 结论：**清单是必要的存档，但不能作为完备性的依据。** 依据只能是生成器（§3）＋闭合判据（§7）。

## 2. 关键转向：按载体枚举，而不是按功能枚举

### 2.1 为什么载体是封闭集

一个在用户机器上 24 小时运行的进程，能失效的方式最终都落在它对**有限几类资源的依赖**上。这不是哲学断言，是工程事实：代码不能凭空失效，它只能因为「时间不对／空间不够／没有权限／输入不认识／同时来了两份／版本对不上／环境变了／人动了它」而失效。

| 载体 | 含义 | 典型的"我不知道"形态 |
|---|---|---|
| **1 时间** | 时钟、超时、顺序、时序 | 时钟回拨后我把"很久没动"读成"刚启动" |
| **2 空间** | 磁盘、内存、句柄、文件数、深度 | 写不进去时我不报警，于是我干净地什么都不记 |
| **3 权限** | 读/写/执行/网络/注册表 | 读不到时我当成"没有" |
| **4 输入** | 格式、编码、大小、非 ASCII、恶意构造 | 我不认识时我挑一个默认值 |
| **5 并发** | 锁、竞态、多实例、重入 | 两份同时写，后写的赢了，我不说 |
| **6 版本** | 数据 schema、代码、依赖、协议 | 旧数据用新代码读，读出一片空白，我当空状态 |
| **7 环境** | 合盖、休眠、网络切换、代理、杀软、时区 | 环境变了，我的判据还在用旧假设 |
| **8 人** | 误操作、忽略、不理解、不读、关掉 | 用户按了按钮，我把它当"已处理" |

### 2.2 与 5 个控制动作交叉

「监理」对外只有 5 个控制动作。这是它的全部作为，没有第六个：

**看**（扫描/探针）→ **判**（结论）→ **报**（通知）→ **挡**（拦截）→ **记**（链/账）

5 × 8 = **40 格**。每格只有一个问题：

> **这类载体坏掉时，我凭什么知道？**

答不出，就是盲区。答"我不会坏"，就是自欺。**40 格是有限集，可以逐格签字，这就是"完备"的可操作定义。**

### 2.3 这套分解为什么比"功能清单"强

因为它**在系统长大时自动长大**：新增一个控制动作（比如"修"）⇒ 立刻多出 8 格；新增一类载体（比如"能耗/电池"）⇒ 多出 5 格。而功能清单在系统长大时只会变得不准。

## 3. 五套方法论：各管一类洞，不可互相替代

创始人问「某种或某几种方法论」。答案是**五种，各管一类，任何一种单独用都会留下另一类的洞**。

| # | 方法论 | 管哪类洞 | 本仓现状 |
|---|---|---|---|
| M1 | **STPA / UCA**（控制动作 × 四类失效） | 控制动作**做错**（不是部件坏了） | **无**（从未用过；但「白名单才是对的」那条纪律是它的直觉版本） |
| M2 | **时态四象**（从未 / 正在 / 曾经 / 将来） | 时间维**漏格** | **部分**（有"曾经/已恢复"，缺"从未"与"将来"） |
| M3 | **闭合性**（全函数 / 具名拒绝） | 域外输入被**静默映射**成域内值 | **部分**（`unknown` 有词；但 `else "L0"` 违反它） |
| M4 | **变形测试 / 删除法** | 判据是**死的**（假绿） | **有**（负控＋"删掉再跑"已入纪律） |
| M5 | **能力分析**（capability，不是 deny-list） | **误挡**与**漏挡**同时存在 | **有雏形**（`_READONLY_CMDS`），但被 token 级否决打穿（§6.1 BL-01） |

### 3.1 M1 STPA 的四类失效，套在监理身上

这是本轮最有产出的一套。对每个控制动作，问四个问题：

| 失效型 | 对监理的含义 |
|---|---|
| **未提供** | 该看的没看、该报的没报、该挡的没挡 |
| **提供了不该提供的** | **误挡**（挡了用户的正常操作）、误报、越权读取 |
| **时机错误** | 报太晚（人已离开）、判太早（环境未就绪）、挡太晚（已执行完） |
| **持续错误** | 停止过早（预算耗尽后静默降级）、持续过长（锁不释放、红灯不降级） |

5 个动作 × 4 类 = **20 格**，与 §2 的 40 格是**两张正交的网**：40 格问"哪类资源坏了"，20 格问"控制错了哪一维"。两张网交叉，覆盖的洞型完全不同。

**为什么这套能把"没想到"逼出来**：因为"时机错误"和"持续错误"这两列，人几乎从不主动想。而本轮实测的两条最严重盲区（BL-01 误挡、BL-02 时钟回拨 fail-open）**恰好都落在人不会主动想的那两列**。

### 3.2 M2 时态四象

任何一个事实，都有四种时间态，而状态机通常只画了后两种：

| 时态 | 例子 | 本仓 |
|---|---|---|
| **从未** | 从未装过／从未跑过 | ✘ **缺**（新装第一屏就是这一态，而它被画成绿） |
| **正在** | 此刻在岗 | ✔ |
| **曾经** | 出过、已恢复 | ✔（`recovered`） |
| **将来** | 还没失效，但即将（缺粮、证书到期、磁盘将满） | △ 只有 `granary` 一处 |

⇒ 「从未」与「将来」是两整列的系统性遗漏。**这不是漏了一条，是漏了一维。**

### 3.3 M3 闭合性：完备不是"答对"，是"不假装答了"

这一条要说得更硬一点。

一个函数是**全函数**，指的是它对定义域内每一点都有值。而**闭合**要求更强：**对定义域外的输入，它不许悄悄返回一个域内的值。** 必须抛出/返回一个**具名的拒绝**。

`inbox_tray.py` 的 `else "L0"` 违反了它：未知态不是被拒绝，而是被映射成"值守中"。**一个系统只要有一处这样的默认分支，"完备"就无从谈起——因为它把"我不知道"永久地、静默地转成了"我很好"。**

这条是可以机械检查的（§7 C2）：**每一处对有限字母表的 dispatch，其默认分支必须是 `raise` 或返回具名 `unknown`，不许返回任何"正常"值。**

### 3.4 M4 变形测试："把要守的东西删掉再跑"

本仓已有，不重复。但要补一句它为什么属于方法论而不是技巧：**它是唯一不需要"正确的期望值"的测试方法。** 而本仓最痛的教训恰恰是"期望值从实现现状抄 ⇒ 把缺陷钉成判据"。删除法绕过了这个陷阱。

### 3.5 M5 能力分析：deny-list 必然漏，因为 token 可以被引用

这是本轮实测撞出来的，见 §6.1 BL-01。一句话总结：

> **判断"这条命令危不危险"，不能看它含不含危险词，要看它有没有能力把危险词变成执行。**

含 `os.remove` 的 `grep` 没有这个能力；含 `2>/dev/null` 的 `grep` 也没有——但现行实现因为 `>` 而否决了降级。**deny-list 的洞不在于"漏了一条规则"，而在于它回答的是错误的问题。**

## 4. 生成器清单（G1–G10）：把清单变成函数

**清单会过期，生成器不会。** 每个生成器是一段可以反复跑、在系统变化时自动产出新行的东西。下表每行都必须能回答「它产出多少行、怎么机器判」。

| ID | 生成器 | 产出 | 机器判法 |
|---|---|---|---|
| **G1** | **载体 × 动作矩阵**（5×8） | 40 格缺口 | 每格必须登记一个检测器 ID 或"显式接受风险"；空即红 |
| **G2** | **UCA 矩阵**（5×4） | 20 格缺口 | 同上 |
| **G3** | **时态四象** | 每条事实 × 4 | 每个事实声明它在四象里的表现；缺一即红 |
| **G4** | **字母表闭合** | 每处 dispatch | AST 扫所有 `dict.get(k, 默认)` / `else` 落正常值 ⇒ 红 |
| **G5** | **面派生**（已立法） | 全量 module | 从 `pyproject.toml` 派生，不写死 |
| **G6** | **渲染点枚举** | 每个事实 × N 处 | 派生自代码（谁读了该事实），不靠记忆 |
| **G7** | **异常吞咽面** | 163 处 | 每个 `except: pass` / `return 默认` 登记"我知道它失败时是什么" |
| **G8** | **同源检查** | 每个事实 | 同一事实只许一处实现；出现第二处 ⇒ 红 |
| **G9** | **删除法** | 每条判据 | 删掉被守物再跑，仍绿 ⇒ 死判据 |
| **G10** | **词表单射** | 每个词 | 一词一义、一词一动作；两词同动作 ⇒ 过度细分 |

### 4.1 为什么是这十个，不是八个或十二个

判据是：**每个生成器必须对应一种"洞的形状"，而洞的形状由"失效的载体"而非"功能"决定。**

G1/G2 管"没想到某一类失效"；G3 管"时间维少一列"；G4 管"默认放行"；G5/G6 管"覆盖面靠记忆"；G7 管"失效被吞"；G8 管"同一事实两处实现"；G9 管"判据是死的"；G10 管"词表不闭合"。

**十个之外还会有第十一个，但新增的判据是"它管哪种洞形状，与现有十个有没有重叠"，而不是"它是不是个好主意"。** 这就是元层的可判据化。

## 6. 新增盲区清单（BL 系列）

编号规则：`BL-载体编号-序号`。每条给证据、给后果、给检测器归属。

### 6.1 已实测取证（4 条）

**BL-01（载体4·挡）误挡：一个无害重定向打穿只读降级。**
`hooks/pre_tool_use.py` 已有一套降级机制（`_READONLY_CMDS`，注释里写得很清楚："一个分不清**提及**与**执行**的钩子，第一天就会被卸载"），且明确把 `>` redirect 列为"不可降级"的理由之一。于是：

```
grep -n "os.remove" egress.py                  ⇒ 放行      （只读动词链，降级生效）
grep -n "os.remove" egress.py 2>/dev/null      ⇒ 被拦      （同一命令，多一个无害重定向）
```

**本会话五条实测记录，其中 ③④ 构成受控对照（只差一个 token）**：

| 序 | 命令形态 | 结果 | 变量 |
|---|---|---|---|
| ① | `grep -n "…unlink…" egress.py \| head -12; …; ls … 2>/dev/null \| wc -l` | **拦** | 链内含 `2>/dev/null` |
| ② | `grep -c "os.remove" egress.py` | 放行 | 无重定向 |
| ③ | `echo … && grep -n "…os.remove…" egress.py \| head -6` | **放行** | 无重定向 |
| ④ | `grep -n "os.remove" egress.py 2>/dev/null \| head -3` | **拦** | 仅多一个 `2>/dev/null` |
| ⑤ | `git commit -F - <<'EOF' … os.remove … EOF` | **拦** | 写路径／heredoc |

③→④ 是干净的 A/B：**同一条命令、同一个文件、只加 `2>/dev/null`**，结论从不拦变拦。
⑤ 是关键补充：降级只覆盖"每个分段都以只读动词开头"的链，**覆盖不到 heredoc**。于是"我要提交一段说明，里面有个词"被判成"我要删文件"。
⇒ 后果：**守卫拦自己的运维、也拦自己的提交。** 而这恰好是代码注释里自己认定"第一天就会被卸载"的那种失效。
⇒ 检测器：G1 载体4×挡 格；修法是能力分析（M5）——问"这段文本有没有能力把词变成执行"，而不是"它含不含这个词"。

**BL-02（载体1·看/判）时钟回拨 ⇒ 静默 fail-open，且可持续一整天。**
`host_shield.py:3262`：

```python
if started_age is not None and started_age <= _STALE_AFTER:
    return "alive"                      # 首拍未到
```

`_sentinel_uptime()` 的注释自己写明「墙钟被回拨时本函数会返回**负数**」。负数 `<= 1800` ⇒ 判"刚启动、首拍未到" ⇒ **返回 alive**。
若用户在哨兵启动后把系统时间往回调一天，`started_at` 就在"未来"，`started_age` 将持续为负 ⇒ **死掉的哨兵在整整一天里都被读成"活着"**。
⇒ 后果：这是"长期绿＝没守卫"的镜像版本，比"长期红"更危险，因为**没人会去查一个一直是绿的灯**。
⇒ 检测器：G1 载体1×看。修法：负值时**不得**落"alive"，应具名 `clock_anomaly` 并归入"看不清"。

**BL-03（载体2·记）磁盘自噬：84 MB／月，零保留策略。**
`~/.antinel/egress` 当前 **84 MB**（首次使用约 1 个月）；`console` 21 MB；`egress.py` 全文无 `KEEP`／`retention`／`prune`／`disk_usage`／`ENOSPC` 处理（已 grep 确认）。
按此速率，一年约 **1 GB**。但更关键的不是体积，是**写失败时会发生什么**。`audit_chain.py:236-238`：

```python
                    f.write(line)
            except OSError:
                pass
        ...
        return rec, got          # got=True（锁拿到了），rec 已算好 prev/hash
```

⇒ 写盘失败被 `pass` 吞掉，然后**照样返回一个"已入链"的记录对象**（带 hash、`got=True`）。而 `got` 只表示**锁拿到了**，不表示**写成功了**——返回值里根本没有这一位。所以即使调用方检查 `got`，也检查不出写失败（`antinel.py:777` 干脆不检查）。
⇒ 后果：**磁盘满 ⇒ 链写不进 ⇒ 调用方以为记下了 ⇒ 我干净地什么都不记 ⇒ 一切绿灯。** 这是安全产品最坏的失效形态：不是报错，是**报成功**。
⇒ 检测器：G1 载体2×记；G7 异常吞咽面（163 个之一，且是**最贵的一个**：它把"记不下来"这个事实本身也一起吞了）。

**BL-04（载体7·看）合盖必然越线，不是偶发。**
`_STALE_AFTER = 3 × HEARTBEAT_SECONDS = 1800 秒 = 30 分钟`。笔记本合盖 8 小时是常态 ⇒ **每天必然产生一次 8 小时的"心跳空档"**，越线 16 倍。
判"陈旧⇒杀重拉"本身是对的（自愈）；**但期间行若把它算成"失守"，用户每天会看到一次红灯**。
⇒ 后果：直接触发"长期红＝没守卫"的死亡螺旋（创始人上一轮已点出）。
⇒ 检测器：G1 载体7×看。修法：区分**主动挂起**与**意外停止**（合盖事件可观测；Windows 有 `WM_POWERBROADCAST`／系统事件日志 6005/6006）。
⇒ 这一条是"载体7 整行"的入口：同一行还有时区、网络切换、杀软误杀。

**BL-05（载体7·报）通知只有"发出"，没有"送达"。**
`inbox_notify.py` 有三种 toast 实现，但**没有任何回执**。Windows 免打扰／通知中心关闭／专注助手 ⇒ 报了，用户没看到，产品不知道。
⇒ 后果：**"我不在时有人替我看"这句话的最后一米是通知，而这一米没有观测。** 用户以为有人看着，其实信息停在通知中心。
⇒ 检测器：G1 载体7×报。修法：至少"未送达则降级为托盘角标 + 首屏横幅"的兜底链，并记一条 `delivery_unknown`。

## 7. 完备性的验收：五条闭合判据（可机器判）

有了生成器，还需要一个"什么时候可以宣布完备"的**判据**，否则又变成感觉。

| ID | 判据 | 机器判法 | 现在 |
|---|---|---|---|
| **C1** | **矩阵无空格**：40 格里每格要么有检测器 ID，要么显式登记"接受此风险＋理由" | 读登记表，空格即红 | ✘（11 格 ✗、14 格未核） |
| **C2** | **默认分支具名**：所有对有限字母表的 dispatch，默认分支不得返回"正常"值 | AST 扫 `else`/`get(k, default)`，值落在正常集合即红 | ✘ **4 处**（探针已就绪，见 §7.1） |
| **C3** | **吞咽可解释**：每个 `except: pass` / `return 默认` 必须有一条"它失败时我当什么"的登记 | 163 处逐条登记；未登记即红 | ✘（0/163） |
| **C4** | **词表单射**：每个成因有且只有一个动作；每个动作有且只有一个成因 | 双向表对拍 | ✓（8×8 单射，探针已证） |
| **C5** | **判据非死**：每条判据有负控，且删除被守物后必须变红 | 变异测试 | △（新套件有，老套件不全） |

**C1 是"完备"的唯一可宣布口径**：不是"所有故障都想到了"，是"40 格每格都有交代"。**交代可以是"我接受这个风险，因为它需要物理接触"——但必须是写下来的交代，不是没人提过。**

### 7.1 C2 不是口号：探针已经写出来并跑过（`output/_p_closure.py`）

为了让"闭合"这条主张可证伪，本轮把 C2 做成了一个能跑的 AST 探针。三个关键设计：

1. **扫描面派生**（32 个模块），不写死——写死就会在加模块后失效。
2. **「正常」取值从产品真源派生**（`inbox_model.STATE_LABEL` 里的 `L0`／「值守中」），不写死——写死就会在改词后失效（假绿第五形态）。
3. **扫空即自报失效**：派生面为空时 rc=2 并打印"这本身就是一次判据失效"，不让它安静地全绿。

实测：

```
扫描面（派生）: 32 个模块
『正常』取值（派生）: keys=['L0'] words=['值守中']

inbox_server   1 处   S1 line 1279  LOGO_MODE.get(..., 'L0')
inbox_tray     3 处   S3 line 161 / 199 / 201   … if … else 'L0'

C2 命中合计: 4 处
```

**负控（必须做，否则它是死判据）**：

| 夹具 | 内容 | 命中 |
|---|---|---|
| bad.py | `return state if state in ("L0","L1") else "L0"` | **1** |
| good.py | 先判 `not in` 就 `raise ValueError("unknown state")` | **0** |

坏写法红、好写法绿 ⇒ 判据活着，且方向正确。

⇒ 这三处 `inbox_tray` 命中就是"未知态被画成绿色「值守中」"的确切位置，`inbox_server:1279` 是第四处（此前未发现）。

## 8. 诚实边界：四件永远做不到的事

写在文档里的边界，比藏在心里的边界安全。

1. **不可能枚举完世界上的失效。** 新硬件、新系统版本、新用法每天产生新失效型。任何"100%"的承诺都是对 ②③ 的偷换。
2. **不可能让"未知"消失。** `unknown` 是它唯一正确的名字。把它消灭＝把失败说成成功（本仓已立此纪律）。
3. **不可能靠判据覆盖"判据本身写错了"。** 判据的错误只能靠负控与双跑发现，不能靠判据自证。这是哥德尔式的外层，只能靠**第二套独立机制**（对拍、双跑、人眼）兜。
4. **不可能让"人"这一行闭合。** 用户会关掉托盘、忽略提醒、卸载重装。能做的是**让"人动了它"这件事本身被记录且可见**，而不是阻止。

## 附录 A：本件的自我证伪条件

1. 若 40 格里有 **>8 格无法判断该归哪一格** ⇒ 说明八类载体不是封闭集，需重划。
2. 若按载体法产出的 BL 里，**>50% 是"理论上可能但工程上不会发生"** ⇒ 说明载体法过于发散，应改为"载体 × 发生概率"加权。
3. 若 **C1 填满后 6 个月内没有一格从"接受风险"翻回"有检测器"** ⇒ 说明登记表退化成了免罪符（狼来了闸的第二形态）。
4. 若有人能给出一个**既不属于 8 类载体、也不是组合**的失效型 ⇒ 载体封闭性假设被推翻，本件的核心论证作废。

第 4 条是我最愿意被人推翻的一条，因为它是本件唯一的强断言。
