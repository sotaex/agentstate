# Antinel·并行协作约定 v1.0（2026-10-21）

**本文件首版。** 管的事只有一件：**同一个仓库里有多条 AI 同时改代码时，怎么才不互相弄丢东西。**

**谁要读**：任何在本仓库并行工作的 AI（不管你在哪个目录、哪条分支、哪个时段）。
开工前读最好；**中途读到也行** —— 所以下面每一节都是自包含的，读到哪一段都能直接用，不要求你看过前面。

**一句话原则**：**损失只发生在"谁有未提交改动"的那段窗口里。** 把这段窗口压到零，就没有任何事会丢。

---

## 0. 三十秒版（赶时间就读这段）

1. **有自己的 worktree，就在自己的 worktree 里改**，不要写主工作区、不要提交进 `main`。
2. **提交只 `git add` 你改的那几个具体文件**，禁用 `git add -A` / `git commit -a`。
3. **共享文件动之前先知会一声**（清单在 §4）。
4. **在飞改动不许裸在工作区**：要暂停就 `git switch -c wip/<线>-<日期>` 提交一次。

## 2. 三条硬规则（每条都附一句"为什么"）

### R1 工作树归属：改代码只在自己的 worktree

- 主工作区（`D:/psl/poc/antinel-security`，分支 `main`）**只属于主线的那一个 AI**。
- 有自己 worktree 的（`.worktrees/night` → 分支 `night-t1t5`；`.worktrees/b` → 分支 `stream-b`），**只改自己目录里的文件**，提交进自己的分支。
- 合并进 `main` 是**一次明确的动作**（§9），不是顺手的事。

**为什么**：两条线共用一个文件目录，就是共用一块黑板——你写的时候我可能正在擦。worktree 让两块黑板物理分开。

```
cd D:/psl/poc/antinel-security/.worktrees/night
git fetch origin && git merge main        # 开工先把主干的新东西拿进来
git add <你改的文件1> <你改的文件2>
git commit -m "..."
```

### R2 提交只 add 自己改的具体文件

**禁用 `git add -A`、`git add .`、`git commit -a`。**

**为什么**：主工作区里可能躺着**别人**的在飞改动。一把梭就把它卷进你的提交——内容没丢，但归属错乱，事后要凭记忆去分哪些是你的，比丢失更难查。

### R3 共享文件动之前先知会

清单见 §4。**为什么**：这些文件两条线都改过，同一时段两个人改同一段，git 可能自动合并成一个"两边都过、语义上却打架"的结果，这种错最贵。

## 3. 开工／中途的检查清单（五步，可机械执行）

```
git worktree list                  # ① 现在有几条线、各自在哪个目录
git status --short                 # ② 有没有**不是我改的**文件是脏的
git log --oneline -5               # ③ 最近几个提交是谁的、我基于的是哪一份
```

④ **发现别人有在飞的改动**：**先落补丁留档，再动手**（`git diff -- <那些文件> > output/_incoming_<线>_<时间戳>.patch`），**不要动它、不要替它提交、不要清理它**，在对话里知会一声。
⑤ **要动 §4 里的共享文件**：先说一声，等对方回一句"我不动"再开始。

## 5. 在飞改动怎么放：不许裸在工作区

**要暂停、要收工、要等别人确认 —— 就提交到一个 wip 分支**：

```
git switch -c wip/<线>-<日期>
git add <你的文件>
git commit -m "WIP：<一句话>"
```

**为什么"留个补丁"不够**：补丁文件本身也在工作区里，一样会被下一次刷写覆盖。分支有 ref 指着，**永远不会丢**。

---

## 6. 运行态：服务是从磁盘拉起的

- 现在的服务（端口 5846）是**从主工作区拉起的**；别人提交后**不会自动生效**，要杀掉 serve 进程，守护进程会按 `~/.antinel/console/url.json` 重拉（端口口令一般不变，但**每次都要重新读那个文件确认**，端口只在被占时才漂）。
- 你要用自己的代码起服务做活体验证：**用独立端口 ＋ 独立中枢**（`ANTINEL_HUB_DIR` 指到别的目录），否则会跟主线那条抢。
- 回读页面前先确认一句：**我要读的是哪一份代码？**

## 7. 提交信息要写清四件事（便于事后归因）

```
批次/主题
病根（不是"改了什么"，是"为什么会错"）
修法（机制层：收成一份实现／换哪个口径）
判据与验证（哪几条、单跑还是全量、活体回读的结论）
```
**为什么**：并行时最贵的不是修错，是**三个月后说不清这行是谁为什么改的**。

---

## 8. 冲突已经发生了怎么办

- **不要用整文件还原、整树 `stash`、`reset --hard` 去处理别人的改动** —— 那是最常见的一次性抹掉对方全部在飞工作的方式。（Antinel 自己的 DST-07 会拦这类命令，2026-10-21 我写文档时提到它就当场被拦了一次。）
- 要恢复：**按 hunk 精准恢复**（先看 `git diff <commit> -- <file>` 判性质：纯回退才整文件，混合文件只恢复属于你的那些 hunk）。
- 拿不准：**先落补丁留档，再问**，别猜。

---

## 9. 合并进主干

- 谁的活谁提；合并由**一次明确的动作**完成（merge 或 cherry-pick），不混在别的批次里。
- 合并前：两侧各自的套件跑一遍相关判据（**逐条单跑即可，非必要不跑全量**）。
- 提交钩子会跑**快道闸门**——**快道不是全量凭证**（它自己会打印"本次跑了 N/34 套"）。全量凭证只有 `python ci/delivery_gate.py`，留给打包前/CI。
