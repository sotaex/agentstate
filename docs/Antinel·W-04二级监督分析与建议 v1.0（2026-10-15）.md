# Antinel · W-04 二级监督：分析与建议 v1.0（2026-10-15）

> 触发：创始人 07:2x 实测「值守台整套静默消失（无 python 进程、8790/14305 均无监听）」，
> 追问「是不是旧病复发、新修订的机制层没起作用」，并要求「W-04 的单点要不要补一级监督 —— 做个分析并给建议」。
> 本文**只分析、只提案，未改任何代码**（改不改由创始人拍板）。

---

## 0. 一句话结论

**不是旧病复发，也不是机制层失效，而是 W-04 的监督链只有一层、且那一层自己没人管。**

- 旧病（2026-10-14 及之前）的症状是「**服务多开**」；这次症状相反，是「**整套静默消失**」。
- A1–A6 机制层管的是**判据套件自身**（登记规范／常驻上限／看守期／重叠审计／L2 触发层），
  **不负责运行时进程存活**。用它解释「服务没了」是把两件事说成一件事。
- 运行时存活归 **W-04**。W-04 这次没救回来，原因是它的监督链是**单层**：

```
[谁起 daemon?]  ← ← ← ★ 这一格是空的
      ↓
   daemon（supervise 单例）
      ↓  每 tick 调 ensure_console()
   console 服务（被 DETACHED_PROCESS 另起）
      ↓
   窗口（经 daemon 推托盘动作 → open_console_now）
```

**监督者（daemon）与被监督者（console）同生共死：daemon 一旦退出，没有人会把它拉回来，
也没有人会向上报「失守」——因为上报者就是它自己（哨兵）。**

## 2. 单点到底在哪（拆到最小）

W-04 的**判活口径本身是硬的**（F1 第②条：pid 与端口两条都要，专门防 pid 复用与端口被占）——
**这一层没问题，不需要改**。

问题全在**谁在看守看守者**：

| 环节 | 谁负责重拉它 | 现状 |
|---|---|---|
| console 服务被杀 | daemon（`ensure_console`，60 秒内） | ✅ 有机制，且 07:15 前实测有效（kill 后 8 秒重拉，见 07:15 记录） |
| **窗口消失** | daemon（推托盘 `open` 动作） | ⚠️ 有路径，但**取决于调用方走的是 `window` 还是 `daemon` 那条**（F5 会降级直起） |
| **daemon 被杀 / 随宿主回收** | **无人** | ❌ **空格** |
| daemon 不在时，谁知道？ | **无人**（上报者就是哨兵自己） | ❌ **静默** |

⇒ 这是一个**「最后一跳没人管」**的结构：链条末端（服务）保护得很好，链条源头（daemon）裸露在外。

## 3. 为什么这次会踩中（本轮的实证链）

1. 我用**会话内后台任务**（`run_in_background`）拉起 daemon ⇒ daemon 挂在会话/沙箱的进程树上。
2. 期间宿主连续报 `SandboxError`，随后组件被拆（F8）⇒ 沙箱重建，**整棵进程树被回收**。
3. daemon 没了 ⇒ 没人重拉 console ⇒ console 也没了（daemon 是先于它死掉的，所以连"重拉"这个动作都不会发生）。
4. 于是 07:26 看到的是「无 python 进程 + 无监听」，**且没有任何告警**。
5. 反证（很干净）：F4 的同一台机器、同一批实验已经证明——**差别不在"起法"，在"谁来起"**。产品自己写过这句话。

**结论：这是我的拉起方式踩了产品已经识别过的坑，不是产品退化。**
但**产品确实留了一个真空格**：连"正确的人"（daemon）自己都没有人管。

## 4. 补级监督：四个选项

### 选项 A —— 把 daemon 注册为 **Windows 计划任务**（OS 级二级监督）

- **做法**：`schtasks` 注册「用户登录时启动」+「任务失败/停止后重启（间隔 1 分钟，最多 N 次）」；
  执行体＝`antinel.cmd inbox daemon --supervise`（或产品自带的等价入口）。
- **优点**：**唯一与 Antinel 自身解耦的监督者**——即使 daemon、console、托盘全死，OS 仍会拉；
  不依赖任何"自己人"活着；符合"要由活得比窗口久的进程起"这条已验证的原则（OS 是那台机器上最长的命）。
- **代价/风险**：
  - 需要在**安装/启用**时写计划任务（一次性的写操作，属"写命令七步"范畴：须走 diff 预览 + 影响声明 + 用户同意）；
  - 用户可能介意"在系统里注册了一个自启项"——须在 UI 里明说、可一键撤销；
  - `schtasks` 在企业策略受限环境下可能被拒 ⇒ 必须**失败即降级**（回落 B/C），且**如实说明降级了**。
- **可逆性**：高（一条 `schtasks /delete` 即撤）。

### 选项 B —— **互监督**（console ↔ daemon 心跳互看）

- **做法**：daemon 每 tick 写心跳时间戳；console 侧若发现"daemon 心跳过期"⇒ 用 `DETACHED` 重拉 daemon。
- **优点**：不依赖 OS，纯进程内实现；改动面小（复用既有 tick 与落盘）。
- **致命弱点**：**两者同时被回收时仍然全灭**（本轮正是这种情形——job 杀整树）。
  它把"单点"变成"两点互看"，但对"整树被端"这一类**毫无抵抗力**。
- **可逆性**：高。

### 选项 C —— **托盘（tray）兼任二级监督**

- **做法**：托盘是用户面常驻、由用户手动启动 ⇒ 活得通常比 daemon 久；让它兼看 daemon 心跳，过期则重拉。
- **优点**：不写系统项；托盘本来就在。
- **弱点**：托盘仍是"自己人"，且**托盘由谁保证活着**同样是空格（只是把空格挪了一格）。
  另：托盘若被用户主动退出，会连带失去监督 —— 语义上要区分「用户主动退出」与「意外死亡」。

### 选项 D —— 什么都不做，只把**边界写进文档**

- **做法**：明说「daemon 不自愈；长期常驻请用正规入口（`%USERPROFILE%\.antinel\antinel.cmd`）或自启」。
- **优点**：零风险。
- **弱点**：把问题留给用户；而用户**看不到任何提示**——本轮就是"静默消失"，最危险的形态。

## 5. 建议（推荐组合）

**推荐 A 为主、B 为辅、C 视需要，D 的文档动作无论如何都要做**：

| 优先级 | 动作 | 为什么 |
|---|---|---|
| **P0** | **A：注册计划任务**（登录自启 + 失败重试） | 唯一能把"空格"填成"OS 级兜底"的选项；且现有安装流程本来就要落自启（登录自启已在判据里出现），增量小 |
| **P1** | **B：daemon ↔ console 心跳互看** | 覆盖"只死一个"的常见情形（成本低）；但**必须同时承认它对"整树被端"无效**，不许写成"已解决" |
| **P1** | **可见性**：daemon 不在 ⇒ **在 UI 上出声** | 本轮最刺眼的不是"它死了"，是"**它死了没人说**"。哪怕不做 A/B，也要让"无 daemon"这个状态在第一个能打开的地方可见 |
| **P2** | **C：托盘兼看** | 视 A/B 落地效果再定；注意区分「用户主动退出托盘」与「意外死亡」 |
| **P0（文档）** | **D**：在用户可见处写明「谁负责拉起值守台」 | 与上面并行，成本几乎为零 |

**一句话**：先补 **A**（把"谁来起 daemon"这个问题交给 OS），再加 **B**（覆盖单点死亡），
同时**必须加可见性**——因为没有可见性的自愈只是"安静地活着"，而本轮暴露的是"**安静地死掉**"。
