# Antinel·0.53.0 两处页面缺陷的根因与机器防线 v1.0（2026-10-18）

> **这份文档是什么**：创始人 2026-10-18 指出两处页面缺陷（账本出现「防护缺口／缺口」、
> 看不到是哪个 AI 编程工具），要求"对照设计文件确保修订正确，并反思为什么会出现、
> 今后如何从机器层面根治，不要 happy path 的办法"。本文记录：① 修订与设计文件的
> 逐条对照；② 三层根因；③ 已落地的机器防线与仍缺的一条；④ 为什么这些不是 happy path。

---

## 一、两处缺陷的事实与修订

### 1.1 账本出现「防护缺口」与「缺口」

**事实**：六态是封闭集合（`inbox_model.STATE_LABEL`）：

| 代号 | 标准名 |
|---|---|
| R0 | **失守** |
| L2 | 拦截 |
| L1 | 注意 |
| Ls | 缺粮 |
| L0 | 值守中 |
| dev | 研发中 |

**「防护缺口」不在这个集合里。** 它在账本页出现于 4 处，另在收件箱与 remediation
出现 5 处：

| 位置 | 原文 | 落点 |
|---|---|---|
| 账本每日格 | 防护缺口 26 | `inbox_server.py` 账本区（`breached` 格） |
| 账本月行 | 缺口 189 | 同上（月行 summary） |
| 账本词条 | 防护缺口 | `glossary.py` `ledger_breached.w` |
| 账本词条排除句 | 那是「防护缺口」 | 同上 `exc` |
| 收件箱条目标题 | 钩子注册文件被改动（防护有缺口） | `remediation.py` |
| 收件箱条目标题 | 防护有缺口（未归类） | `remediation.py` ×2 |
| 收件箱「不做的后果」 | 只能看到「有缺口」 | `remediation.py` |
| 顶部条状态句 | 此刻没查出缺口 | `inbox_model.py` |
| 收件箱「要处理」词条 | 防护有缺口、…… | `glossary.py` |

**词源**：`防护缺口` 是 0.48 时代旧词（`antinel-0.48.2/glossary.py` 已有）。0.51.0
六态定名（commit `f6fc49a`）把 R0 定为「失守」，**账本这一份没有跟着改**。

**修订**：九处一律改为六态标准名「失守」或平实描述（"有东西没被挡住"／"有问题"）。

### 1.2 看不到是哪个 AI 编程工具

**事实**：运行状态页「工具识别」行原文：

> 近 7 天 477 条记录里，104 条认得出是哪个工具（有直接证据 104 条），373 条说不清（78%）；……

括号里的「有直接证据 104 条」是**置信度**，不是工具名。句子承诺"认得出是哪个
工具"，却永不给出那个名字。

**修订后**：

> 近 7 天 477 条记录里，104 条认得出是哪个工具——**全是 WorkBuddy**（有直接证据 104 条），373 条说不清（78%）；……

工具名走 `M.host_distribution`（唯一实现），显示名走 `_host_label`（宿主表 `name`）。
单工具时写「全是 X」（与总量并列会被读成占比），多工具时写「A n 条、B n 条」，>3 种截断。

## 二、修订与设计文件的逐条对照

| 设计要求 | 原文位置 | 本次修订如何满足 |
|---|---|---|
| 事实→家映射固定：**状态词→顶部条** | §5.1 | 账本不再自造态名，格子词从 `M.STATE_LABEL` 派生；顶部条仍是状态词的唯一家 |
| **口径唯一**：工具维度扩进 `M.day_counts`，渲染层禁自算 | §5.2-2 | 账本四格数字仍只来自 `M.day_counts`；本次只改词，不动数 |
| **声明可验证**：状态词、工具名必须能追到结构化数据 | §5.2-3 | 态名追到 `STATE_LABEL`；工具名追到 `host_distribution` + 宿主表 `name` |
| **徽标四态：工具名（env 铁证）／可能是 X／来源不明／旧记录** | §6 | 「工具识别」行现在点名（env 铁证那一档）；说不清那部分仍如实说"说不清" |
| 归并行与日报排行显示分布 | §6 | 未动（本机单工具，`host_count=1`，按既有开关不显示——设计 §19.2 已声明此机不可自证） |
| 账本：撤头部四卡／区一起点改昨天／按月折叠不动 | §4.3 | 均未动，本次只改格子词 |
| 运行状态：工具识别块（判定方式／成功数／说不清占比／旧记录分代） | §4.4-1 | 四样都在；本次**新增点名** |

**必须指出的一处设计缺口**：§4.4-1 对「工具识别」块的枚举（判定方式／成功数／
说不清占比／旧记录分代）**没有"点名工具"这一项**，而 §6 明确要求「工具名」。
两份要求分散在不同章节，实现与判据都只跟了 §4.4 ⇒ 句子里有"认得出是哪个工具"
却永不给名字。**本次修订是按 §6 补齐 §4.4 的枚举缺口**，建议设计文件 v1.13 把
§4.4-1 改成「判定方式／**是哪个工具（点名）**／成功数／说不清占比／旧记录分代」。

## 三、根因：为什么机器一条都没发现

### 3.1 问题一：判据替旧词背书（最危险的一层）

不是"某个人忘了改一个词"，而是**判据把旧词抄成了期望值**：

```python
# 0.53.0 的 ci/inbox_guards_0490.py（T-04）
for word, key, lv in (("拦截", "blocked", "L2"), ("注意", "noticed", "L1"),
                      ("防护缺口", "breached", "R0")):
```

产品渲染「防护缺口」，判据断言页面必须有「防护缺口」⇒ **两边一致、全绿**。
改六态名的人只改了六态表；改判据的人从实现抄了字面量。**抄写把错误固化成了标准。**

三层原因：
1. **命名源分裂**：态名的权威是 `STATE_LABEL`，但账本格子里是硬编码字面量——第二份命名源。
2. **判据从实现派生，而非从权威派生**：判据的期望值抄自实现 ⇒ 产品错，判据跟着错。
3. **没有词表闭包检查**：现有判据查"数字同源"（F40）、"句子不重复"（指纹），
   但没有任何一条查"页面上的态名 ⊆ 权威词表"。

### 3.2 问题二：判据照"句子"写，不照"问题"写

U22 原有五条腿：分母对／成功数对／置信度对／说不清占比对／空态说真话。

**五条腿全部是这句话的组成部分，没有一条是"这一块要回答的问题"。**
于是出现最荒唐的形状：**一个专门回答"是哪个工具"的块，判据不检查工具名。**

三层原因：
1. **尺子照抄实现结构**：把句子拆成字段逐项验算，误以为"字段都对"＝"块被守住"。
2. **设计要求分散且无承接检查**：§4.4 与 §6 对同一块的要求不一致，没有机制检查
   "每条设计要求是否都有判据承接"。
3. **句式陷阱**："认得出是哪个工具"读起来像答案在句中，实际括号里是置信度；
   纯数字比对读不出"承诺未兑现"。

## 四、机器防线（根治，不是 happy path）

### 防线 A · 派生（已落地）

**做法**：账本格子的态名从 `M.STATE_LABEL` 派生，产品与判据**同一个源**。

```python
for key, lv in (("blocked", "L2"), ("noticed", "L1"), ("breached", "R0")):
    word = M.STATE_LABEL[lv]
```

判据侧同样写 `word = M.STATE_LABEL[lv]`。

**为什么这是根治**：改六态名 ⇒ 产品与判据**同时**变，物理上不存在"改一边忘一边"。
不是"加一条不许写旧词的检查"，而是让旧词**没有地方可写**。

### 防线 B · 闭包闸（已落地）

**判据**：`T-04e`／`N-T04e`。扫五页可见文本（`PC.body`，S48 口径），命中退休态名即红。

```python
_RETIRED_STATE_WORDS = (
    ("防护缺口", "0.51.0 定名「失守」后退役（0.48 旧称）"),
    ("缺口", "同上；裸用会被读成第四种态"),
)
```

**为什么必须有它**：派生只能保证"新写的对"，不能保证"旧词不从别的渲染路径回来"
（收件箱条目标题、remediation 文案、未来新增页面）。

**它不是装饰——上线当刻就抓到了 5 处我漏掉的地方**（`remediation.py` 4 处、
收件箱「不做的后果」1 处）。这正是"负控有效"的实证。

负控：喂「防护缺口」必红、喂月行「缺口」必红、喂合法「失守」不许误伤。

### 防线 C · 问题-答案闸（已落地）

**判据**：U22 ①b 腿 + `N-U22c` 负控。

- ①b：句子里必须出现夹具里每个工具的**显示名**（从 `_host_label` 派生，不硬编码品牌）。
- ③ 腿：单工具时也必须点名（「全是 WorkBuddy」）。
- `N-U22c`：`_dist = []`（把工具名摘掉）⇒ U22 必须红，且红因必须含「点名」。

**为什么这是根治**：它守的不是"某个数"，而是"这一块的问题有没有被回答"。
判据的期望值来自数据（`host_distribution`／宿主表），不来自句子形状。

### 防线 D · 设计要求→判据映射（**未落地，本次提出的下一步**）

**问题二的结构性根因**是：设计要求分散（§4.4 与 §6），且**没有任何机制检查
"每条设计要求是否都有判据承接"**。人读漏一节，机器不会提醒。

**提议**：建 `docs/设计条款-判据映射.json`：

```json
[
  {"clause": "§4.4-1", "requirement": "工具识别块：判定方式／点名工具／成功数／说不清占比",
   "guarded_by": ["U22", "N-U22c"]},
  {"clause": "§6", "requirement": "工具名（env 铁证）",
   "guarded_by": ["U22", "HN15", "U21"]}
]
```

配一条元判据：**设计文件里出现的每个 `§x.y` 条款号，必须在映射表里有登记且
`guarded_by` 非空**；未登记即红。新增设计条款不同步登记 ⇒ 交付闸门不通过。

**为什么这条最难但必须做**：前三条防线守的是"已知的两个词/一个句子"，
这条守的是"下一次没人读到的那个章节"。落它需要一次人工填表（约 30–40 条），
建议作为 0.54.0 的第一件。

## 五、为什么这不是 happy path

happy path 的形状是：**就着这次的错，加一条刚好能抓住这次的检查**。例如：

- ❌ 写一条 `assert "失守" in page`——它抓得住这次，抓不住"下次改成别的词"。
- ❌ 把「WorkBuddy」硬编码进判据——品牌一换，判据要么误红、要么被改成新品牌名。
- ❌ 只在账本页扫旧词——收件箱那 5 处正是这么漏掉的。

本次三条落地的共同形状是：**期望值从权威源派生，尺子不复制实现的字面量**。

- 态名 ← `STATE_LABEL`（唯一命名源）
- 工具名 ← `host_distribution` + 宿主表 `name`（唯一归因源）
- 旧词 ← 退休词表（登记即永久，堵住所有渲染路径）

判据不再"抄实现"，而是"验权威"。
